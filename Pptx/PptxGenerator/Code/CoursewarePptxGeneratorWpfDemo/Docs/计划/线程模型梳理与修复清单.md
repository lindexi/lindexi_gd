# CoursewarePptxGeneratorWpfDemo 线程模型梳理与修复清单

## 1. 文档目的

本文是本轮线程问题修复的唯一实施依据。目标不是继续给代码“补 Dispatcher”，而是先回答以下问题：

1. 哪些对象具有 WPF/UI 线程亲和性；
2. 哪些对象只是普通业务状态，但会被 WPF 绑定观察；
3. 哪些异步方法允许在任意线程继续执行；
4. 哪一层负责把最小状态提交切回 UI 线程；
5. 哪些事件只表达业务完成，不应承诺订阅者线程；
6. 当前未提交改动中哪些修复方向正确，哪些逻辑必须撤销或重构。

本文明确禁止：

- 把完整业务流程、网络调用、模型流或 XML 流水线整体包进 Dispatcher；
- 使用 `.Result`、`.Wait()`、`GetAwaiter().GetResult()` 等异步转同步；
- 把 `ConfigureAwait(false)` 理解为“切到后台线程”；
- 依赖“调用入口碰巧来自 UI 线程”来保证后续所有通知安全；
- 使用 fire-and-forget Dispatcher 掩盖状态写入顺序或异常。

## 3. 必须统一的概念

### 3.1 `await` 不是线程切换 API

- 普通 `await`：等待异步操作；如果存在同步上下文且 awaiter 需要恢复上下文，续体可能回到该上下文。
- `ConfigureAwait(false)`：表示当前等待之后不要求恢复捕获的上下文；它不保证续体运行在线程池，也不创建后台工作。
- Dispatcher：只应用于明确需要某个 UI Dispatcher 的最小操作。
- CPU/IO 业务方法：默认不应要求 UI 线程，也不应为了“后台化”而使用 Dispatcher 或 `ConfigureAwait(false)`。

### 3.2 UI 线程亲和对象与 UI 可观察状态不是同一概念

#### 真正具有 WPF 线程亲和性的对象

- `RenderTargetBitmap`、`DrawingVisual`、WPF 文本/图像渲染相关对象；
- 未冻结的 WPF `Freezable`；
- WPF 控件和其他 `DispatcherObject`；
- WPF 绑定集合在 UI 正观察和枚举时的写入操作。

#### 普通 CLR 对象，但其通知被 UI 观察

- `CoursewareWorkspaceViewModel`、`CoursewareSlideWorkspaceViewModel`、`CoursewareSlideItemViewModel`；
- `SlideMlRenderTool.Latest*`；
- `SlideGenerationPipeline` / `SlideChatManager` 的 `PropertyChanged`；
- `CopilotChatMessage.MessageItems` 和其中各消息项属性；
- `ICommand.CanExecuteChanged`。

这些对象本身未必继承 `DispatcherObject`，但它们的集合写入和通知必须有清晰、稳定的 UI 提交策略。

### 3.3 事件默认不承诺线程

核心库事件应遵循：

- 在产生事件的操作线程同步触发；
- 订阅者若写 UI 状态，由订阅者或更靠近 UI 的适配层负责调度；
- 只有事件契约明确声明 UI 线程时，发布者才可承担 UI 调度。

否则，核心流水线会被 UI 框架污染，非 UI 调用方也会被迫等待无关 Dispatcher。

### 3.4 .NET 异步与线程调度最佳实践

#### 3.4.1 `Task` 必须表示完整操作生命周期

- 一个公开或内部可等待方法返回的 `Task`，应在该操作的业务工作、结果提交、失败/取消状态提交和必要清理全部完成后才结束。
- 如果调用方在 `await` 返回后仍可能看到迟到的 `PropertyChanged`、集合写入、命令通知或活动管道切换，该方法的完成契约就是不完整的。
- `async` 应一路向上传播。真正的 UI 事件处理器可以使用 `async void`；`ICommand.Execute` 虽然也是 `void` 接口，但异步命令适配器应保持同步 `void`，只负责启动并观察一个可等待任务，不能把实现改成 `async void`。
- 必须长期运行但不能由当前调用方等待的任务，需要有明确的生命周期所有者、取消令牌、异常观察和关闭等待；不能只写 `_ = SomeAsync()`。

#### 3.4.2 `await` 只描述等待，不描述线程所有权

- `await` 前后的线程不能作为业务正确性的隐含条件。
- UI 层可以选择依赖同步上下文，也可以选择 `ConfigureAwait(false)` 后显式提交，但同一方法必须采用一致策略；禁止只在成功分支显式调度、在 `catch`/`finally` 中继续直接写 UI 状态。
- 类库默认不承诺恢复调用方上下文；UI 层不得假设调用某个类库方法后自然回到 UI 线程。
- `ConfigureAwait(false)` 不是性能开关、后台线程开关或解除 UI 亲和性的工具。它只表示当前 await 不要求恢复捕获上下文。
- WPF 异步命令是明确例外：生产入口 `ICommand.Execute` 已由 WPF 在 UI 线程调用，命令内部应保留该同步上下文。若命令自己使用 `ConfigureAwait(false)`，随后再注入 Dispatcher 调度 `CanExecuteChanged` 或异常回调，就是先破坏正确线程契约、再用额外抽象修补自己制造的问题。

#### 3.4.3 先确定状态所有者，再确定 Dispatcher 边界

- `SlideMlRenderTool` 拥有 `Latest*`，因此由它负责结果缓存的可等待提交。
- `MainWindowViewModel` 拥有 `IsBusy`、`StatusText`、`IsIterating`、可编辑文本和命令状态，因此这些状态必须由 ViewModel 的 UI 提交边界负责。
- 一个被调用对象完成了自己的 Dispatcher 提交，不会把调用方的后续续体“传送到 UI 线程”，也不会替调用方提交其他状态。
- 每份可观察状态只设置一个提交所有者；上层不能再次包裹下层结果提交，下层也不能越层修改上层 ViewModel 状态。

#### 3.4.4 Dispatcher 只执行短小、同步、不可异步打断的提交

- Dispatcher 委托只做字段赋值、集合最小变更和同步通知。
- 不在 Dispatcher 内执行网络请求、模型调用、MCP 连接、文件 IO、XML 解析、图片编码或等待外部异步操作。
- UI 提交 API 优先接受 `Action`；如果底层框架接口只能接受 `Func<Task>`，适配层应立即执行同步 `Action` 并返回已完成任务，不把任意异步委托暴露给 ViewModel。
- 需要一起被 UI 观察的状态应在同一个同步提交中更新，例如完成状态文本和 `IsBusy = false`，避免 UI 看到中间组合。

#### 3.4.5 命令、事件和进度必须拥有异常与顺序契约

- `ICommand.Execute` 是同步 `void` 入口，异步命令适配器应在其中启动受控的 fire-and-forget 观察任务；实际执行任务必须由 `ExecutionTask` 持有，异常由观察任务捕获并交给显式异常回调。
- 命令自身的开始/结束 `CanExecuteChanged` 应自然保持 `ICommand.Execute` 进入时的 UI 同步上下文，不为命令注入 Dispatcher，也不在命令内部使用 `ConfigureAwait(false)`。ViewModel 从其他异步路径主动调用 `RaiseCanExecuteChanged` 时，调用方仍须保证自己位于其 UI 状态提交边界。
- `ExecuteAsync` 是供测试或显式调用方等待的入口，不承诺把任意工作线程调用自动调度到 UI；线程所有权测试必须从真实 WPF Dispatcher 调用它，不能用“工作线程调用后命令自行切回 UI”固化错误契约。
- 核心业务事件默认同步在线程中立的操作线程触发；UI 订阅者负责把自己的最小状态提交到 UI。
- 如果事件处理结果是操作完成的一部分，发布 API 应提供可等待回调或由更高层显式等待状态提交；不能依赖 `void` 事件中的 fire-and-forget Dispatcher。
- 高频进度需要有序队列、可等待回调或可排空机制；普通 `IProgress<T>` 在存在同步上下文时会异步投递，不能天然代表“报告完成即 UI 已更新”。

#### 3.4.6 线程安全与 UI 调度是两个不同问题

- Dispatcher 解决的是线程亲和对象和 UI 可观察通知边界，不自动解决普通字段的并发读写。
- 活动管道、会话代次、取消源和后台初始化状态需要按数据竞争选择 `Interlocked`、`Volatile`、锁、不可变快照或串行队列。
- 多个相关字段被后台线程读取时，应优先发布单个不可变快照，而不是假设“它们在 UI 线程连续赋值”就等于跨线程原子可见。
- 取消和 Dispose 后的回调必须通过会话代次、令牌或所有权检查拒绝迟到提交。

#### 3.4.7 WPF 专用规则

- `DispatcherObject` 只能由所属 Dispatcher 访问；`Freezable` 只有在成功 `Freeze()` 后才可跨线程读取。
- `ObservableCollection` 的修改、绑定属性通知和 `ICommand.CanExecuteChanged` 应在绑定 UI 的 Dispatcher 上发生。
- `Application.Current.Dispatcher` 只属于当前 WPF 应用；核心库不能自行假设它存在。
- 无 `Application` 的测试/工具场景可使用专用 STA Dispatcher，但初始化和关闭都必须异步且可观察。

### 3.5 ViewModel 异步操作的统一模板

每个由 WPF 命令触发的长操作应按以下阶段组织：

1. **UI 开始提交**：检查可执行条件，快照输入、集合和选项，设置 `IsBusy`/状态文本并触发命令通知；
2. **线程中立工作**：在 Dispatcher 外等待模型、渲染、MCP、文件和评估操作；
3. **形成结果**：在普通局部变量中记录成功、取消或失败结果，不直接写绑定属性；
4. **UI 结束提交**：在一个可等待的短同步提交中写最终状态、清理 `IsBusy`/`IsIterating` 并完成命令通知；
5. **任务结束**：只有第 4 步完成后，命令执行任务才允许完成。

入口若严格保证只由 WPF UI 命令调用，第 1 步可同步执行。ViewModel 若还提供非命令调用入口，应由 ViewModel 方法自己的线程契约处理 UI 提交，不能把 Dispatcher 注入命令来伪装所有入口都来自 UI。无论选择哪种方式，第 2 步之后的 ViewModel 写入都必须遵循该 ViewModel 已确定的统一策略。

### 3.6 错误示范

#### 错误示范 A：只修成功分支

```csharp
await service.RunAsync().ConfigureAwait(false);
await dispatcher.InvokeAsync(() => StatusText = "完成");

// 错误：取消、失败和 finally 已经不保证位于 UI 线程
catch (OperationCanceledException) { StatusText = "已取消"; }
finally { IsBusy = false; }
```

正确方向是先在局部变量中确定最终状态，再在一个可等待的 UI 提交中同时更新 `StatusText` 和 `IsBusy`。

#### 错误示范 B：把下层提交误认为上层也安全

```csharp
await renderTool.ApplyRenderResultAsync(result).ConfigureAwait(false);
StatusText = "重新渲染完成";
IsBusy = false;
```

`ApplyRenderResultAsync` 只拥有 `renderTool.Latest*` 的提交契约，不能为 ViewModel 的后续写入提供线程保证。

#### 错误示范 C：把完整异步流程放入 Dispatcher

```csharp
await dispatcher.InvokeAsync(async () =>
{
    await model.CallAsync();
    await File.WriteAllBytesAsync(path, bytes);
    StatusText = "完成";
});
```

这会扩大 UI 占用范围，并错误暗示整个异步委托始终属于 UI 线程。正确做法是在 Dispatcher 外完成工作，只调度最后的同步状态提交。

#### 错误示范 D：未观察任务

```csharp
_ = dispatcher.InvokeAsync(UpdateUi);
_ = TryEnableMcpAsync();
_ = EvaluateContextAsync(context);
```

除非任务由明确的后台任务所有者登记、观察、取消并在关闭时等待，否则这些写法会丢失异常、完成顺序和生命周期。

#### 错误示范 E：让核心事件承诺 UI 线程

```csharp
await dispatcher.InvokeAsync(() => Rendered?.Invoke(result));
```

核心事件应在线程中立的操作线程同步触发；需要 UI 的订阅者自行提交自己的状态。

| `AppendMessagesToSessionAsync` | 内部调用 `ChatManager.TryRunInMainThread`，会处理会话可见集合写入 | 不再外层重复 Dispatcher |
| `AppendResponseUpdate` | 明确不隐式调用 Dispatcher；直接修改 `CopilotChatMessage.MessageItems` 和消息项属性 | 当消息正在 WPF 中绑定显示时，调用方必须在 UI 提交边界执行 |
| `StartChatting` / scope `Dispose` | 修改 `CopilotChatManager.IsChatting`；`OnPropertyChanged` 自行尝试主线程通知，但字段写入发生在调用线程 | 不应为了字段本身把整个流包进 UI；需避免跨线程读写竞态，并明确通知边界 |
| `GetChatClientAgentAsync` / `GetAgentSessionAsync` | 模型/会话初始化，无 UI 集合写入要求 | 任意线程，自然异步 |

## 5. 目标线程契约

### 5.1 `SlideMlRenderPipeline`

- `NormalizeXml`、解析、`PreLayout`：不要求 UI 线程。
- `PreMeasure`、`FinalLayout`、框架渲染：由 `SlideMlRenderPipeline` 在其注入的 `IMainThreadDispatcher` 上执行。
- `RenderAsync` 返回后不承诺调用方线程。
- WPF 输出 `RenderTargetBitmap` 当前已调用 `Freeze()`；冻结后的位图可跨线程读取。

### 5.2 `SlideStreamingPipeline`

- 是核心业务编排层，不拥有 UI Dispatcher。
- 片段提取、DOM 合并、上下文错误收集和事件触发都在调用操作的当前线程顺序执行。
- `Rendered`、`FragmentReceived`、`StreamCompleted`、`StreamInterrupted` 不承诺 UI 线程。
- 不等待任何 UI 通知；只等待真正的渲染操作完成。

### 5.3 `SlideMlRenderTool`

- `Latest*` 四个属性必须在同一个不可被异步打断的同步提交中按顺序更新，然后才允许发出 `SlideRendered`。
- 更新完成必须可等待，禁止 fire-and-forget Dispatcher。
- `SlideMlRenderTool` 已经持有创建它的 UI 框架 Dispatcher，因此由它提供 `ApplyRenderResultAsync` / `ResetLatestResultAsync` 作为唯一、可等待的结果提交边界；调用方不再自行包 Dispatcher。
- 该边界只提交四个缓存字段和同步通知，不执行渲染、模型调用、文件 IO 或其他长耗时操作。
- `IPreviewImage.Save` 不能一概假设需要 UI Dispatcher：
  - 冻结的 `WpfPreviewImage` 可跨线程编码；
  - `FilePreviewImage` 是普通文件 IO；
  - Avalonia 实现应由其自身契约决定。
- 若接口无法表达具体图片线程要求，应优先让实现返回可安全跨线程的不可变快照，而不是让核心工具把所有图片保存调到“主线程”。

### 5.4 `StreamingSlideGenerator`

- Agent 网络流、XML 合并和渲染调用不得运行在 UI Dispatcher 包裹内。
- `AppendMessagesToSessionAsync` 使用 AgentLib 自身调度，不重复包装。
- `AppendResponseUpdate` 是真实 UI 绑定对象写入边界：仅这一小段需要使用手动上下文的 Dispatcher，并等待提交完成后继续。
- `StartChatting`/`Dispose` 不应通过通用 `RunOnMainThreadAsync` 把状态作用域逻辑和流式循环混在一起；应依据 AgentLib 的状态通知契约单独处理。
- 构造函数中未使用的 `_dispatcher` 必须移除，避免伪造“整个生成器依赖 UI”的错误印象。

### 5.5 Courseware ViewModel

- 所有绑定属性、`ObservableCollection` 和 `PropertyChanged` 的显式提交都必须在 `IViewModelDispatcher` 指定线程执行；ViewModel 从异步路径主动调用命令通知时也遵循该边界。
- 长耗时服务调用、文件 IO、模型调用、MCP 调用和渲染等待必须在 Dispatcher 外。
- Dispatcher 委托应是短小同步提交；不在 Dispatcher 内等待外部异步操作。
- `IViewModelDispatcher` 不需要 `Func<Task>` 重载；它容易把“进入 UI 线程”误解为“整个异步委托生命周期都在 UI 线程”。
- `AsyncRelayCommand` 的生产入口固定为 WPF UI 线程；命令内部保留该同步上下文，使执行计数、开始/结束 `CanExecuteChanged` 和异常观察沿同一命令生命周期完成。命令不接收 `IViewModelDispatcher`，也不使用 `ConfigureAwait(false)` 后再切回 UI。
- fire-and-forget UI 提交必须消除或统一观察异常和生命周期；进度回调需要保持顺序。

### 5.6 `WpfDispatcher`

- 应优先使用 `Application.Current.Dispatcher`。
- 没有 WPF Application 时可以使用专用后台 STA Dispatcher，但其初始化不能通过 `GetAwaiter().GetResult()` 同步等待。
- `InvokeAsync` 应异步等待“Dispatcher 已准备好”；`CheckAccess` 不能为了创建回退 Dispatcher 而阻塞，回退 Dispatcher 尚未就绪时应直接返回 `false`。

### 5.7 普通 `PptxGeneratorWpfDemo` ViewModel

- 命令开始、成功、取消、失败和结束必须属于同一个可等待操作，不允许成功分支与 `catch`/`finally` 使用不同线程策略。
- `MainWindowViewModel` 只负责提交自己拥有的绑定状态；渲染工具、聊天管理器和生成管道分别负责自己的状态，不通过“调用了某个 Dispatcher API”传递线程保证。
- `SlideChatManager.PropertyChanged`、评估完成和迭代完成事件不假设发布线程；ViewModel 转发通知时必须使用统一 UI 提交边界并观察异常。
- 构造初始化、窗口事件和命令不能使用裸 `_ = SomeAsync()`；异步命令应暴露可等待执行任务，后台初始化应有显式所有者。
- `Application.Current.Dispatcher` 和 `WpfDispatcher.Instance` 不能各自形成独立策略；ViewModel 状态提交只依赖一个注入或固定的 UI 调度抽象，异步命令本身不持有 Dispatcher。

## 6. 上一轮初始改动与本轮新增问题审查

### 6.1 `StreamingSlideGenerator.cs`

当前新增逻辑：

- 使用 `RunOnMainThreadAsync` 包装 `StartChatting`；
- 使用同一帮助方法包装 `AppendResponseUpdate`；
- 使用同一帮助方法包装 scope `Dispose`；
- 每次 await 后继续 `ConfigureAwait(false)`。

结论：部分动机正确，抽象方式错误。

- `AppendResponseUpdate` 确实是绑定消息对象的 UI 写入边界，应保留“最小调度并等待”的语义。
- `StartChatting`、`Dispose` 与消息集合写入不是同一类操作，不应被同一个帮助方法统一包装。
- `ConfigureAwait(false)` 不会主动切换线程；问题不是“先切 UI、再切后台”，而是代码把不同线程契约混成一个无差别工具，导致职责不清和多余跳转。
- `_dispatcher` 字段完全未使用，应移除。

### 6.2 `SlideStreamingPipeline.cs`

当前新增逻辑：把 `Rendered` 事件通过 `_dispatcher` 调度到主线程，并新增测试要求核心流水线等待 UI 通知完成。

结论：必须撤销。

原因：

- `SlideStreamingPipeline` 不拥有 UI；
- 真正的 WPF 渲染已经在 `SlideMlRenderPipeline` 内部完成调度；
- `Rendered` 订阅者可能是测试、CLI、Avalonia 或普通业务状态同步；
- 把事件下沉为 UI 线程事件会制造无关等待和跨框架耦合。

### 6.3 `SlideMlRenderTool.cs`

当前变化包含三部分：

1. `ApplyRenderResult` 从内部 fire-and-forget Dispatcher 改为同步直接写；
2. `CreatePreviewDataContentAsync` 增加 Dispatcher 包装 `image.Save`；
3. `RenderSlideAsync` 开始等待 Dispatcher 并复用 `ApplyRenderResult`。

结论：

- 去掉 `ApplyRenderResult` 的 fire-and-forget 是正确方向；原实现存在“方法已返回但 Latest* 仍未更新”的确定性竞态。
- 直接公开同步写方法仍会迫使所有调用方自己判断线程，容易重复调度；应改成可等待的明确提交 API。
- 对所有 `IPreviewImage.Save` 一概调度到 UI 线程过宽；WPF 位图已冻结，文件图片也不需要 UI。应按图片实现契约处理。
- `RenderSlideAsync` 等待结果提交完成是正确的顺序要求。

### 6.4 `SlideGenerationPipeline.cs`

当前变化：把两个原本 fire-and-forget 的属性通知 Dispatcher 改为 `await`。

结论：等待通知完成是正确方向，但仍需进一步简化：

- 属性通知不应由多个路径重复触发；`SlideMlRenderTool.SlideRendered -> SlideGenerationPipeline.OnSlideRendered` 已经是统一通知链。
- 流式结束后再次手工通知四个属性容易重复。
- 核心管道不应依赖“主线程属性通知”这一隐式契约；若保留 UI 可观察对象，应由统一结果提交边界保证顺序。

### 6.5 `CoursewareSlideWorkspaceViewModel.cs`

当前变化：重新渲染路径在调用 `ApplyRenderResult` 前使用 ViewModel Dispatcher。

结论：属于真实 UI 状态提交，但不应成为调用方特例。应调用统一、可等待的渲染结果提交 API，然后在 ViewModel Dispatcher 内只更新页面自身状态。

### 6.6 `SlideStreamingPipelineTests.cs`

新增测试把“Rendered 必须在主线程且流水线必须等待 Dispatcher”固化为契约。

结论：测试方向错误，必须替换为：

- 流式流水线不调用 UI Dispatcher；
- `Rendered` 与渲染操作保持顺序同步；
- UI 订阅者的调度在 UI 适配/ViewModel 测试中验证。

### 6.7 `PptxGeneratorWpfDemo/MainWindowViewModel.cs`

当前实现只把每个操作的成功状态放进 `Application.Current.Dispatcher`，但取消、异常和 `finally` 直接写 UI 状态；`RunRerenderAsync` 还把 `ApplyRenderResultAsync` 的内部提交错误理解为调用方状态也安全。

结论：必须按完整命令生命周期重构，而不是继续逐行增加 Dispatcher。

- 每个命令开始时快照 UI 输入并提交开始状态；
- Dispatcher 外等待长耗时工作；
- 用局部结果表达成功、取消和失败；
- 在一个可等待的结束提交中写 `StatusText`、`IsBusy`、`IsIterating` 等相关状态；
- 事件回调统一通过同一 ViewModel UI 提交边界转发；
- 删除构造函数和窗口事件中的裸异步任务。

### 6.8 后台评估、命令和 MCP 初始化

- `SlideGenerationPipeline` 的自动评估是生成后的独立业务阶段，会写 `IsEvaluating`、`LastSlideEvaluation` 并触发事件；它不应延长 `SendMessageAsync`，但必须由管道持有任务、观察异常并提供可等待的完成入口；
- 共享 `DelegateCommand` 当前既不能等待异步委托，又用未观察 Dispatcher 任务通知 `CanExecuteChanged`，不适合作为异步命令边界；
- Courseware 默认 MCP 初始化是明确允许在 `CreateAsync` 返回后完成的可选增强；活动管道由 `SwitchableSlideMlRenderPipeline` 原子发布，初始化帮助方法负责观察取消和异常，管理器创建不得等待远程 MCP；
- 普通 Demo 构造函数和 `LostFocus` 事件中的 MCP 连接同样必须显式等待或通过有异常观察的事件适配层执行。

## 7. 其他已确认问题

### T01：`WpfDispatcher` 使用异步转同步初始化回退 Dispatcher

文件：`PptxGenerator.Wpf/Threading/WpfDispatcher.cs`

现状：`dispatcherReady.Task.GetAwaiter().GetResult()`。

### T02：`SlideStreamingPipeline` 错误承担 UI 事件调度

目标：移除 `_dispatcher` 依赖和 `RaiseRenderedAsync`，恢复核心事件线程中立。

### T03：`StreamingSlideGenerator` 通用主线程帮助方法混淆三种状态操作

目标：

- 仅为 `AppendResponseUpdate` 建立窄 UI 提交方法；
- 独立处理聊天状态作用域，不把流式循环放进 Dispatcher。

### T04：`SlideMlRenderTool` 结果状态提交 API 缺少清晰异步契约

目标：增加 `ApplyRenderResultAsync` 并保留可等待的 `ResetLatestResultAsync`；任何路径都在方法完成前保证 `Latest*` 和通知已完成，且所有调用方删除自己的结果提交 Dispatcher。

### T05：预览图片保存被过度调度

目标：移除对所有 `IPreviewImage.Save` 的主线程假设；为 WPF 输出保持冻结，为跨框架实现建立可验证的保存契约。

### T06：`SlideGenerationPipeline` 重复或散落属性通知

目标：统一由渲染结果提交完成事件驱动四个渲染属性通知，移除流式/非流式尾部重复通知和不必要 Dispatcher。

### T07：`SlideGenerationPipeline` 评估状态和预览保存线程契约未统一

现状：`IsEvaluating`、`Last*Evaluation` 和事件可能在 `ConfigureAwait(false)` 后的线程写入；`EvaluateContextAsync` 直接调用 `IPreviewImage.Save`。

目标：

- 核心评估操作不依赖 UI；
- 若这些属性继续作为 UI 可观察属性，结果/状态通知必须经过管道持有的 Dispatcher 进行短同步提交；
- 预览序列化复用明确的跨线程安全 API。

### T08：`IViewModelDispatcher.Func<Task>` 允许错误扩大 UI 区域

目标：删除异步委托重载，只允许短同步状态提交。调用模式固定为：先 await 后台工作，再 `InvokeAsync(Action)` 提交状态。

### T09：对 `AsyncRelayCommand` 线程契约的误判

原错误判断：执行计数在调用线程更新、`RaiseCanExecuteChanged` 直接同步触发，因此需要为命令注入 ViewModel Dispatcher。

复核结论：生产环境中的 `ICommand.Execute` 由 WPF UI 线程调用，原实现的普通 `await` 会保留 UI 同步上下文。真正的错误是后来在命令内部加入 `ConfigureAwait(false)`，主动放弃正确上下文，再用 Dispatcher 包装通知和异常回调；这制造了不存在的线程切换需求，并把 `Execute` 错改为 `async void`。

目标：恢复同步 `void Execute` 启动 `ObserveExecutionAsync(ExecuteAsync(...))` 的受控 fire-and-forget 入口；保留 `ExecutionTask` 作为可等待生命周期；命令内部不注入 Dispatcher、不使用 `ConfigureAwait(false)`，异常观察和开始/结束通知自然保持命令入口的 UI 上下文。

### T10：Courseware ViewModel 存在未等待的 UI 提交

位置包括：

- `CoursewareWorkspaceViewModel.CreateAnalysisProgress`；
- `CreateAnalysisMessageProgress`；
- `HandleUnexpectedCommandException`；
- `CoursewareSlideItemViewModel.OnSlideChatManagerPropertyChanged`；
- `CoursewareSlideWorkspaceViewModel.HandleUnexpectedCommandException`。

风险：

- 进度乱序；
- 生命周期结束后迟到提交；
- Dispatcher 操作异常无人观察；
- 测试无法确定完成时状态已提交。

目标：进度使用有序异步队列或由服务 await 回调；异常处理路径显式观察提交任务；迟到更新受会话/取消标识保护。

### 核心库

### 14.4 `AsyncRelayCommand` 错误修复复盘

- 错误根因不是 `AsyncRelayCommand` 或普通 Demo 的 `AsyncDelegateCommand` 缺少 Dispatcher，而是上一轮忽略了 WPF `ICommand.Execute` 已经从 UI 线程进入这一前置契约；
- 在命令内部加入 `ConfigureAwait(false)` 主动丢失同步上下文，再注入 `IViewModelDispatcher` 调度 `CanExecuteChanged` 和 `_onException`，属于先制造线程问题、再用 Dispatcher 掩盖问题；
- 把 `Execute` 改成 `async void` 破坏了原有同步适配入口。正确实现是同步 `void Execute` 启动受控的观察任务，由 `ExecutionTask` 暴露实际执行生命周期，由 `ObserveExecutionAsync` 消费异常；
- `_onException` 不需要 Dispatcher 包装。观察任务使用普通 `await`，会回到命令入口的 UI 同步上下文；若这里出现线程切换，应先检查是谁使用了 `ConfigureAwait(false)` 或从错误线程调用命令，而不是继续增加调度器；
- 测试不能从线程池调用 `ExecuteAsync` 后要求命令自行切回 UI。正确测试是在真实 WPF STA Dispatcher 上进入命令，验证执行续体、`CanExecuteChanged` 和异常观察始终保持该 UI 上下文。
