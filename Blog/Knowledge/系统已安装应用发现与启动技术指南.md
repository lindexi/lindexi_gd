# Windows 已安装应用发现与启动技术指南

## 1. 文档目标

本文说明如何在 .NET 桌面程序中完成以下能力：

1. 发现当前 Windows 系统中可由用户启动的应用；
2. 将传统桌面应用、应用包和系统 Shell 入口统一建模；
3. 解析快捷方式、资源化名称和应用入口；
4. 合并多来源数据并处理重名、失效项和本地化名称；
5. 根据用户输入定位应用并启动；
6. 通过缓存、权限隔离、错误处理和安全策略提高可用性。

“已安装应用”并不存在一个覆盖所有 Windows 应用形态的单一权威接口。可靠方案必须组合多个数据源，并把“用于展示的信息”“用于启动的入口”和“实际运行进程”分开处理。

---

## 2. 先明确三个不同问题

### 2.1 应用是否已安装

安装状态通常来自安装包数据库、注册表卸载项、应用包目录或厂商自定义配置。但“已安装”不等于“用户可以直接启动”。驱动、运行库、更新组件、卸载器和后台服务也可能具有安装记录。

### 2.2 应用是否适合展示

面向用户的应用列表应尽量接近开始菜单中的可启动入口。快捷方式已经由系统或安装程序完成筛选，通常比扫描磁盘或读取卸载注册表更符合用户认知。

### 2.3 应用应该如何启动

不同应用需要不同入口：

- 传统桌面应用可以通过 `.lnk` 快捷方式或 `.exe` 启动；
- 应用包通常通过应用用户模型标识对应的 Shell 地址启动；
- 系统虚拟目录通过 `shell:` URI 启动；
- 系统设置页面通过协议 URI 启动，例如 `ms-settings:`；
- 某些入口是启动器，实际业务进程与启动器并不是同一个文件。

因此，数据模型不能只保存一个“可执行文件路径”。

## 3. 统一数据模型

推荐使用不可变记录承载应用信息：

```csharp
internal sealed record ApplicationInfo
{
    public required ApplicationType Type { get; init; }

    public required string Name { get; init; }

    public required string EntryPath { get; init; }

    public string? ExecutablePath { get; init; }

    public string? RootDirectory { get; init; }

    public string? ActualExecutablePath { get; init; }

    public required DateTimeOffset LastModified { get; init; }
}

internal enum ApplicationType
{
    Win32Desktop,
    PackagedApplication,
    WindowsShell
}
```

各字段职责如下：

| 字段 | 含义 | 典型值 |
|---|---|---|
| `Type` | 应用入口类型 | 传统桌面、应用包、Shell |
| `Name` | 展示和搜索使用的名称 | “计算器” |
| `EntryPath` | 交给系统 Shell 的启动入口 | `.lnk`、`shell:AppsFolder\...`、`ms-settings:` |
| `ExecutablePath` | 可确认时保存的启动程序路径 | `C:\...\app.exe` |
| `RootDirectory` | 应用文件所属根目录 | 安装目录或包工作目录 |
| `ActualExecutablePath` | 启动器拉起的实际进程路径 | `C:\...\main.exe` |
| `LastModified` | 数据新旧比较依据 | 快捷方式或安装目录的修改时间 |

### 3.1 为什么必须保留 `EntryPath`

启动时优先使用 `EntryPath`，因为它保留了安装程序配置的工作目录、命令行参数、协议处理和系统 Shell 行为。直接启动 `ExecutablePath` 可能丢失快捷方式参数，也可能绕过应用包的激活机制。

### 3.2 为什么区分启动进程和实际进程

一些桌面应用先运行轻量启动器，再创建真正的主进程。若后续需要判断应用是否运行、定位窗口或关闭应用，仅记录启动器路径会导致匹配失败。`ActualExecutablePath` 用于补充这一关联，不应替代 `EntryPath`。

## 4. Windows 应用发现的总体流程

推荐按以下顺序执行：

1. 扫描公共开始菜单和当前用户开始菜单；
2. 添加无法稳定从菜单中发现的系统 Shell 入口；
3. 在受支持的系统版本上枚举应用包；
4. 为已发现应用补充本地化别名；
5. 从可选配置源补充实际进程路径等增强信息；
6. 将有效项和无效项分开保存；
7. 按确定性的覆盖规则处理同名项。

参考流程可表示为：

```text
公共开始菜单 ─┐
当前用户菜单 ─┼─> 快捷方式解析 ─┐
系统入口清单 ─┤                 │
应用包枚举 ───┘                 ├─> 去重与覆盖 ─> 本地化别名 ─> 信息补充 ─> 最终列表
                                │
无效或可疑入口 ──────────────────┘（单独记录，不向用户暴露）
```

## 5. 从开始菜单发现传统桌面应用

### 5.1 扫描范围

使用以下特殊目录，不要硬编码用户目录：

```csharp
var commonStartMenu = Environment.GetFolderPath(
    Environment.SpecialFolder.CommonStartMenu);

var userStartMenu = Environment.GetFolderPath(
    Environment.SpecialFolder.StartMenu);
```

两者分别覆盖所有用户共享的开始菜单和当前用户的开始菜单。应用快捷方式可能位于任意层级，因此需要递归查找 `*.lnk`。

### 5.2 安全递归遍历

目录遍历应满足以下要求：

- 先检查目录是否存在；
- 跳过重解析点，避免符号链接形成循环或越过预期目录；
- 单个文件或目录无权限时只跳过该项；
- 不因一个损坏快捷方式中止整个发现过程；
- 对异常做结构化记录，包含文件路径和失败阶段。

示例：

```csharp
internal static IEnumerable<FileInfo> EnumerateFilesSafely(
    DirectoryInfo directory,
    string searchPattern)
{
    IEnumerable<FileInfo> files;
    IEnumerable<DirectoryInfo> directories;

    try
    {
        files = directory.EnumerateFiles(searchPattern, SearchOption.TopDirectoryOnly);
        directories = directory.EnumerateDirectories("*", SearchOption.TopDirectoryOnly);
    }
    catch (UnauthorizedAccessException)
    {
        yield break;
    }
    catch (DirectoryNotFoundException)
    {
        yield break;
    }

    foreach (var file in files)
    {
        yield return file;
    }

    foreach (var child in directories)
    {
        if ((child.Attributes & FileAttributes.ReparsePoint) != 0)
        {
            continue;
        }

        foreach (var file in EnumerateFilesSafely(child, searchPattern))
        {
            yield return file;
        }
    }
}
```

生产实现还应把延迟枚举期间抛出的异常纳入保护范围，因为 `EnumerateFiles` 返回后，异常仍可能在迭代时发生。

### 5.3 解析 `.lnk` 目标

`.lnk` 不是普通文本文件，应使用 Windows Shell COM 接口：

1. 创建 `ShellLink` COM 对象；
2. 取得 `IPersistFile`；
3. 调用 `Load` 加载快捷方式；
4. 通过 `IShellLinkW.GetPath` 获取目标路径；
5. 完成后释放 COM 接口指针。

核心接口标识是系统公开约定：

- Shell Link 类：`00021401-0000-0000-C000-000000000046`；
- `IShellLinkW`：读取 Unicode 路径；
- `IPersistFile`：加载快捷方式文件。

解析时应优先使用 Unicode 接口，并准备长度足够的缓冲区。传统的 `MAX_PATH` 缓冲区无法覆盖所有长路径场景，改进实现可先尝试较大的缓冲区，并记录路径被截断的风险。

### 5.4 快捷方式有效性过滤

开始菜单中并非所有快捷方式都适合作为应用入口。建议执行以下检查：

1. 目标路径为空时，不立即判定无效。部分系统入口无法解析出普通文件路径，但快捷方式本身仍能由 Shell 启动；
2. 目标存在扩展名；
3. 扩展名属于允许范围，例如 `.exe` 和 `.msc`；
4. 目标文件存在；
5. 文件名不是常见卸载器名称；
6. 高风险脚本类型默认不纳入自动启动范围。

`.bat`、`.cmd`、`.com`、`.ps1` 等入口会扩大命令执行面，除非业务明确需要并具备可信来源校验，否则不应默认加入。

### 5.5 快捷方式名称与启动入口

名称使用快捷方式文件名去掉扩展名后的结果；启动入口保存快捷方式完整路径，而不是解析后的目标路径：

```csharp
var info = new ApplicationInfo
{
    Type = ApplicationType.Win32Desktop,
    Name = Path.GetFileNameWithoutExtension(link.Name),
    EntryPath = link.FullName,
    ExecutablePath = resolvedTargetPath,
    LastModified = link.LastWriteTimeUtc
};
```

这种设计兼顾了稳定启动和进程识别。

## 6. 发现应用包

### 6.1 数据来源

Windows 10 及以上系统可以通过系统 API 枚举应用容器。可获取的信息通常包括：

- 应用容器名称；
- 显示名称；
- 描述；
- 包完整名称；
- 工作目录；
- 能力与二进制信息。

参考实现使用网络隔离相关的系统接口枚举应用容器。该方式无需依赖 WinRT 投影，适合对裁剪或原生发布有约束的 .NET 程序，但需要正确处理非托管内存和结构体布局。

### 6.2 过滤规则

枚举结果应至少满足：

- 显示名称非空；
- 包完整名称非空；
- 应用标识不在禁用清单中；
- 资源化显示名称可以成功解析；
- 工作目录合理存在，或至少保留可诊断信息。

某些容器属于系统内部组件，不应展示。禁用清单应使用稳定标识，而不是依赖可能本地化的显示名称。

### 6.3 构造启动入口

应用包入口通常采用：

```text
shell:AppsFolder\<ApplicationUserModelId>!App
```

然后交给 Windows Shell 激活。不要尝试直接运行包目录中的可执行文件，因为这可能绕过包身份、激活参数和运行时约束。

### 6.4 解析资源化字符串

应用包的显示名称可能是普通字符串，也可能是以 `@` 开头的间接资源引用。可调用 `SHLoadIndirectString` 将其解析为当前系统语言下的文本。

处理原则：

1. 普通字符串直接使用；
2. 形似包标识而非自然语言的字符串不作为展示名称；
3. 间接资源加载失败且结果仍以 `@` 开头时，视为不可展示；
4. 不可展示项进入诊断列表，不进入用户可见列表。

### 6.5 安装时间的近似值

应用容器接口未必直接返回安装时间。可以取以下时间的较大值作为近似依据：

- 工作目录最后修改时间；
- 工作目录顶层可执行文件的最新修改时间。

该值只能用于同名条目的新旧比较，不能作为审计意义上的精确安装时间。

### 6.6 非托管资源释放

调用返回非托管数组的系统接口时，必须使用与接口匹配的释放函数。仅释放托管固定句柄并不能释放系统分配的数组。正确实现应在 `try/finally` 中释放系统返回的内存，并检查 API 返回码；否则重复刷新可能造成持续的非托管内存泄漏。

## 7. 补充系统 Shell 入口

开始菜单和应用包枚举仍可能漏掉常见系统功能，例如：

- 此电脑；
- 回收站；
- 网络位置；
- 控制面板；
- 系统设置。

这类入口可以维护一个很小的系统清单：

```text
shell:MyComputerFolder
shell:RecycleBinFolder
shell:NetworkPlacesFolder
shell:ControlPanelFolder
ms-settings:
```

清单的特点是：

- 只包含 Windows 稳定公开的 Shell 名称或协议；
- 明确标记入口类型；
- 优先级高于扫描结果，避免被名称相同但语义不同的快捷方式覆盖；
- 不把厂商专属应用硬编码进通用发现层。

业务扩展应用如确需补充，应通过独立配置源注入，避免污染系统发现逻辑。

## 8. 注册表应该承担什么角色

### 8.1 不建议把卸载注册表作为唯一来源

常见卸载项路径可以提供显示名称、安装位置和卸载命令，但存在以下问题：

- 包含运行库、补丁、驱动和卸载组件；
- 安装位置可能为空或不准确；
- 不一定包含可启动入口；
- 32 位和 64 位视图不同；
- 当前用户安装与全局安装分散在不同配置单元。

如果目标是构建“软件资产清单”，卸载项很重要；如果目标是构建“用户可启动应用列表”，开始菜单和应用包入口更合适。

### 8.2 适合作为补充信息源

注册表或其他受控配置源可用于建立以下映射：

```text
启动器路径 -> 实际业务进程路径
```

为提高查找效率，可先从应用列表构建忽略大小写的反向索引：

```csharp
var lookup = new Dictionary<string, List<string>>(
    StringComparer.OrdinalIgnoreCase);
```

同一个启动器可能对应多个展示名称，因此索引值应是名称集合，而不是单个名称。

### 8.3 同时读取 32 位和 64 位视图

在 64 位系统上，应显式遍历：

```csharp
RegistryView.Registry32
RegistryView.Registry64
```

每个注册表项单独捕获异常。单个损坏值不应影响其他应用的信息补充。

### 8.4 对外发布时的配置隔离

通用实现不应写死组织、厂商或产品专属注册表路径。推荐通过配置注入允许读取的路径，并设置白名单：

```json
{
  "ApplicationDiscovery": {
    "SupplementaryRegistryPaths": [
      {
        "Hive": "LocalMachine",
        "Path": "SOFTWARE\\ApplicationDiscovery"
      }
    ]
  }
}
```

实际部署时替换示例路径即可。读取逻辑应保持通用。

## 9. 多来源合并与去重

### 9.1 使用名称作为索引的优缺点

以显示名称作为字典键便于列出和搜索，但同名应用会冲突。至少应使用确定性的覆盖规则，避免结果随文件枚举顺序变化。

可采用以下优先级：

1. 明确维护的系统 Shell 入口；
2. 应用包入口；
3. 开始菜单快捷方式；
4. 其他补充来源。

同一来源出现同名项时，可以使用 `LastModified` 较新的记录覆盖旧记录。

### 9.2 更稳健的生产模型

如果业务需要完整保留同名应用，建议内部使用稳定标识作为主键：

- 快捷方式：规范化后的快捷方式完整路径；
- 应用包：应用用户模型标识；
- Shell：协议或 Shell URI；
- 显示名称仅作为索引，映射到一个或多个应用。

```csharp
IReadOnlyDictionary<ApplicationId, ApplicationInfo> applications;
IReadOnlyDictionary<string, IReadOnlyList<ApplicationId>> nameIndex;
```

这样可以在用户输入存在多个候选时要求进一步选择，而不是静默覆盖。

### 9.3 有效项与无效项分离

无效项不应直接丢弃。维护独立诊断集合有助于定位：

- 快捷方式目标不存在；
- 扩展名不受支持；
- 资源化名称无法解析；
- 包工作目录异常；
- 权限不足；
- COM 或系统 API 调用失败。

诊断信息应写入受保护日志，不应将本机完整路径无条件暴露给远程调用方或普通用户。

## 10. 本地化名称与别名

系统返回的应用名可能是英文、当前语言文本或资源标识。为改善搜索体验，可以为已确认的应用增加本地化别名。

推荐规则：

1. 仅当原始应用确实存在时添加别名；
2. 别名指向同一启动入口，不复制发现流程；
3. 若别名与现有应用同名，不覆盖现有真实入口；
4. 资源文件按类别维护，避免把用户可见文本写死在代码中；
5. 别名集合应支持多语言，但内部稳定标识不随语言变化。

如果使用“名称为键”的简单模型，别名可以复制一份记录并替换 `Name`。更完善的模型则应把多个名称挂到同一个应用标识上。

## 11. 缓存与后台预热

扫描开始菜单、调用 COM 和枚举应用容器都可能产生明显延迟，不适合每次查询都同步执行。

### 11.1 推荐缓存策略

- 应用管理器使用单例生命周期；
- 构造后启动一次后台加载；
- 首次请求若尚未完成，则等待同一个加载任务；
- 后续请求立即返回已有快照；
- 超过刷新间隔后触发后台更新；
- 更新期间继续提供旧快照，避免查询阻塞；
- 新快照完整构建后再原子替换。

参考刷新间隔可设为 5 分钟。若需要更及时，可监听开始菜单目录变化和应用安装事件，再用定时刷新作为兜底。

### 11.2 避免并发重复刷新

异步延迟初始化应保证多个调用方共享同一个任务。使用 `Interlocked.CompareExchange` 可以避免锁竞争：

```csharp
var task = valueFactory().AsTask();
var existing = Interlocked.CompareExchange(ref instanceTask, task, null);
return existing is null ? await task : await existing;
```

刷新时不要直接把缓存替换为一个尚未成功完成的新任务，否则刷新失败可能导致原有有效快照不可用。更稳健的方式是：

1. 保留当前快照；
2. 独立创建刷新任务；
3. 刷新成功后替换快照；
4. 刷新失败时记录错误并继续使用旧数据；
5. 使用互斥标记确保同一时刻只有一个刷新任务。

### 11.3 把阻塞工作移出请求线程

目录扫描和 COM 调用属于同步阻塞操作，可以放入后台任务执行。异步 API 应接受 `CancellationToken`；但若底层系统调用不可取消，需要明确取消只影响等待方，不能假装底层扫描已停止。

## 12. 应用名称匹配

启动前必须把用户输入映射到唯一应用。

### 12.1 匹配顺序

推荐顺序如下：

1. 使用适合用户体验的比较器进行精确匹配；
2. 检查本地化别名和业务别名；
3. 执行模糊匹配；
4. 多个候选接近时返回候选列表，不自动猜测；
5. 无可靠候选时明确返回未找到。

### 12.2 模糊匹配

可使用加权相似度算法对名称评分，并设置最低阈值。例如：

- 最低接受分数：75；
- 最多保留前 5 个候选；
- 比较前统一大小写；
- 对常见卸载器名称降权或排除。

中文名称使用英文分词型算法通常收益有限。可先做以下规范化：

- 去除首尾空白；
- 统一全角和半角字符；
- 统一大小写；
- 规范括号、书名号和连接符；
- 对常见简称建立显式别名。

安全上不应只因“分数最高”就启动。若第一名与第二名分差很小，应要求用户确认。

## 13. 启动应用

### 13.1 统一交给系统 Shell

对 `.lnk`、`shell:` URI、协议 URI 和应用包入口，使用：

```csharp
private static void Launch(ApplicationInfo application)
{
    ArgumentNullException.ThrowIfNull(application);

    var process = Process.Start(new ProcessStartInfo(application.EntryPath)
    {
        UseShellExecute = true
    });

    if (process is null)
    {
        throw new InvalidOperationException(
            $"系统未能启动应用入口：{application.Name}");
    }
}
```

`UseShellExecute = true` 是关键，它允许系统根据入口类型选择处理器。若设置为 `false`，协议 URI、Shell 地址和快捷方式不一定能按预期工作。

### 13.2 为什么不等待应用窗口出现

`Process.Start` 成功只表示启动请求已提交，不表示：

- 主窗口已经创建；
- 应用初始化完成；
- 启动器已创建实际业务进程；
- 应用没有复用现有进程；
- 用户已经看到前台窗口。

因此，启动 API 应返回“启动请求已成功提交”，不要声称应用已完全就绪。如果业务需要等待窗口，应另行实现带超时和取消的窗口检测流程。

### 13.3 前台激活限制

Windows 会限制后台进程把其他窗口强行切到前台。某些交互式程序会在启动前发送一次无副作用的合成输入，以满足系统前台切换条件，然后立刻发起启动。

该方式必须谨慎使用：

- 仅用于明确的用户交互触发；
- 不在后台定时任务中滥用；
- 不使用会改变用户输入状态的按键；
- 不能保证所有 Windows 版本和安全策略下都有效；
- 应允许启动成功但未前置，而不是把未前置误判为启动失败。

更推荐让用户显式触发启动，并尊重系统前台窗口策略。

### 13.4 从高权限进程启动普通权限应用

如果宿主进程以管理员身份运行，直接启动子进程可能让目标应用继承高权限。这不符合最小权限原则，也可能造成拖放、窗口消息和文件虚拟化行为异常。

可采用以下策略：

1. 普通权限宿主直接使用 Shell 启动；
2. 高权限宿主取得桌面 Shell 进程；
3. 打开 Shell 进程令牌；
4. 复制主令牌；
5. 使用复制后的令牌创建子进程；
6. 关闭进程句柄、线程句柄和令牌句柄。

该流程适用于直接执行文件。对于 Shell URI 和快捷方式，更理想的架构是由一个普通权限代理进程负责启动，避免在高权限进程中复制令牌并自行处理复杂的 Shell 激活。

### 13.5 32 位进程访问系统目录

32 位进程运行在 64 位 Windows 上时，`System32` 可能被重定向到 `SysWOW64`。若必须启动真正的 64 位系统工具，可以使用 `Sysnative` 虚拟目录访问原生系统目录。该逻辑应只用于已知系统工具，不要用于拼接任意用户输入。

## 14. Linux 的对应设计

如果需要跨平台，Linux 通常通过桌面入口文件发现应用：

- `/usr/share/applications/*.desktop`；
- `/usr/local/share/applications/*.desktop`；
- `~/.local/share/applications/*.desktop`；
- `$XDG_DATA_DIRS` 和 `$XDG_DATA_HOME` 指定的目录。

需要解析的关键字段包括：

- `Name` 与本地化的 `Name[语言]`；
- `Exec`；
- `TryExec`；
- `Hidden`；
- `NoDisplay`；
- `OnlyShowIn` 与 `NotShowIn`；
- `Terminal`；
- `Type=Application`。

启动时优先使用桌面环境提供的启动方式，例如 `gio launch` 或 `gtk-launch`，而不是简单把 `Exec` 字段交给 `/bin/sh`。`Exec` 包含 `%f`、`%F`、`%u`、`%U`、`%i`、`%c`、`%k` 等字段代码，必须按 Desktop Entry Specification 解析。

不得把未经验证的路径和参数拼进 `sh -c`。如果必须直接启动，使用 `ProcessStartInfo.ArgumentList` 分离参数，避免命令注入。

## 15. 安全设计

### 15.1 不接受任意入口路径

对外 API 应接受应用标识或名称，再从已发现的可信快照中取得 `EntryPath`。不要允许调用方直接提交文件路径、协议字符串或命令行。

### 15.2 建立允许与拒绝策略

默认拒绝以下入口：

- 卸载器；
- 命令解释器和脚本宿主；
- 注册表编辑器等高风险系统工具，除非业务明确允许；
- 目标文件已经不存在的快捷方式；
- 位于临时目录、下载目录或网络共享中的可疑入口；
- 需要提升权限的入口。

策略应基于稳定标识和规范化路径，不能只比较展示名称。

### 15.3 路径规范化

比较路径前应：

1. 转换为完整路径；
2. 统一目录分隔符；
3. 使用 `StringComparer.OrdinalIgnoreCase`；
4. 检查文件是否存在；
5. 必要时解析最终文件路径，防止重解析点绕过目录限制；
6. 不通过字符串前缀简单判断目录归属，应使用带边界的路径比较。

例如，`C:\Program Files2` 不能被误判为位于 `C:\Program Files` 下。

### 15.4 日志和隐私

本机用户名、安装路径和应用清单可能属于敏感设备信息。日志应：

- 默认不导出完整应用清单；
- 调试导出必须显式启用；
- 对用户目录做脱敏；
- 限制日志目录访问权限；
- 设置保留周期；
- 不将完整异常和本机路径直接返回给远程调用方。

## 16. 错误处理与可观测性

### 16.1 发现阶段

发现是“尽力而为”的聚合流程。单项失败应记录并继续，整体失败才抛出异常。建议记录以下指标：

- 各来源发现的条目数；
- 有效项与无效项数量；
- 快捷方式解析失败数量；
- 应用包资源解析失败数量；
- 完整扫描耗时；
- 缓存刷新成功或失败次数；
- 当前快照生成时间。

### 16.2 启动阶段

启动是明确的用户操作，失败应向上抛出精确异常，并保留内部原因。可区分：

- 应用不存在或已从缓存中失效；
- 入口格式不受支持；
- 文件不存在；
- 权限不足；
- Shell 未注册对应协议；
- 系统拒绝创建进程。

不要捕获所有异常后只返回布尔值，否则调用方无法区分输入错误、环境错误和系统错误。

## 17. 建议的服务边界

可以将职责拆分为以下组件：

```text
ApplicationCatalog
├── StartMenuApplicationSource
├── PackagedApplicationSource
├── ShellApplicationSource
├── ApplicationMetadataEnricher
├── ApplicationMerger
└── ApplicationCache

ApplicationResolver
└── 精确匹配、别名匹配、模糊匹配、歧义处理

ApplicationLauncher
└── Shell 启动、权限隔离、结果报告
```

不要为了形式而给每个类增加接口。只有需要替换外部系统依赖或进行隔离测试的边界才值得抽象，例如文件系统、注册表、系统 API 和进程启动器。

## 18. 测试策略

### 18.1 单元测试

重点验证纯逻辑：

- 同名项按来源优先级合并；
- 同来源选择较新的记录；
- 卸载器名称被过滤；
- 路径比较忽略大小写但保留目录边界；
- 本地化别名不覆盖真实入口；
- 模糊匹配低于阈值时返回未找到；
- 两个高分候选接近时返回歧义；
- 实际进程路径补充到所有共享启动器的应用。

### 18.2 Windows 集成测试

在隔离环境中验证：

- 创建临时开始菜单结构并解析快捷方式；
- 损坏快捷方式不会中断扫描；
- 无权限目录被跳过；
- 应用包入口可以由 Shell 接受；
- `shell:` 和协议 URI 可以启动；
- 高权限宿主启动的目标进程保持普通完整性级别；
- 刷新失败时旧快照仍可用。

涉及真实系统应用的测试容易随系统版本和语言变化，不应作为严格的单元测试断言。可将其设计为显式运行的环境验证测试。

### 18.3 性能测试

至少记录：

- 冷启动首次扫描耗时；
- 缓存命中耗时；
- 开始菜单包含大量快捷方式时的扫描耗时；
- 连续刷新后的托管内存和非托管内存变化；
- 多调用方并发读取时是否触发重复扫描。

## 19. 推荐实现步骤

1. 定义区分入口、可执行文件和实际进程的数据模型；
2. 实现开始菜单安全遍历与快捷方式解析；
3. 添加严格的入口过滤策略；
4. 实现应用包枚举和资源化名称解析；
5. 添加少量稳定的系统 Shell 入口；
6. 定义确定性的合并优先级，并保留无效项诊断；
7. 添加本地化名称和显式别名索引；
8. 实现可保留旧快照的后台缓存刷新；
9. 实现名称解析和歧义处理；
10. 统一通过系统 Shell 启动可信入口；
11. 对高权限场景增加普通权限代理或令牌隔离；
12. 增加安全策略、结构化日志、指标和平台集成测试。

## 20. 关键结论

- 构建可启动应用列表时，开始菜单比卸载注册表更接近用户认知；
- Windows 应用包需要通过应用标识和 Shell 激活，不能简单扫描 `.exe`；
- 系统虚拟目录和设置页面属于 Shell 或协议入口，不一定存在普通可执行路径；
- 启动入口、启动器路径、应用根目录和实际进程路径必须分开建模；
- 多来源数据必须有确定性的优先级和重名处理策略；
- 扫描结果应缓存并后台刷新，刷新失败时保留旧快照；
- 启动时使用 `UseShellExecute = true`，并把结果表述为“启动请求已提交”；
- 高权限宿主不应让普通应用无意继承管理员权限；
- 对外只接受已发现应用的稳定标识，不接受任意路径或命令；
- 非托管枚举接口必须正确释放系统分配的内存，避免周期刷新造成泄漏。
