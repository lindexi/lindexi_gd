# Markdown 着色性能调查与自动化探测方案

## 当前结论的边界

已新增应用侧 `SimpleWrite.Tests` 项目并加入解决方案，通过公开 API 测量真实编辑器与 Markdown 高亮器。初次测量未修改生产代码，Release 测试通过 34 项，耗时 4 分 10 秒。随后按用户确认的最小方案，仅修改 `MarkdownDocumentHighlighter` 创建设置器时的初始化，为已有 `PlainText` 属性传入本轮 `markdownText`，不修改 `TextRunPropertySetter` 内部。

## 第二阶段优化：坐标映射与不重叠链接样式

用户要求进一步优化后，本次修改设置器内部：`PlainText` 初始化时为固定文本构建 UTF-16 到文档字符偏移的数组，区间转换直接查表；保持 CRLF 折叠、代理对（含中间索引）的现有语义，未提供文本的路径仍调用原转换器。每轮 20 万字符的映射约占 0.8 MB，不跨文本版本缓存。

Markdown 段落生成互不重叠的普通文本/链接区间，避免先对整段设置普通样式，再恢复链接样式。删除链接后原区间仍由普通样式覆盖。最终样式规则未改变。

探索中单独拆分样式区间没有耗时收益（输入着色约 822 ms），单独坐标映射也未出现稳定整体收益（一次测量约 1254 ms）。组合后独立 Release 测试得到：

- 每字着色中位数：800.83 → 181.62 ms；输入总耗时：810.63 → 198.35 ms。
- 每字着色分配：111.49 → 43.76 MB；总分配：112.81 → 45.07 MB。
- 三次打开合计：1497.98、966.24、2070.64 ms；首次着色：966.00、609.17、1554.10 ms。打开性能没有稳定改善，分配约 270 MB，较原约 247 MB 上升，区间数量增加存在成本。
- 原始报告：`Markdown-1000Lines-200Chars-a038104ce96f485b8f0c915281e0f2cf.json`。

以上不是受控 CPU 采样，运行中机器状态有波动，不能用比值作为严格保证。保留组合实现以改善输入，尚未达到流畅输入或打开性能目标，后续需阶段诊断样式区间遍历与布局，避免继续猜测热点。

验证：高亮库全部 372 项测试通过；应用侧 Release 全部 167 项通过（含新增 LF/CRLF、代理对前缀下的链接删除与尾部普通文本样式检查）。性能测试的数据规模与输入序列未调整。下文保留此前各阶段结果用于对比。

## 1000 行长文档：打开与中间输入

新增 `SimpleWrite.Tests/LargeMarkdownPerformanceTests.cs`，自动生成 1000 个物理行，每行恰好 200 个 UTF-16 字符（不含 LF），全文 200999 字符，以中文为主。每 20 行一个二级标题，正文包含加粗、强调、Markdown 链接，没有代码块。连续非空正文行在 Markdown 中可属于同一段落，不等同于 1000 个 Markdown 段落。

在新编辑器中装入文档并完成首次高亮，重复 3 次；在第三个编辑器的第 501 行正文开头，逐字输入“这里开始连续输入测试文字”（12 个字符），每次编辑后提取全文并应用高亮，最后检查文本完整性。每个阶段独立计时，报告写入测试输出目录的 `PerformanceResults/Markdown-1000Lines-200Chars-*.json`。

独立运行该用例的 Release 结果（.NET 9.0.19、Windows X64、无调试器）：

| 打开轮次 | 创建编辑器与高亮器 | 装入文本 | 取全文 | 首次高亮 | 合计 | 托管分配 |
|---|---:|---:|---:|---:|---:|---:|
| 第一次 | 28.41 ms | 528.63 ms | 13.07 ms | 1146.77 ms | 1716.88 ms | 247.58 MB |
| 第二次 | 0.07 ms | 354.60 ms | 10.85 ms | 945.23 ms | 1310.76 ms | 247.14 MB |
| 第三次 | 0.06 ms | 324.22 ms | 9.34 ms | 933.65 ms | 1267.27 ms | 247.14 MB |

输入阶段的单字耗时中位数：编辑 0.073 ms、取全文 10.16 ms、着色 800.83 ms、合计 810.63 ms；合计最大值 857.23 ms。平均每字托管分配 112.81 MB，其中高亮阶段 111.49 MB。MB 为十进制累计分配，不是存活内存。

报告：`Markdown-1000Lines-200Chars-eff91e68d12841cf91032ea2e00a1fe8.json`。随后完整 Release 测试集 163 项通过，耗时约 31 秒。完整运行会另写报告，其他用例可能预热运行时，不能将其中第一次打开当作进程冷启动。

边界：这里“打开”是内存文本创建编辑器、装入和首次着色，不含文件 I/O、应用启动、Dispatcher 排队或完整布局绘制；三次打开分别保留结果，不据此计算可靠 P95。测试文档包含加粗语法，但不表示现有高亮器已经对所有 inline 语法提供视觉样式；本用例验证文本完整性并测量当前实现。12 个输入样本的 P95 等于最大值，只作探索。结论是约 20 万字符、无代码块场景仍存在明显同步高亮开销，不能将问题仅归因于代码语言分析。

## 非 C# 场景扩展

性能矩阵已扩展为 10 种内容：Plain、Headings、Lists（包含嵌套列表与引用）、Links、CSharp、Json、Xml、JavaScript、Python、Unknown。保留原有 Links/CSharp 文本不变，增加 128 个场景，共 160 个性能场景，加上 2 个样式检查，Release 下 162 项全部通过，运行器报告耗时 17 秒。

## 首轮性能实测

环境：Windows 10.0.26200、X64、.NET 9.0.19、Release、未附加调试器。每轮执行真实单字符插入，再提取全文并高亮；不包含 Dispatcher 排队、完整布局和屏幕绘制。报告中的块数指生成器重复单元数，每单元包含段落、标题及链接段落或一个短 C# 代码块。

以下为完整运行的结果，MB 使用十进制，分配是每轮当前线程托管累计分配，不是存活内存或进程工作集：

| 场景 | UTF-16 长度 | 位置 | 着色中位数 | 每轮着色平均分配 |
|---|---:|---|---:|---:|
| 100 个 C# 代码块 | 10890 | 文首 | 7286.31 ms | 616.44 MB |
| 100 个 C# 代码块 | 10890 | 文中 | 5320.94 ms | 302.43 MB |
| 100 个 C# 代码块 | 10890 | 文尾 | 16.63 ms | 1.76 MB |
| 100 个链接单元，无代码块 | 10090 | 文首 | 6067.36 ms | 473.00 MB |

同规模 C# 文档关闭高亮、文首输入时，编辑与取文本合计中位数为 8.13 ms。开启高亮的文首场景中，编辑本身中位数为 0.11 ms，取文本为 5.81 ms。对照存在不同样式状态，不应将差值精确解释为某个内部方法的开销。

结论：已复现严重的、与编辑位置相关的同步高亮开销；无 C# 代码块时同样存在，不能只归因于 Roslyn。重复全文提取、坐标扫描、快照失效及样式应用仍需阶段测量或受控优化对照，现有报告不是调用栈采样。

## 已确认的调用路径与风险

1. `SimpleWrite/Business/TextEditors/SimpleWriteTextEditor.cs` 中，`TextChanged` 请求调度 `ApplyHighlight`，后者取 `Text` 并调用高亮器，然后 `InvalidateVisual`。
2. `AvaloniaTextEditorDispatcherRequiring` 使用 UI Dispatcher。`Background` 是队列优先级，不是后台线程；可以合并尚未执行的请求，但一次开始后的同步着色仍阻塞 UI。
3. `MarkdownDocumentHighlighter.ApplyHighlight` 每轮执行全文 `Markdown.Parse`，遍历所有顶层块，重新构造快照、段落子串、URL 信息及代码块字符串。已有快照只跳过应用阶段，并不是增量解析。
4. Markdown 创建 `TextRunPropertySetter` 时未提供 `PlainText`。每次 SourceSpan 的起止位置转换都会回退到编辑器提取全文，再执行 UTF-16 到文档坐标的转换。`TextIndexConverter` 从文本起点枚举 Rune；多样式区间下存在反复提取与扫描的放大效应。
5. 快照按列表位置比对，且比较绝对 SourceSpan。在文首插入字符后，后续块偏移变化，会导致大量快照失效；未改内容的代码块也可能重新着色。应优先比较文首和文尾输入的差异。
6. `TextRunPropertySetter` 还会遍历区间现有属性，必要时设置样式。样式修改触发的布局及后续绘制需要单独测量，不能由解析耗时推断。
7. Debug 下部分样式设置有额外的取文本检查。正式性能基线应使用 Release、无调试器环境；不能把 Debug 数字当作发布版数字。

以上是可从源码确认的工作量，不是已通过采样证实的热点排名。

## 无外部性能工具的测试方案

推荐使用已有 xUnit 技术栈和 .NET 内置 `Stopwatch`、`GC.GetAllocatedBytesForCurrentThread`。在应用目录的独立测试项目中通过公开 API 测试真实 `TextEditor` 和 `MarkdownDocumentHighlighter`，不修改库可见性、不 mock 高亮器、不增加性能测试框架。

### 第一层：同步高亮性能测试

- 初始化文档与真实高亮器，先完成初始着色。
- 每个样本执行一次真实插入或删除，再对编辑后的文本调用高亮器。仅重复对同一文本高亮会过度命中缓存，不能代表输入。
- 分别记录编辑操作、提取文本、`ApplyHighlight` 的耗时与分配；另外记录整体耗时。准备数据、校验结果和输出报告不放入计时区间。
- 设置无高亮的编辑对照；比较实际工作量，不把两组耗时差严格当作内部阶段耗时。
- 单独测试同文重复着色，用于观察快照命中后的固定开销。
- 先在独立实例预热，再用新实例运行相同操作序列；冷启动另测。每场景至少收集几十个样本，报告中位数、P95、最大值和每次分配字节。
- 当前线程分配计数只适用于不跨线程、不 await 的同步区间，不代表原生内存或进程总内存。

建议参数矩阵：

| 维度 | 样本 |
|---|---|
| 文档规模 | 小、中、大三个固定规模，同时输出 UTF-16 长度、段落数、代码块数 |
| 内容 | 普通段落、标题和 URL 密集、多个短 C# 代码块、单个长代码块 |
| 编辑位置 | 文首、文中、文尾 |
| 编辑动作 | 输入字符、退格、回车、修改代码块围栏 |
| 坐标边界 | LF、CRLF、代理对字符 |
| 缓存状态 | 初次着色、同文重复、逐字编辑 |

编辑序列应固定；使用文档坐标 API 时正确转换 UTF-16 索引。性能测试之后验证文本内容与关键样式，防止通过漏着色获得虚假性能收益。

### 第二层：输入与布局集成测试

第一层不包含应用 Dispatcher 的真实排队、完整布局和屏幕呈现，不能宣称测得用户端到端输入延迟。

进一步复用应用侧调度逻辑，在自动化 Avalonia UI 测试宿主中记录：

- 文本变更到着色开始：排队时间。
- 着色开始到结束：同步阻塞时间。
- 文本变更到对应版本布局完成：输入到布局延迟。
- 每轮输入的高亮调用次数、布局次数，检查是否存在事件放大。

必须等待明确的完成信号并设置超时，不能用固定 Sleep 充当完成条件；不能测完输入方法返回就停止计时。文档版本需要关联，以免把上一次布局完成误当作本次完成。无头环境的布局完成也不等于真实屏幕呈现。

### 第三层：阶段归因（后续需要库侧支持）

若整体测量仍不足以定位，可在库侧增加默认关闭的结构化诊断，分别采集解析、快照构建、区间坐标转换、样式应用、代码块着色，以及布局阶段；通过计数器记录全文提取次数、处理块数、实际应用块数等。该步骤需要单独处理底层库只读边界。

内置计时能测量划定的区间，不会自动提供未插桩方法的完整 CPU 调用树。不要为诊断使用无限制反射或高频字符串日志。

## 如何接入自动测试与防止误报

- 性能用例使用独立测试集合并关闭与其他集合的并行执行，通过测试分类自动发现；无需打开应用、手动输入或外部 profiler。
- 常规测试运行正确性与可重复的工作量断言；性能基线在 CI 的 Release 无调试任务中自动运行，报告写入测试输出。
- 尚无库侧计数能力时，只报告时延和分配，不能虚构工作量断言。
- 建立基线之后再设置经过验证的宽松回归预算。不要一开始就对每次调用硬断言 16 ms，也不要只凭单次计时或整套测试总时长判断优化成败。
- 相同机器上的前后版本、不同规模增长趋势、文首/文尾对比均可帮助定位；比值也受噪声影响，不是天然稳定的硬门槛。
- 报告保留运行时、构建配置、操作系统、场景规模、样本数及原始摘要；分配统计不在样本间强制 GC。

## 建议优化顺序（尚未实施）

1. 给 Markdown 的样式设置器传入当前 `markdownText`，消除每个区间重复提取全文；仍需处理坐标转换反复扫描的问题。
2. 一轮构建坐标映射或使用有序游标，避免每个区间从文首扫描；保留 CRLF 和代理对语义测试。
3. 按代码块内容、语言及相关样式配置复用相对着色结果，避免仅因绝对偏移变化而重跑代码分析；应用时仍需映射到新坐标。
4. 依据测量结果减少不必要的样式应用及布局；使用编辑器已有批量机制前先核实 API 与事件语义。
5. 最后评估后台解析与版本校验。不能把整个 `ApplyHighlight` 直接放进 `Task.Run`，因为它修改 UI 关联编辑器状态。后台仅计算不可变结果，UI 线程应用当前版本，过期结果丢弃。

调度防抖只能减少执行频率，不能消除单轮同步阻塞，不应代替上述热点优化。
