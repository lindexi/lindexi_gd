# 文本着色性能优化实践：从自动化复现到受控改动

本文提炼 SimpleWrite 的 Markdown 着色优化经验，面向其他文本编辑器、语法着色器、富文本处理和区间样式系统。重点是可迁移的方法，而不是要求其他项目采用相同实现。

项目原始调查、各阶段报告索引与详细数字见 [Markdown 着色性能记录](../Avalonia/Markdown-Highlighting-Performance.md)。以下数字均为本机探索性结果，不是跨机器性能承诺。

## 1. 先明确测量边界

“输入卡顿”不是一个单独的方法耗时。应拆成：

1. 输入事件和文档内容修改。
2. 提取文本快照。
3. 语法解析、快照构造、区间计算。
4. 样式比较与应用。
5. 布局及绘制。
6. UI 调度排队和最终屏幕呈现。

本次测试测量真实编辑器的同步编辑、取全文及高亮调用，不包含完整 UI 排队与屏幕绘制。所谓“打开”是创建编辑器、装入内存文本、取全文和首次着色，不包括磁盘读取及应用启动。

**把测量范围写进测试报告，避免用局部方法返回时间宣称端到端体验已经改善。** UI Dispatcher 的 Background 优先级仍在 UI 线程执行，并不等于后台计算。

## 2. 用普通测试框架建立可复现基线

无需外部 profiler，就可以用现有 xUnit/NUnit/MSTest 与 .NET 内置 API 建立第一层性能测试：

- 用 `Stopwatch.GetTimestamp` 和 `Stopwatch.GetElapsedTime` 记录阶段耗时。
- 用 `GC.GetAllocatedBytesForCurrentThread` 的差值记录同步区间的托管分配。
- 使用真实文档模型和高亮器，不 mock 正在测量的实现。
- 每个样本真正插入字符，再对新文本着色；同文重复着色单列为缓存命中场景。
- 保留原始样本和中位数、P95、最大值，不只输出平均值。
- 数据准备、预期结果构造、断言、JSON 序列化及写盘都放在计时区间外。
- 记录运行时、操作系统、架构、构建配置、是否附加调试器、文档大小及样本数。
- 采用 Release、无调试器、禁止测试并行；不要在每个样本前强制 GC。

当前线程分配不包括原生内存，不等于存活内存、进程工作集或 GC 次数；跨线程、跨 await 的工作不能直接用该计数差值解释。

### 适合移植的测试矩阵

| 维度 | 建议场景 |
|---|---|
| 文档规模 | 小、中、大，记录实际字符数而非只有文件名 |
| 内容 | 普通文本、标题、链接密集、列表、各语言代码块、未知语言 |
| 编辑位置 | 文首、文中、文尾 |
| 操作 | 输入、删除、回车、语法边界变化 |
| 缓存 | 首次着色、同文重复、连续编辑 |
| 对照 | 不启用高亮的相同编辑序列 |
| 坐标 | LF、CRLF、代理对字符、非零区间起点 |

本次已实现的矩阵以插入为主，不能把表中建议的所有操作都视为已经覆盖。

### 冷启动和稳态分开

首次打开可能包含 JIT、静态初始化和字体等缓存初始化。后续测量应使用新的编辑器实例，但明确它们仍位于已运行的进程中。整个测试程序集运行顺序不保证某个用例第一个执行，因此“该用例第一次打开”不一定是进程冷启动。

## 3. 本次发现的三个可迁移问题

### 3.1 下层辅助函数隐藏了重复全文读取

上层已经拿到 Markdown 文本，但创建区间样式设置器时没有传入它。设置器每次转换区间起止位置，都回退到编辑器重新获取全文。

如果有 K 个样式区间、全文长度 N，约 2K 次全文提取会放大为 O(KN) 级别的文本处理工作，并产生大量短命对象。

第一步仅在调用处填充设置器已有的 `PlainText` 属性，没有重构算法。约 1.1 万字符、100 个短 C# 代码块的文首输入场景中：

- 单轮着色中位数从 7286 ms 降至 127 ms。
- 单轮着色平均托管分配从 616.44 MB 降至 12.86 MB。

**迁移经验：先检查热循环中的便利 API 是否隐藏了全文复制、枚举、序列化或 I/O。调用方已有的数据，应在清晰的生命周期内传递复用。**

### 3.2 坐标转换重复从起点扫描

Markdown 使用 UTF-16 索引，而编辑器的字符偏移会折叠 CRLF，并将代理对视作一个字符。原实现每个区间端点都从文本开头重新扫描。

后续优化为：固定文本快照建立一次索引映射，端点转换直接查表。构建复杂度 O(N)，查询 O(1)，额外内存约为 `4 × (UTF-16 长度 + 1)` 字节；20 万字符约占 0.8 MB。

必须保留的语义：

- CRLF 与单独 CR/LF 的行为。
- 有效代理对、孤立代理项及代理对中间索引的原有转换行为。
- 空文本、文档末尾、非法索引和非零起始偏移。
- 文本变化后不能复用旧映射。

本项目将映射限制在传入文本的设置器生命周期内；未提供文本的路径仍沿用原转换。若其他项目文本很短、样式区间很少，一次完整映射可能得不偿失，可评估有序游标或稀疏检查点。不能盲目复制数组缓存方案。

### 3.3 最终样式相同，但中间发生大量修改

原段落着色先整段设置普通样式，再给链接设置链接样式。在文首或文中输入后，后续块的绝对偏移变化，快照失效；未变的链接也会经历“清除 → 恢复”。

改为生成互不重叠的普通文本和链接区间，使已有样式相同的区域能够直接跳过实际修改。删除链接时，原链接位置必须由普通样式覆盖，不能只更新仍存在的链接。

**迁移经验：不仅要比较最终输出，也要检查应用过程是否制造了多余状态变化。** 这同样适用于 UI 属性更新、富文本格式化和增量渲染。

## 4. 失败尝试同样需要记录

本次没有直接一次性提交所有设想，而是分别测试：

| 尝试 | 观察与判断 |
|---|---|
| 只拆分普通文本/链接区间 | 输入分配下降，但耗时没有改善，首次着色变慢；更多区间增加了转换与遍历成本 |
| 只建立坐标映射 | 未观察到稳定的整体耗时改善；消除一种扫描不等于消除全部开销 |
| 两者组合 | 输入耗时与分配明显下降，但打开阶段仍存在成本和波动 |

两项优化会相互影响：区间拆分增加转换次数，而索引映射降低每次转换成本。因此，单项尝试没有收益，不代表组合一定没有收益；反过来，也不能用组合收益声称其中每一项独立有效。

这些运行存在机器负载和运行时状态波动，不构成严格的因果归因实验。更可靠的后续验证应使用固定环境、多次交替运行前后版本，并增加阶段计时和工作量计数。

## 5. 大文档实测与尚未解决的问题

文档为 1000 个物理行，每行 200 个 UTF-16 字符，不含换行；全文 200999 字符，以中文为主，包含标题、加粗、强调和链接，无代码块。在第 501 行正文开始连续输入 12 个汉字。

| 指标 | 复用全文后的基线 | 映射与区间拆分组合后 |
|---|---:|---:|
| 每字着色中位数 | 800.83 ms | 181.62 ms |
| 每字同步处理总耗时中位数 | 810.63 ms | 198.35 ms |
| 每字着色平均托管分配 | 111.49 MB | 43.76 MB |
| 每字总平均托管分配 | 112.81 MB | 45.07 MB |

MB 为十进制。测试不包含完整 UI 延迟。标题、加粗语法存在于测试输入，不表示现有实现已对全部 inline 语法提供视觉样式。

**输入改善并不等于优化完成：** 约 198 ms 的同步处理仍可能明显卡顿。打开合计分别测得约 1.50、0.97、2.07 秒，未见稳定改善；分配从约 247 MB 增至约 270 MB。不能只报告输入收益而隐去打开阶段的成本。

下一步应量化解析、快照构造、属性遍历、实际属性修改、布局请求次数，再决定是否缓存相对样式、进行增量解析或批量应用。不要继续仅凭总耗时猜测热点。

## 6. 正确性必须随优化一起验证

优化不能靠漏着色、丢链接、跳过布局或破坏撤销来换取更快数字。至少考虑：

- 编辑后全文与预期一致。
- 插入导致后续偏移变化，标题和链接仍正确定位。
- 链接删除后恢复普通样式，链接后的文字没有错误继承链接样式。
- LF、CRLF 和代理对字符仍与原坐标转换一致。
- 不相关语言高亮路径没有回归。

本次高亮库 372 项测试和应用侧 167 项测试通过；这不能证明所有语义边界已覆盖，也不是性能达标证明。公开 API 可以验证结果，内部算法的穷举或差分测试可按所在仓库的测试访问约定另行补充。

## 7. 自动化运行与报告注意事项

- 性能测试通过分类供测试运行器和 CI 自动发现，报告自动落盘；不需要手动打开编辑器打字。
- 报告使用唯一文件名避免覆盖，并记录所属版本或构建标识，便于长期对比。本次历史报告主要通过文档记录文件名，其他项目建议直接在报告中加入构建标识。
- 初期先采集基线，不立即设严格毫秒阈值；基线稳定后再增加经过验证的宽松回归预算。
- 少量样本的 P95 很不稳定：本次 8 或 12 个样本的 nearest-rank P95 等于最大值，只能作探索参考。
- 若耗时过长，公开说明采样数调整，不要静默删掉最慢场景。
- 测试总运行时间不能代替每次输入的延迟；测试通过也不能代表用户体验达标。

## 8. 迁移到其他项目的检查清单

1. 写出实际输入到显示的调用链，明确同步和异步边界。
2. 固定真实数据形态、编辑位置与操作序列。
3. 分别测首次打开、稳态输入及无高亮对照。
4. 检查热循环中的全文读取、坐标转换和临时对象。
5. 检查是否因为绝对位置变化而使大量缓存失效。
6. 检查是否反复清除再恢复本来正确的样式。
7. 每次小改动保留前后报告，记录失败实验与内存代价。
8. 验证文本、样式、Unicode 坐标和撤销等语义。
9. 同时评估打开和输入，不只优化一个指标。
10. 如果考虑后台解析，只在后台处理不可变快照；UI 线程应用当前版本，过期结果丢弃。不能直接把修改编辑器的方法放进 `Task.Run`。

核心原则：**先让问题可自动复现，再减少重复工作；用测量决定保留什么，用正确性测试约束不能牺牲什么。**
