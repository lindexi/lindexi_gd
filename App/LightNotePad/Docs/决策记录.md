## D01：保存编码 — UTF-8 无 BOM

### 背景

文件编码决定文本在不同系统和软件之间的可移植性。BOM（Byte Order Mark）在部分场景下会导致兼容性问题（如 Unix 脚本解析、Git diff 噪音、某些编辑器不识别）。

### 备选方案

| 方案 | 描述 |
|------|------|
| A | UTF-8 with BOM（Windows 记事本默认） |
| B | UTF-8 无 BOM |
| C | 保留原始编码不变 |
| D | 用户可选择编码 |

### 选定方案

**方案 B：UTF-8 无 BOM**（`new UTF8Encoding(false)`）

### 决策理由

1. **跨平台兼容性**：UTF-8 无 BOM 是 Linux/macOS/Git/Web 的事实标准
2. **开发工具友好**：Git diff 中无 BOM 噪音，CI/CD 脚本无干扰
3. **用户无感知**：普通用户不关心编码细节，现代软件（VS Code、Notepad++、浏览器）均能正确处理 UTF-8 无 BOM
4. **与 Windows 记事本差异化**：Windows 记事本默认 UTF-8 with BOM，但部分场景 BOM 有害（如 shebang 脚本），LightNotePad 默认更安全

### 对标产品行为

| 产品 | 默认保存编码 |
|------|-------------|
| Windows 记事本（Win10+） | UTF-8 with BOM |
| VS Code | UTF-8 无 BOM |
| Notepad++ | UTF-8 无 BOM（可选） |
| **LightNotePad** | **UTF-8 无 BOM** |

### 影响范围

- **F08 保存/另存为**：写入时必须显式 `new UTF8Encoding(false)`
- **TC-F08-04**：需用 hex 工具验证保存文件前 3 字节非 `EF BB BF`
- **F11 编码处理**：打开时 .NET StreamReader 自动检测 BOM，保存时始终无 BOM

### 变更追溯建议

若未来需要支持用户选择编码：
1. 在设置界面增加「保存编码」下拉选项
2. 默认值仍为 UTF-8 无 BOM
3. 更新 TC-F08-04 和 TC-F11-03 用例

## D02：状态栏行列号 — 逻辑行语义

### 背景

文本编辑器状态栏的行列号有两种计算方式：逻辑行（源文件行）和视觉行（屏幕折行）。两者在自动换行场景下差异显著。

### 备选方案

| 方案 | 描述 |
|------|------|
| A | 逻辑行：按源文件换行符（`\n`/`\r\n`）计算，Tab/CJK 各算 1 字符 |
| B | 视觉行：按屏幕折行计算，自动换行时行号随折行变化 |
| C | 同时显示两者（如 "Ln 5, Col 3 (Vis 8)"） |

### 选定方案

**方案 A：逻辑行**，Tab 算 1 字符，CJK 字符算 1 字符

### 决策理由

1. **对标 Windows 记事本**：Windows 记事本使用逻辑行 + Tab/CJK 各算 1 字符
2. **一致性优于视觉精确**：用户习惯用行列号定位（如报错日志 "第 42 行第 5 列"），逻辑行号与文件内容一一对应
3. **实现简单**：LightTextEditorPlus 底层直接支持逻辑行定位
4. **避免混淆**：视觉行号随窗口宽度变化，同一位置在不同窗口宽度下行号不同，不适合作为定位依据

### 对标产品行为

| 产品 | 行列号语义 | Tab 算 | CJK 算 |
|------|-----------|--------|--------|
| Windows 记事本 | 逻辑行 | 1 字符 | 1 字符 |
| VS Code | 逻辑行 | Tab 大小可配置 | 1 字符 |
| Notepad++ | 逻辑行 | 1 字符 | 1 字符 |
| **LightNotePad** | **逻辑行** | **1 字符** | **1 字符** |

### 影响范围

- **F13 状态栏**：订阅 `CurrentCaretOffsetChanged`，按逻辑行计算
- **TC-F13-04~06**：Tab、CJK、自动换行场景的状态栏验证
- **自动换行（F12）**：视觉折行不改变 Ln 值

### 变更追溯建议

若未来需要支持视觉行显示：
1. 作为可选的显示模式（非默认）
2. 需要同时在状态栏标注 "逻辑行" 或 "视觉行"
3. 更新 F13 全部测试用例

## D03：默认换行 — 自动换行

### 背景

纯文本编辑器最基础的排版选项：是否在窗口边缘自动折行。对阅读体验有直接影响。

### 备选方案

| 方案 | 描述 |
|------|------|
| A | 默认自动换行 |
| B | 默认不换行（需要水平滚动条） |

### 选定方案

**方案 A：默认自动换行**

### 决策理由

1. **阅读优先**：LightNotePad 定位「阅读优先」，自动换行避免用户水平滚动，阅读体验更好
2. **对标 Windows 记事本**：Windows 记事本默认自动换行
3. **用户输入习惯**：绝大多数普通用户不会写超长行代码，自然换行更符合直觉
4. **LightTextEditorPlus 已实现**：底层库已支持，接入成本为零

### 对标产品行为

| 产品 | 默认换行 |
|------|----------|
| Windows 记事本 | 自动换行 |
| VS Code | 不换行（代码编辑器） |
| macOS 文本编辑 | 自动换行 |
| **LightNotePad** | **自动换行** |

### 影响范围

- **F12 自动换行**：T40 配置默认开启
- **TC-F12-01**：验证启动后自动换行为开启状态
- **F13 状态栏**：逻辑行不受折行影响（D02）
- **F15 触摸滚动**：自动换行时主要为垂直滚动

### 变更追溯建议

若未来需要默认不换行（面向程序员场景）：
1. 在设置界面增加开关
2. 可考虑根据文件扩展名（.cs/.py/.js）智能切换默认值
3. 更新 TC-F12-01 验证默认值

## D04：对标产品 — Windows 记事本

### 背景

明确定位参考物有助于统一团队的行为预期，减少无谓讨论。

### 备选方案

| 方案 | 描述 |
|------|------|
| A | 对标 Windows 记事本 |
| B | 对标 Notepad++ |
| C | 对标 VS Code |
| D | 对标 macOS 文本编辑 |
| E | 不定对标，独立设计 |

### 选定方案

**方案 A：Windows 记事本**

### 决策理由

1. **零学习成本**：目标用户为普通用户，Windows 记事本是他们最熟悉的文本工具
2. **功能边界清晰**：记事本功能极简，天然限制了范围蔓延（scope creep）
3. **行为可预测**：行列号、编码、快捷键等行为有明确参照，减少产品决策争议
4. **差异化空间适中**：在记事本基础上微调（UTF-8 无 BOM），既熟悉又更好

### 对标产品行为对照

| 行为 | Windows 记事本 | LightNotePad | 是否一致 |
|------|---------------|-------------|----------|
| 默认保存编码 | UTF-8 with BOM | UTF-8 无 BOM | ❌（刻意差异） |
| 状态栏行列号 | 逻辑行，Tab/CJK=1 | 逻辑行，Tab/CJK=1 | ✅ |
| 默认换行 | 自动换行 | 自动换行 | ✅ |
| 未保存提示 | 三选一 | 三选一 | ✅ |
| 窗口标题 | `{文件} - 记事本` | `{文件} - LightNotePad` | ✅（模式一致） |
| 查找替换 | Ctrl+F/Ctrl+H | Ctrl+F/Ctrl+H | ✅ |
| 字体缩放 | Ctrl+滚轮 | 不支持 | ❌（刻意差异） |

### 影响范围

- **全部 15 项功能**：行为不一致时优先对齐 Windows 记事本
- **TC-F13-09**：需与记事本对比行列号
- **TC-F09** 系列：关闭提示行为对齐

### 变更追溯建议

若未来需要调整对标策略：
1. 明确新的对标产品和理由
2. 全量审计功能差异清单
3. 更新全部对比测试用例

## D05：不做 — 拖拽选中文本

### 背景

部分文本编辑器支持用鼠标拖拽已选中的文本来移动/复制文本。这是一个常见但非必需的功能。

### 备选方案

| 方案 | 描述 |
|------|------|
| A | 支持拖拽移动/复制选中文本 |
| B | 不支持拖拽选中文本 |

### 选定方案

**方案 B：不支持**

### 决策理由

1. **用户明确要求**：需求对齐阶段用户明确表示不需要
2. **对标记事本**：Windows 记事本本身不支持此功能
3. **实现成本**：需要额外的拖拽事件处理、光标定位、撤销栈集成
4. **误操作风险**：普通用户可能误拖导致文本错位，增加学习成本

### 对标产品行为

| 产品 | 拖拽选中文本 |
|------|-------------|
| Windows 记事本 | ❌ 不支持 |
| VS Code | ✅ 支持 |
| Notepad++ | ✅ 支持 |
| **LightNotePad** | **❌ 不支持** |

### 影响范围

- **不做测试范围 N01**：不编写拖拽选中文本相关测试用例
- **F04 复制粘贴剪切**：用户通过 Ctrl+C/X/V 完成同等操作

### 变更追溯建议

若未来需要支持：
1. 评估与 LightTextEditorPlus 底层的兼容性
2. 增加 TC-F04-11「拖拽移动选中文本」用例
3. 确保与撤销栈（F03）和关闭未保存提示（F09）无冲突

## D06：不做 — 超大文件特殊处理

### 背景

超大文本文件（>100MB）可能引起性能问题。常见的处理方式包括：分块加载、只读模式、内存映射等。

### 备选方案

| 方案 | 描述 |
|------|------|
| A | 特殊处理超大文件（分块加载/只读/内存映射） |
| B | 不做特殊处理，由用户自行承担性能风险 |

### 选定方案

**方案 B：不做特殊处理**

### 决策理由

1. **用户明确要求**：需求对齐阶段用户明确表示不管超大文件
2. **场景极低频**：普通用户极少打开 100MB+ 纯文本文件（此类文件通常是日志/数据导出）
3. **实现成本高**：分块加载/内存映射需要大幅改动 LightTextEditorPlus 集成方式
4. **MVP 优先**：在 M1-M3 有限时间内，优先保障常规文件体验

### 对标产品行为

| 产品 | 超大文件策略 |
|------|-------------|
| Windows 记事本 | 直接加载，可能卡死 |
| VS Code | 分块加载 + 限制 |
| Notepad++ | 直接加载，可能卡顿 |
| **LightNotePad** | **不做特殊处理** |

### 影响范围

- **不做测试范围 N02**：不测试 500MB+ 文件
- **D-01 异常场景**：100MB 文件作为冒烟（不崩溃即可，不要求性能）
- **性能基线 P02**：仅针对 1MB 文件

### 变更追溯建议

若未来需要支持：
1. 在 M4+ 版本规划中评估
2. 最低要求：打开 >100MB 文件时不崩溃、提示用户文件较大
3. 理想方案：分块加载首屏 + 异步加载后续内容

## D07：不做 — Ctrl+滚轮字体缩放

### 背景

许多现代编辑器（VS Code、浏览器、Word）支持 Ctrl+滚轮缩放字体。这是一个常见的体验增强功能。

### 备选方案

| 方案 | 描述 |
|------|------|
| A | 支持 Ctrl+滚轮缩放字体 |
| B | 不支持，字体大小仅通过设置界面修改 |

### 选定方案

**方案 B：不支持**

### 决策理由

1. **用户明确要求**：需求对齐阶段用户明确表示不要 Ctrl+滚轮
2. **对标记事本**：Windows 记事本不支持 Ctrl+滚轮缩放
3. **简化交互**：减少快捷键复杂度，降低误操作概率
4. **设置持久化**：字体大小通过设置界面统一管理，行为可预测

### 对标产品行为

| 产品 | Ctrl+滚轮缩放 |
|------|--------------|
| Windows 记事本 | ❌ 不支持 |
| VS Code | ✅ 支持 |
| 浏览器（Chrome/Edge） | ✅ 支持 |
| **LightNotePad** | **❌ 不支持** |

### 影响范围

- **不做测试范围 N03**：不编写 Ctrl+滚轮相关用例
- **F14 字体设置**：字体大小仅通过设置界面 → T45-T49
- **快捷键注册（T54）**：无需为 Ctrl+滚轮注册事件

### 变更追溯建议

若未来需要支持：
1. 增加 TC-F14-08「Ctrl+滚轮缩放」用例
2. 考虑是否持久化缩放比例（临时缩放 vs 持久设置）
3. 注意与触摸缩放手势（pinch-zoom）的关系
