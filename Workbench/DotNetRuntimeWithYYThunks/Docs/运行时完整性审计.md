# 运行时完整性证据审计

审计日期：2026-10-30。没有重建 runtime、没有安装环境、没有修改既有产品、历史日志、原始 manifest 或 Builder 组装实现。只新增 `Builder/IntegrityAudit` 独立 net10.0 审计器及本报告。使用专用运行入口执行审计器，Release 编译和实际运行退出 0；`audit-self-checks.json` 全部通过。

## 结论及边界

1. **“实际构建完全没有使用 Python”不成立。** 两份最终成功的原始构建日志均记录 Python 3.9.13 的发现，以及 `python.exe .../pgocheck.py coreclr.dll clrjit.dll` 的实际命令和后续 PGO 检查结果。这证明使用过 Python，但不能扩张为“所有 Python 代码生成脚本都在这次重新执行”。
2. **不能证明从 clean 树全量构建。** 成功日志有增量目标、Up-to-date 和 `incremental-native-build`；Builder 只删除相关 CMakeCache 和 cmake_cmd_line，不删除全部中间输出。未捕获每个生成器的历史运行不是其从未运行的证据；当前 Ninja 规则也不是执行证据。
3. 对照安装文件确实已完成全量枚举、SHA256 和长度比较，而非只检查 smoke 或几个关键 DLL。参考安装实际为 **x86**，不是预先假定的 x64：根 dotnet.exe、所有参考 hostfxr.dll 和 coreclr.dll 的 PE Machine 均为 I386。x86 有同架构但不同版本参考；**x64 没有直接同架构参考，仅布局对比**。所有 hash 结果仅是观测，不要求不同版本、架构、签名、优化选项的文件相等。
4. 未发现证据足够认定的、需要立即修复的 Builder 运行时 DLL 组装漏项。产品与两级历史 manifest 完全一致，deps 列出的所有资产存在。**不据此认证标准发行内容完全等价**：`.version` 元数据确实没有发布，x64 有额外 interpreter/GC，未做 ReadyToRun；历史没有详细 binlog/逐目标执行轨迹，无法追认所有条件验证、生成器均重新运行。
5. 不以 smoke 成功替代完整性，也不以此认证 Win7。未触发产品修复，因此没有伪造 post 产品；本次只读结果就是 pre 审计基线，历史失败和成功证据全部保留。

## 证据目录与重现

全部输出位于 `Builder/artifacts/integrity-audit/`：

- `inventories.json`：参考与两份成品，所有版本、相对路径、来源、文件长度、SHA256、PE Machine；参考顶层目录也有记录，但 SDK 等不参与 missing。
- `comparisons.json`、`full-diff.tsv`：18 组比较的**完整** missing、extra、common-equal、common-differing，每项带双方长度和 hash，不是样本。
- `host-fxr-comparisons.json`：参考每个实际存在的 fxr 版本与两份产物的完整文件信息。每个 fxr 版本均只有 hostfxr.dll；版本归一后 missing/extra 均 0、common-differing 均 1。
- `missing-classification.json`：每一个 missing 的分类；跨大版本未给同版本遗漏结论。
- `mapping.json`、`mapping-summary.json`：全部 deps 资产到目的文件映射、原始和发布 manifest 核验；`summary.json` 为汇总。
- `decoded-commands.json`：历史 plan 的 EncodedCommand **仅解码成文本，没有执行**，保留实际入口和全部参数。
- `evidence-lines.json`：日志、CMakeCache、Ninja、官方清单与 SDK targets 的逐行命中，含原路径和行号。
- `evidence-index.json`、`evidence/`：原日志、计划、manifest、生成规则、当前 cache、官方相关源码和本地 SharedFramework SDK targets 快照，索引记录 hash。外部包路径在快照中以 `_parent_` 编码，写入仍局限在 Builder。
- `findings.txt`：所有 missing/extra 和关键 Python 证据的可读汇总。
- `audit-self-checks.json`：比较组数、文件分区守恒、两级 manifest、deps 资产存在性检查。

专用执行命令为 `dotnet run --project Builder/IntegrityAudit/IntegrityAudit.csproj -c Release -- Builder`。它不启动 runtime 构建或 Python，不修改参考/产物，不执行解码脚本。本次多次运行仅改进审计输出，产品未重建。

### 对照最近的同大版本 10.0.14：逐个 missing/extra

以下均位于 `shared/Microsoft.NETCore.App/<version>/`。

x86 missing 2：
- `.version`：真实路径差异，但不是缺失的执行程序集。官方 `Microsoft.NETCore.App.Runtime.props:68-84` 的 `CreateDotVersionFile` 仅在 `EnableSourceControlManagerQueries == true` 时生成并添加到 FilesToPublish。成功日志未记录该属性最终求值，不能断言具体为何为 false 或目标为何未产出；属于有条件的源码版本元数据差异，不能冒充完全一致标准发行。Builder 命令未显式关闭该属性，不手工伪造文件。
- `mscordaccore_x86_x86_10.0.1426.52326.dll`：构建版本限定的 DAC 别名。产物存在 `mscordaccore.dll` 和 `mscordaccore_x86_x86_42.42.42.42424.dll`；并非应复制参考的不同版本 DAC。

x86 extra 1：`mscordaccore_x86_x86_42.42.42.42424.dll`。

x64 missing 3：`.version`、上述参考 x86 DAC 别名、`Microsoft.DiaSymReader.Native.x86.dll`。后两者为架构/版本命名不同，x64 对应 `mscordaccore_amd64_amd64_42.42.42.42424.dll` 和 `Microsoft.DiaSymReader.Native.amd64.dll`。官方 Runtime.props:56-65 将 x64 映射为 amd64。

x64 extra 4：`clrgcexp.dll`、`clrinterpreter.dll`、`Microsoft.DiaSymReader.Native.amd64.dll`、`mscordaccore_amd64_amd64_42.42.42.42424.dll`。

`clrinterpreter.dll` 不应被误判为“标准发布必需而 x86 漏掉”。官方当前平台条目有 Unix Debug/Checked 的解释器条件，没有 Windows Release 解释器条目；Builder/RuntimeLayout.targets 额外给 Windows x64 加入平台条目，NativePlan 给该目标加入官方版本资源。此为非标准特性/发布配置差异，不是绕过版本检查。clrgcexp 在官方平台允许条目内，但平台允许不代表标准发行每架构必带。不能据此认证 x64 的配置等价官方零售发行。

旧大版本大量 missing 是旧版 Windows API-set/UCRT 分发文件，以及版本/架构特定文件，不从 3.x/6.x 复制它们来“补齐”10.x。逐项已保存在完整 diff 和分类 JSON；分类只说明跨版本，不声称已证明每项可无条件删去，尤其不据此认证 Win7 依赖闭包。

## skip、子集、优化和验证

历史解码命令实际为 `eng/build.ps1 -subset clr.runtime+clr.corelib+libs.native+libs.sfx+host.native+host.tools -arch x86|x64 -os windows -configuration Release -runtimeConfiguration Release`。不是构建所有测试/SDK/所有 CLR 工具；选择 clr.runtime 而不是宽泛 clr.native，早期失败与后续成功都保存在 evidence 快照。CLR、CoreLib、libs、host 的实际输出可在成功 0.log 中核实，不仅依据计划。

随后实际调用官方 Runtime.CoreCLR.sfxproj 的 GetFilesToPublish 及 Bundle.bundleproj 的 PublishToDisk。显式属性：`PublishReadyToRun=false`、`GenerateInstallers=false`、`GeneratePackageOnBuild=false`、`RuntimeFlavor=CoreCLR`、`PrimaryRuntimeFlavor=CoreCLR`，以及 Builder 的 DirectoryBuildTargetsPath。**ReadyToRun/crossgen 发布优化确实关闭**，不是日志未捕获；安装器/NuGet 包不属于此 runtime 文件夹交付。文件长度较零售版小不能直接判缺文件，版本/签名/优化均不同。

核对实际本地 SharedFramework SDK `10.0.0-beta.26116.108/targets/sharedfx.targets`（完整快照位于 evidence 的 `_parent_.../.nuget/packages/`；其他缓存 SDK 版本仅旁证，不混为实际版本）：

- 579-585：GetFilesToPublish 调用 `_GetAllSharedFrameworkFiles`。
- 531-543：该目标依赖 deps/runtimeconfig 生成、平台清单、闭包、重复类型、文件版本验证。
- 298-307：平台检查 `已打包文件 - PlatformManifestFileEntry`，发现没有清单条目的已打包文件会报错；**不是反向要求所有允许条目都存在**。
- 521-527：文件版本检查除非 `PermitDllAndExeFilesLackingFileVersion=true`；闭包和重复类型除非 `SkipValidatePackage=true`。
- 587-603：官方过滤 PackOnly 和不适合 runtime 的目标路径；607-617：PublishToDisk 过滤普通符号文件并 SkipUnchangedFiles。它们不是 Builder 手工排除 DLL。

Builder 源码、历史命令未发现显式 `SkipValidatePackage=true`、`PermitDllAndExeFilesLackingFileVersion=true` 或关闭平台验证。RuntimeLayout.targets 导入正常父 targets，只补 interpreter 条目；不是空 targets 替代验证。但成功日志为普通输出，无二进制日志和最终属性 dump，因此只能说**验证链可达且没有显式关闭证据**，不能声称每个条件验证都已由详细运行轨迹单独证实。

Builder 的 `RuntimeLayout.Validate` 仅检查少数关键文件、5 个 PE 架构和全量文件 hash，不是官方全量发行清单验证。原文“未跳过验证”应按上述边界理解，不能扩大为每项官方发行质量门均已认证。

## 后续建议（本次未执行）

若要求可重现的标准发行完整性认证，应另开有明确边界的 clean 构建实验，保留详细 binlog、Ninja verbose、生成器轨迹、最终属性和 GetFilesToPublish 展开清单，并选同版本同架构同选项官方包比较。若交付契约要求 `.version` 或标准 Release 特性集，应先确认该契约与源码控制查询条件，再最小修正 Builder，并另存 pre/post；本次不伪造版本元数据、不移入用户安装文件、不通过重建掩盖历史。
