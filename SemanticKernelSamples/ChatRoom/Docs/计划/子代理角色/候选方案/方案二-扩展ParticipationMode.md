# ChatRoom 子代理角色候选方案二：扩展 ParticipationMode

## 1. 方案概述

在现有参与模式中加入仅允许子代理协议调用的值：

```text
AlwaysParticipate
MentionOnly
SubAgentOnly
```

`SubAgentOnly` 同时承担普通聊天室调度隔离与子代理身份标识。

共同产品约束见[需求功能](../ChatRoom-子代理角色需求功能.md)。本文档只描述该建模方案的差异。

## 2. 主要改造

- 在 legacy 与 Domain 的参与模式中加入 `SubAgentOnly`。
- 自动调度、普通 mention、管理者兜底和公开执行入口统一排除 `SubAgentOnly`。
- 用户严格前缀解析与 AI 专用工具只允许调用 `SubAgentOnly` 角色。
- 角色模板、持久化和 UI 增加新参与模式。
- 旧数据保持现有参与模式，不发生语义变化。

子代理调用、临时会话、返回工具、上下文隔离和错误处理仍需独立实现，不能仅依赖枚举值完成。

## 3. 优点

- 新增字段最少。
- 可复用现有参与模式在调度和 UI 中的传播链路。
- 旧枚举值不变时，旧数据兼容相对直接。
- 对 legacy 角色模型的表面改动较小。

## 4. 缺点与风险

- `ParticipationMode` 原本回答“普通聊天室中何时参与”，子代理身份回答“允许通过哪种协议执行”，两个维度被混在同一枚举。
- 子代理仍需防御性禁止普通执行入口，说明单一参与模式不能完整表达调用协议。
- 参与模式切换会同时改变角色身份和调用权限，容易产生意外行为。
- `SubAgentOnly + IsManagerRole` 等组合缺少清晰语义，需要额外不变量。
- 未来增加更多受控调用协议时，参与模式枚举会持续膨胀。
- Standard/Coding 执行引擎、管理者身份和调用协议之间的正交关系不够清晰。

## 5. 对两套架构的影响

### 5.1 legacy `ChatRoomManager`

需要修改自动循环、普通 mention、直接执行、上下文构造、模板、JSON 持久化与 Avalonia 配置入口。

### 5.2 新 `ChatRoomCoordinator`

需要修改角色状态、命令验证、mention 调度、runtime 入口、snapshot schema 与角色动态更新逻辑。

两套架构必须对 `SubAgentOnly` 保持一致解释，否则同一角色在迁移前后会出现行为差异。

## 6. 适用条件

只有在团队明确接受“子代理就是一种参与模式”，并确定未来不会引入更多独立调用协议时，才适合采用本方案。

## 7. 结论

当前不推荐。

虽然本方案表面改动较少，但会形成长期语义债务。子代理调用协议与普通聊天室参与时机应保持独立，以便形成可验证的角色不变量。
