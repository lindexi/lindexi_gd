# ChatRoom 子代理角色候选方案三：独立子代理注册表

## 1. 方案概述

普通聊天室角色定义保持不变，房间另外维护子代理定义集合与运行时注册表。普通参与者和子代理从模型层开始分离，不共享同一角色集合。

共同产品约束见[需求功能](../ChatRoom-子代理角色需求功能.md)。本文档只描述该建模方案的差异。

## 2. 目标模型

房间分别维护：

```text
Participants
SubAgents
```

普通调度、普通 mention 和公开执行入口只读取 `Participants`；严格用户直调和 AI 子代理工具只读取 `SubAgents`。

子代理定义仍需包含稳定身份、模型、人设、技能、执行引擎、Coding 工作区和权限配置。

## 3. 主要改造

- 新建子代理定义模型与注册表。
- 为 legacy 与 Coordinator 分别建立子代理查找和运行时入口。
- 从普通角色调度链路完全移除对子代理的识别需求。
- 角色大厅、模板、编辑页和输入提示分别支持普通角色与子代理。
- 持久化和 snapshot 同时维护普通角色集合与子代理集合。
- 定义普通角色与子代理互相转换时的身份、配置和历史迁移规则。

## 4. 优点

- 模型边界最彻底，普通调度天然无法枚举子代理。
- 普通参与者与受控任务代理可以拥有不同生命周期、权限和配置。
- 长期适合子代理与聊天室角色持续分化的场景。
- 未来可以独立扩展子代理注册、发现、权限和资源治理能力。

## 5. 缺点与风险

- 当前角色模板、角色大厅、模型配置、技能、Coding 工作区和持久化均围绕统一角色定义，需要复制或抽取大量配置模型。
- legacy 与 Coordinator 两套架构都要新增第二套集合、注册表和动态更新协议。
- UI 需要处理两类对象的创建、编辑、列表与转换。
- 普通角色转为子代理或反向转换时，需要明确身份和历史数据迁移。
- 首版改造范围大，容易把子代理功能演变成角色系统重构。
- 旧数据迁移比新增正交字段复杂。

## 6. 对两套架构的影响

### 6.1 legacy `ChatRoomManager`

需要新增独立子代理集合、查找服务、执行入口、模板和 JSON 持久化，同时保证现有角色列表不再承载子代理。

### 6.2 新 `ChatRoomCoordinator`

需要在 Domain、Coordinator、Runtime 与 snapshot 中建立第二套定义和生命周期管理，并设计跨集合更新命令。

## 7. 适用条件

当子代理与普通角色在生命周期、权限、配置项、部署方式或资源治理上出现明显分化，且团队愿意承担角色系统结构性重构时，可重新评估本方案。

## 8. 结论

首版暂不推荐。

本方案边界清晰，但当前成本明显高于需求本身。现阶段更适合在统一角色定义上增加正交调用模式，同时保留未来迁移为独立注册表的可能性。
