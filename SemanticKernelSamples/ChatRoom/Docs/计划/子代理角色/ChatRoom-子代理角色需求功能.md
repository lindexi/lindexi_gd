# ChatRoom 子代理角色需求功能

## 1. 文档目的

本文档只定义 ChatRoom 子代理角色需要实现的产品行为和审核边界，供人类确认需求是否正确、实现路径是否偏离。

候选技术方案及比较见[候选方案汇总](候选方案/ChatRoom-子代理角色候选方案汇总.md)。本文档不规定具体数据模型、类型名称或代码改造方式。

## 2. 背景

当前聊天室可以区分人类与非人类角色、自动参与与仅 mention 参与、管理者身份，以及 Standard 与 Coding 执行引擎，但这些维度都不能准确表达“只能通过受控任务协议调用”的子代理角色。

子代理不是聊天室中的普通发言参与者，而是具有稳定角色配置、模型、人设、技能和执行引擎的受控任务代理。

## 3. 核心需求

1. 角色可以被定义为普通聊天室参与者或子代理。
2. 子代理不能进入普通自动发言队列。
3. 子代理不能被人类或非人类角色通过普通消息中的 `@角色名` 触发。
4. 非人类角色只能通过专用子代理工具调用子代理。
5. 用户可以直接调用子代理，但消息必须严格以 `@子代理角色名 ` 开头。
6. `@子代理角色名 ` 出现在消息中段时无效。
7. 子代理每次调用都是独立任务，不读取整个聊天室历史，不复用上一次调用的会话。
8. 子代理普通文本输出不能直接成为调用结果，必须通过返回工具显式提交给调用方。
9. 子代理输出不能进入整个聊天室的后续上下文。
10. 用户直调产生的请求与结果可以显示和持久化，但必须作为预置信息隔离。
11. AI 调用子代理时，结果只返回给调用者当前的模型运行，不写入聊天室公开消息。
12. legacy `ChatRoomManager` 与新 `ChatRoomCoordinator` 必须对同一角色定义保持一致解释。
13. 旧角色、旧模板、旧消息和旧快照必须默认保持普通聊天室语义。

## 4. 严格触发规则

假设存在名为“代码审查子代理”的子代理角色。

| 输入 | 是否调用 | 原因 |
|------|----------|------|
| `@代码审查子代理 检查当前改动` | 是 | 严格位于消息开头，角色名后为 ASCII 空格，且任务非空 |
| `Xxxx。@代码审查子代理 检查当前改动` | 否 | 不在消息开头 |
| `Xxxx。 @代码审查子代理 检查当前改动` | 否 | 不在消息开头 |
| ` @代码审查子代理 检查当前改动` | 否 | 存在前导空白 |
| `@代码审查子代理\t检查当前改动` | 否 | 分隔符不是 ASCII 空格 |
| `@代码审查子代理` | 否 | 缺少固定空格和任务内容 |
| `@[代码审查子代理] 检查当前改动` | 否 | 首版不支持方括号语法 |
| `@普通助手 检查当前改动` | 否 | 目标不是子代理，继续按普通 mention 规则处理 |

## 5. 上下文与可见性

### 5.1 用户直接调用

- 用户请求和子代理结果允许显示在聊天室中。
- 两类消息均可持久化，便于用户回看。
- 两类消息都不能进入普通角色后续模型输入。
- 两类消息都不能触发普通 mention 或自动调度。

### 5.2 AI 角色调用

- 调用请求由专用工具发起。
- 最终结果仅作为工具结果返回当前调用者。
- 调用过程和结果不写入公开聊天室消息。
- 其他角色不能从聊天室历史读取该调用结果。

### 5.3 子代理执行

- 每次调用使用独立临时会话。
- 默认不读取聊天室历史和旧调用上下文。
- 最终结果必须由返回工具提交。
- 未调用返回工具应视为调用失败，而不是把最后一段普通文本当作结果。

## 6. 非目标

本轮不包含以下能力：

- 并行运行多个用户直调子代理。
- 让子代理自动参与聊天室讨论。
- 让子代理通过公开发言广播结果。
- 保存和恢复子代理自己的长期会话。
- 通过角色名称、提示词、模板名称或工具集合推断子代理身份。
- 支持用户直调时的方括号角色名语法。
- 规定子代理身份必须合并到现有参与模式或执行引擎。

## 7. 验收检查表

- [ ] 普通自动调度不会执行子代理。
- [ ] 消息中段的普通 `@子代理名` 不会执行子代理。
- [ ] 普通公开执行入口不能绕过限制执行子代理。
- [ ] 严格位于开头且格式正确的用户消息能够调用目标子代理。
- [ ] AI 角色只能通过专用工具调用子代理。
- [ ] 每次调用不读取聊天室历史或上次调用会话。
- [ ] 未通过返回工具提交时，调用明确失败。
- [ ] AI 调用结果不会出现在公开聊天室消息中。
- [ ] 用户直调请求和结果可见、可持久化，但不进入普通上下文或调度。
- [ ] legacy 与 Coordinator 的行为一致。
- [ ] 旧数据读取后仍为普通角色语义。

## 8. 已知实现约束

- 当前同时存在 legacy `ChatRoomManager` 与新 `ChatRoomCoordinator` 两套链路，方案必须覆盖两者。
- 普通 mention 当前会扫描整条消息，因此用户直调子代理必须采用独立严格协议。
- 现有 `SubAgentToolProvider` 已具备无状态调用、受控工具和显式返回工具等目标语义，应优先复用。
- `IsPresetInfo` 当前不能单独完成聊天室上下文隔离；实现必须在上下文构造、mention、自动调度和持久化恢复中执行过滤。
