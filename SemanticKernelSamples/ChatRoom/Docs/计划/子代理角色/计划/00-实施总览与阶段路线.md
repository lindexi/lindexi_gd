## 1. 先回答：方案是否真的需要很多份文档

不需要九份。

功能本身属于**中等复杂度的跨层改造**，不是一个小字段，也不是需要建设新平台的大工程。它同时影响角色模型、Mention 调度、Standard 工具、调用会话、持久化和 Avalonia，因此不能压成一张文件清单；但原草稿把设计说明、代码基线、非目标、风险、测试矩阵、文件表和提交边界在每册重复，造成文档规模远大于实现规模。

最明显的问题是：

- 同一条产品语义在总览、候选方案和多个分册重复说明。
- 同一批文件在“按序任务”“文件级改动表”“测试矩阵”“任务台账”重复列出。
- 为尚未发生的问题提前设计 execution host、ticket、revision 重基线、会话栈、聊天状态引用计数和通用 JSON shape validator。
- 把“允许自调用和环路”误读成“必须预先证明所有嵌套组合都完全可靠”。需求只是不要增加专用拒绝，不是要求先建设任意深度调用框架。
- Coordinator 尚未接入生产 UI，却被展开成比生产 legacy 链更大的首期工作面。

因此实施计划压缩为五份文档：一份总览，四份实施分册。每份文档只保留目标契约、必要代码事实、按序任务和完成门禁，不再维护独立文件台账。

这五份也不是五套设计。它们只是按实施边界拆开，便于开发时一次只打开相关文件：

- `01` 固定数据和调度语义。
- `02` 完成 legacy 生产执行链。
- `03` 开放持久化和 UI 入口。
- `04` 汇总测试、提交与验收，不再重复设计。

若只看代码实现，核心工作集中在前两册；后两册主要是产品接入和验证。

## 2. 真正的复杂点

以下复杂度不能删掉，否则会改变需求或留下真实缺陷。

### 2.1 两条架构必须解释基础语义一致

桌面产品当前使用 legacy `ChatRoomManager`，仓库同时存在未来的 Coordinator/Runtime 架构。角色和消息会进入两套模型，因此 `InvocationMode`、结构化 Mention、preset 过滤和顶层开头 Mention 不能只在一边定义。

处理原则：先完成并验证生产 legacy 链，再把已经稳定的模型、解析、调度和可见性语义映射到 Coordinator；不提前迁移 Avalonia，也不在首期为 Coordinator 建设 Standard AITool 的嵌套执行框架。

### 2.2 Mention 必须记录位置

现有解析结果只有 RoleId，无法区分消息开头和中段。新增 `StartIndex`、`Length` 和来源 MessageId 是需求直接要求，不是额外抽象。

解析器只负责报告匹配；调度器负责判断：

| 来源消息 | 目标模式 | Mention 位置 | 调度 |
|---|---|---|---|
| 非 preset | Participant | 任意有效位置 | 保持现有行为 |
| 非 preset | SubAgent | 索引 0 | 调度 |
| 非 preset | SubAgent | 非索引 0 | 不调度 |
| preset | 任意 | 任意位置 | 不调度 |

### 2.3 Standard 子代理需要正式返回值

公开文本和 AITool 返回值是两件事。`ReturnOutputToCaller`、一次提醒和第二次失败属于产品协议，不能用“取最后一段文本”代替。

### 2.4 调用间无记忆需要新的调用会话

子代理复用角色定义、执行器和 `CopilotChatManager`，但每次调用都必须使用新的 `CopilotChatSession` / `AgentSession`。同一次 Standard 调用的提醒必须复用本次会话，下一次调用不得恢复旧状态。

实现需要一个最小的“本次执行使用哪个会话”接缝，不能只依赖可变的 `SelectedSession`。但计划不预设会话栈或复杂生命周期框架，先以实际调用链测试确定最小改动。

### 2.5 preset 必须成为聊天室消息语义

只给底层 `CopilotChatMessage` 设置 `IsPresetInfo` 不足以阻止后续角色读取和 Mention 调度。外层 `ChatRoomMessage` 必须保存该字段，并由调度、上下文和持久化共同执行过滤。

## 3. 应删除的过度设计和过度防御

实施时明确不预先建设以下能力：

- 不新增子代理专用 runtime、invoker、命令体系或 UI 事件。
- 不新增 invocation stack、最大深度、环路检测、自调用拒绝或父子取消树。
- 不因“可能自嵌套”预先重写 `CopilotChatManager.IsChatting`；只有测试证明通用状态错误时才修复根因。
- 不预先设计 Coordinator 的 execution host、execution ticket、公开输出候选层次或 checkpoint revision 新框架；首期只实现顶层执行可以表达的语义。Coordinator 内部 Standard AITool 调用作为后续独立工作，只有生产入口迁移或明确要求时才展开。
- 不建立跨三种格式的大型通用 JSON 验证框架；各加载入口先验证版本，再依赖 DTO 和领域模型做必要字段与枚举校验。
- 不为每个步骤维护反向任务台账、风险台账和重复文件表。
- 不为“只修改 InvocationMode”顺手重新分类所有角色字段；只保证该字段不触发 runtime replacement，其他字段保持现状。
- 不修改 Coding 执行链，只在普通执行入口读取其现有完成结果。

## 4. 固定产品语义

### 4.1 正交角色字段

```text
ParticipationMode : 普通参与者何时进入自动队列
ExecutionKind     : Standard 或 Coding
IsManagerRole     : 普通自动循环中的管理者身份
InvocationMode    : Participant 或 SubAgent 的触发方式
```

`InvocationMode` 不推断或改写其他字段。SubAgent 不进入默认队列和管理者兜底，但显式执行入口仍可执行它。

### 4.2 子代理调用

- Mention 路径和 AITool 路径最终都复用普通角色执行能力。
- 子代理只接收本次任务文本，不读取聊天室历史、调用者会话或旧调用会话。
- Standard 必须调用 `ReturnOutputToCaller`；第一次未提交时提醒一次，第二次失败。
- Coding 使用现有完成结果，不注入 Standard 返回工具。
- 子代理原始输出仍是普通 Assistant 消息，并设置 `IsPresetInfo = true`。
- preset 消息可见、可保存，但不进入其他角色上下文，也不参与 Mention 调度。
- 子代理本次 checkpoint 可以保存；下一次调用不恢复它。

### 4.3 明确不修改

- `AgentLib/Tools/SubAgentToolProvider.cs`
- `AgentLib/Model/CopilotChatSubAgentItem.cs`
- `AgentLib.Coding/CodingAgent.cs`
- `AgentLib.ChatRoom/CodingChatRoomRoleExecutor.cs`
- AgentLib.Coding 的现有工具与子代理机制

AgentLib 只允许增加通用的默认工具按名称排除能力，不得引用 ChatRoom 类型。

## 6. 四个实施阶段

### 阶段一：模型与调度

完成：

- legacy/Domain `InvocationMode`。
- 结构化 `ChatRoomMention`。
- 消息 `IsPresetInfo` 与 `Mentions`。
- legacy/Coordinator 共用现有 Mention 语法。
- 默认队列、管理者兜底、Mention 和上下文过滤。

阶段门禁：普通 Participant 行为无回归；Human/Assistant 开头 Mention SubAgent 均能被调度；中段和 preset 不调度。

### 阶段二：执行与工具

完成：

- 通用 Step/runtime 调用选项。
- ChatRoom Standard 排除 AgentLib 默认 `InvokeSubAgent`。
- `InvokeChatRoomSubAgent` 与 `ReturnOutputToCaller`。
- 每次调用新会话、同次提醒复用会话。
- Standard 一次提醒；Coding 读取现有完成结果。
- legacy 生产链完整可用。

阶段门禁：连续两次调用不共享聊天历史；父 Standard AI 能获得工具结果继续当前轮；不修改 Coding 执行器。Coordinator 内部 AITool 调用不属于本阶段门禁。

### 阶段三：持久化与 UI

完成：

- legacy 配置、角色模板和 snapshot 格式版本升级。
- 新字段往返和旧版本拒绝。
- 恢复时 preset 传播到底层消息。
- 角色编辑、类型标签、菜单和 Mention 插入位置。
- 发送时保留前导空白。

阶段门禁：新格式往返通过；子代理 Mention 从 UI 插入到索引 0；消息模板无分叉。

### 阶段四：回归与文档

完成：

- 分层测试和完整构建。
- README 使用说明。
- Git 差异检查禁止修改范围。
- 区分既有 Coding 测试失败和本次回归。

## 7. 实施原则

1. 先用测试固定现有 Mention 语法，再替换 RoleId-only 结果。
2. 先完成 legacy 生产语义，再把同一语义带到 Coordinator。
3. 优先扩展现有 `StepAsync` / runtime request，不新建第二套子代理执行链。
4. 只增加实现当前需求所需的通用接缝；若一个抽象只被单个调用点使用且不能降低复杂度，就不新增。
5. 不把旧字段和新字段长期双写。
6. 不把普通文本当作 Standard 正式返回值。
7. 不通过关闭全部默认工具来排除 `InvokeSubAgent`。
8. 不因 `InvocationMode` 改写 `ParticipationMode`、`ExecutionKind`、`IsManagerRole` 或 `IsHuman`。
9. 每阶段结束运行目标测试和解决方案构建，不等待最后统一修复。

## 8. 完成定义

- 开头 Mention 和 Standard AITool 都可调用 SubAgent。
- legacy 完成 Mention 与 AITool 两种调用；Coordinator 完成基础模型、调度和顶层 Mention 一致性。
- Standard 返回协议严格执行一次提醒；Coding 链路保持现状。
- 子代理调用内有状态、调用间无记忆。
- 子代理输出正常展示和持久化，但不会污染后续上下文或调度。
- 三套持久化格式只接受当前版本。
- Avalonia 可配置和正确触发子代理，不增加专用消息模板。
- 禁止修改文件无差异，相关构建和测试通过。
