# ChatRoom 子代理角色方案三探索过程：独立子代理注册表

## 1. 探索目标

验证是否应从模型层彻底分离普通聊天室角色和子代理，以天然满足普通调度无法触达子代理的要求。

## 2. 初始假设

如果房间分别维护普通参与者和子代理集合，普通自动调度、普通 mention 和公开执行入口只读取普通集合，就可以降低遗漏过滤条件的风险。

## 3. 调查依据

当前项目同时存在 legacy `ChatRoomManager` 与新 `ChatRoomCoordinator`。角色定义还被以下能力共同使用：

- 角色模板与角色大厅。
- 模型、人设和技能配置。
- Standard/Coding 执行引擎与 Coding 工作区。
- Avalonia 角色编辑和角色列表。
- legacy JSON 与新 snapshot 持久化。
- 角色动态更新、删除和运行时注册。

因此建立独立子代理注册表，不只是新增一个集合，还需要决定这些共享配置是复制、抽取还是建立新的公共基类。

## 4. 推导过程

### 4.1 边界收益

普通参与者与子代理从模型层分离后，普通调度天然不会枚举子代理。未来也可以分别设计生命周期、权限、资源限制和发现机制。

### 4.2 首版成本

为了支持现有角色能力，独立子代理模型需要重新承载或复用大量配置。两套聊天室架构还要分别增加集合、注册表、命令、持久化和 UI 流程。

### 4.3 迁移问题

必须额外定义：

- 普通角色转为子代理时是否保留稳定身份。
- 子代理转回普通角色时如何迁移历史和模板。
- 旧数据如何判断对象属于哪个集合。
- 两套集合中的名称唯一性和引用关系如何处理。

这些问题超出了首版“增加受控子代理调用语义”的必要范围。

## 5. 探索结论

该方案长期边界清晰，但会把当前功能演变为角色系统结构性重构。现阶段统一角色定义仍能复用稳定身份、人设、模型、技能和执行引擎，只需增加正交调用模式即可满足需求。

当前结论：首版暂不推荐。

## 6. 重新评估条件

出现以下变化时应重新评估：

- 子代理拥有明显不同的生命周期或部署方式。
- 子代理权限、资源治理或配置项与普通角色大幅分化。
- 普通角色与子代理不再需要互相转换。
- legacy 架构退出，角色模型可以进行集中重构。
