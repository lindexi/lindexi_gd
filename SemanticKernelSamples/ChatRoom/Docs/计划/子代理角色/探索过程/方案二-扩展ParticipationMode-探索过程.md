# ChatRoom 子代理角色方案二探索过程：扩展 ParticipationMode

## 1. 探索目标

验证能否用最小模型改动，把子代理身份直接加入现有 `ParticipationMode`，同时满足[需求功能](../ChatRoom-子代理角色需求功能.md)。

## 2. 初始假设

现有参与模式已经影响自动调度和 mention 行为。如果增加 `SubAgentOnly`，可能以较少改动阻止子代理作为普通角色参与聊天室。

## 3. 调查依据

现有系统同时存在以下独立维度：

- `AlwaysParticipate` 与 `MentionOnly`：普通聊天室中的参与时机。
- Standard 与 Coding：角色执行引擎。
- 管理者身份：自动循环的兜底和仲裁身份。
- 普通执行入口：可以绕过 mention 调度直接执行角色。

子代理需求还要求严格用户前缀、专用 AI 工具、无状态临时会话、返回工具协议和上下文隔离。这些行为无法由参与模式枚举单独提供。

## 4. 推导过程

### 4.1 可复用部分

`SubAgentOnly` 可以成为自动调度、普通 mention 和部分 UI 配置的过滤条件，因此表面改造成本较低。

### 4.2 无法覆盖的部分

即使增加 `SubAgentOnly`，仍需修改公开直接执行入口，防止调用者绕过调度过滤；仍需独立的严格用户解析器、子代理 invoker、返回工具和上下文隔离。

这说明“何时参与普通聊天室”和“允许通过何种协议调用”并不是同一个维度。

### 4.3 非法组合风险

- `SubAgentOnly + IsManagerRole` 的管理者语义不清晰。
- 将角色从 `MentionOnly` 切换为 `SubAgentOnly` 会同时改变身份与调用权限。
- 未来新增其他受控调用方式时，需要继续扩展参与模式。

## 5. 探索结论

该方案技术上可行，但最少新增字段并不等于最少长期复杂度。它会把调用协议塞入普通参与策略，增加模型语义债务和防御性检查遗漏风险。

当前结论：不推荐。

## 6. 重新评估条件

满足以下条件时可重新评估：

- 团队明确将子代理定义为普通参与模式的一种。
- 未来不会增加其他独立调用协议。
- 接受参与模式变化同时改变角色身份与调用权限。
- 能为所有直接执行入口建立统一且可验证的保护。
