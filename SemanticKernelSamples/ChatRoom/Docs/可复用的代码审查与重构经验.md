# 可复用的代码审查与重构经验

## 阅读目的

本文总结适用于长期维护的软件项目的代码审查、重构、测试和问题调查方法。读者不需要了解任何特定项目。

核心要求是：依据实际代码和业务契约设计，保持职责清晰；不为假设增加防御，不用补丁掩盖结构问题，不把测试通过等同于设计正确。

## 1. 用实际证据驱动修改

### 不把理论可能性当作实际问题

“集合可能被修改”“操作可能并发”“服务可能不支持”只是语言或系统层面的可能性，不自动构成新增机制的理由。

增加快照、锁、兜底、探测或状态检查之前，应至少有一种依据：

- 明确的业务需求或公共 API 契约。
- 实际调用链确实允许这种行为。
- 可复现的问题、性能数据或外部依赖的真实限制。

例如，只读集合接口不保证底层不可变，但如果调用链已经独占该集合且不会修改，再复制一次通常没有收益。集合复制也只是浅拷贝，不能被描述为整个输入对象都不可变。

### 修复前先复现

面对偶现问题，先建立可控测试，记录操作顺序、等待点、异常和状态，不猜测根因后直接修改。

- 使用明确的同步信号控制时序，避免依赖随机延迟。
- 区分“请求尚未开始”“已有部分输出”“执行中”“正在收尾”等实际时间点。
- 未复现时明确测试覆盖边界，不把“测试通过”写成“问题不存在”。
- 已复现时保留回归测试，再修复。

暂停问题也是合理决定：记录事实、未覆盖时序和后续调查入口，不继续引入猜测性改动。

## 2. 新代码需要立即打补丁时，先审查结构

功能刚接通就需要增加特判、默认兜底、创建委托或额外包装，通常值得重新检查对象职责。

不要仅问“怎样让这行代码工作”，还要问：

1. 这个对象应该知道具体实现类型吗？
2. 谁拥有对象，谁决定创建和释放？
3. 配置是否有唯一装配入口？
4. 是否出现两条行为不同的默认创建路径？
5. 当前抽象是否真正被消费者使用？

修复结构问题可以推倒刚写的代码，而不是因为已经写好就继续叠加。

创建委托、延迟包装、多态都不是天然错误。错误在于没有真实职责依据，只把它们用作掩盖原有设计缺陷的接缝。

## 3. 让生命周期与所有权清楚可见

组合根负责配置与装配，运行协调者负责业务操作，对象所有者负责创建、复用和释放。

- 可复用对象的延迟创建应位于其明确的所有者中。
- 不使用某项能力时，不应无条件创建它的专用对象。
- 延迟创建后需要跨操作保留状态的对象，应复用而非每次重建。
- 不让协调者同时承担实现选择、具体对象构造和协议执行。
- 不为测试方便而在生产 API 增加无业务意义的默认装配路径。

共享资源类型或租约只有在实际共享和生命周期约束需要时才成立。不能因为设计图出现了某个名称，就先创建类型，而消费者仍各自持有资源。

“重置状态”与“结束旧操作”也不同。旧操作仍可能在 finally、回调或保存流程中修改对象，仅清空字段不等于安全重启。涉及旧操作与新操作隔离时，应单独定义语义和测试，不先实现复杂的重启框架。

## 4. 参数和配置属于真正使用它们的层

如果底层方法为了接收配置不得不展开大量参数，应检查配置类型是否错误地放在上层。

- 与执行有关的选项放在对应执行层。
- UI 文案、控件状态不进入执行选项。
- 通用基础库不承担只属于某个领域的配置。
- 取消令牌通常放在参数列表最后。
- 参数顺序应体现主要依赖和输入，不将核心执行对象藏在末尾可选参数中。

参数过多时，按实际内聚性选择解决方式：

- 少量真正共享的选项使用一个选项类型。
- 单次执行依赖和复杂循环可放进专用执行对象。
- 对象初始化使用具名属性，比长位置参数列表更容易审查。
- 必须赋值的初始化属性可使用 `required` 与 `init`。

参数容器只有一个消费者，且没有独立职责时，可以直接合并到执行对象。局部函数适合短小且紧密关联的逻辑，不应用来隐藏不断扩张的执行流程。

## 5. 统一行为契约，不在公共结果中识别具体实现

公共运行结果可以表达消息、完成任务及运行操作，但不应持有多个具体执行器，再通过条件判断选择行为。

有真实多实现需求时，可以使用接口和具体实现，让调用方只调用统一操作。只有数据和完成任务的消费者不需要了解执行协议。

注意以下基础规范：

- C# 接口名称使用 `I` 前缀，类型名、文件名和引用同步调整。
- 能明确使用具体类型的装配和持有位置，不必统一改成接口。
- 接口用于确实需要的行为契约或外部依赖，不为每个类创建接口。
- 不包装已经足够表达需求的抽象。
- 有可变状态和活动生命周期的对象通常使用普通类，而不是默认使用 record。
- record 主构造函数会生成属性；不需要这些属性和值相等语义时，使用普通构造函数和私有字段。
- 枚举和关键状态类型应有文档注释，说明业务含义与生命周期，而不只是翻译名称。

## 6. 协议状态与展示状态分离，但不建立第二套业务管理

展示内容与后续执行所需的结构化状态不是同一件事。

- 原始状态由对应执行机制持续维护。
- 展示模型负责渲染，不成为每次运行重建原始状态的数据源。
- 同一业务实体拥有其状态，避免在上层执行适配器中另设长期字典代管生命周期。
- 恢复只发生在明确的存储初始化入口，不在正常执行中自动从其他模型推导。
- 保持原始顺序、标识和扩展字段，不能只保存可读文本。

这对依赖稳定请求前缀、缓存或不透明状态的系统尤为重要。重新拼接内容可能改变语义和成本。保存恢复也不能保证远端缓存仍有效，应分别说明。

服务端状态转换成功时，应按该机制应用完整原生结果；失败、取消或解析失败时保留旧状态。是否允许回退是业务契约，不由客户端偷偷决定。

## 7. 状态通知必须覆盖完整业务状态

只根据某个阶段字段变化发通知，可能漏掉其他影响界面的字段变化。

典型表现是：直接读取属性已经正确，UI 最后收到的通知却仍表示运行中。

设计要点：

- 用完整业务状态统一推导按钮文字、可见性和命令可用性。
- 所有状态更新通过一个入口发布。
- 最外层操作负责开始和结束；内部步骤只推进状态，不能提前宣布整个操作空闲。
- 清理取消源及必要收尾后，再发布最终空闲状态。
- 用户的“是否继续”选项与“操作是否仍活动”不能混为一谈。

状态表达应足够但不过度：如果两套枚举高度重叠，并产生大量无意义组合，可合并为单一业务状态枚举。只有真正独立的维度才适合正交建模。

测试不仅检查最终属性，还应检查最后一次属性通知、命令通知所反映的值，以及保存期间是否提前开放冲突操作。

## 8. 边界处理按业务顺序设计，不追求不存在的极端保证

请求执行期间新增输入，可以在下一处理边界消费队列，不一定需要取消重发、迁移状态或复杂同步。

- 在明确边界统一消费，并保持顺序。
- 当前业务允许的并发队列已经足够时，不额外添加锁。
- 不为未经证明的极端时序引入重试、事务或防丢机制。
- 展示消息追加应针对所属业务实体，而不是依赖可能变化的全局当前选择。
- 新增路径应核对既有路径实际做了什么，不能假设某个底层调用同时完成了展示、日志和存储。

不同处理顺序可能改变用户体验和成本，应由需求明确，例如新输入是否优先于昂贵的后台整理工作。

## 9. 外部兼容问题先隔离复现，再处理

异常堆栈只是调查线索，不足以直接归因。

按顺序缩小范围：

1. 捕获实际请求与原始响应，避免记录凭据。
2. 定位具体字段和失败时机。
3. 使用官方模型读取入口建立最小本地复现。
4. 绕过业务层，以最小真实请求排除提示词、历史、工具和记录器的影响。
5. 确认实际加载的依赖版本，而不只检查项目文件。

外部 SDK 有原生序列化能力时应优先使用，不先用反射、私有访问或手工字段重组。

若需求明确接受某个已知异常，应限定处理范围并记录损失：不能捕获所有异常冒充成功，不能伪造缺失用量，也不能从展示文本制造原生结果。版本变更必须重跑最小复现，不能假定升级或降级必然有效。

诊断记录器也可能改变现场：完整缓冲响应会改变流式和取消时序，因此不能把诊断用缓冲悄悄用于所有测试。

## 10. 集成测试应模拟真实业务入口

通过界面命令、附件集合、路径应用、历史存储入口测试，能覆盖比直接调用客户端更多的业务行为；但不能称为鼠标键盘端到端自动化。

建议覆盖：

- 连续操作及上下文保留。
- 配置选择真正进入请求。
- 本地工具实际执行，结果标识与调用标识对应。
- 操作取消后的收尾及后续操作。
- 保存后释放旧运行对象，重新初始化并从磁盘恢复。
- 状态转换期间的通知和命令可用性。

测试名称表达行为，厂商、模型和端点集中配置，不用供应商名称限定测试职责。真实测试缺少凭据时的行为遵循项目约定，不擅自改变。

模型测试还应注意：

- 模型只能看到输入，不知道客户端做了什么恢复或重启动作。
- 问题应询问上下文事实，不要求模型理解客户端生命周期。
- 测试任务与应用定位一致，减少系统提示词造成的歧义。
- 需要逐字输出时明确格式和大小写，而不是事后放宽断言。
- 附件被发送与内容被正确理解是两种证据，不能混为一谈。
- 暂缓的语义测试可以标记忽略并写明原因，不能直接声称能力通过。

## 11. 报告验证结果时保持边界准确

- 编译通过不等于没有设计问题或符合规范。
- 定向测试通过不等于全量回归通过。
- 一次真实服务成功不保证所有输入、版本和端点均有效。
- 缺少原始终态、用量或响应字段时，明确说明缺失。
- 环境失败、外部依赖失败、业务断言失败分别描述，不混写为代码修复成功。
- 文档应标明当前事实、历史实验和未完成项，避免互相矛盾。

## 12. 界面问题检查真实布局，不靠视觉猜测修补

- 同一选项组的字号、命中区域、标记和对齐应一致。选中状态不能只靠颜色表达，键盘焦点也必须可见。
- 自定义模板应检查主题选择器和模板部件名称，避免继承不符合预期的悬停背景等样式；不要靠不断叠加样式隐藏冲突。
- 区分控件外边距、内部留白和内容元素的外边距。移动滚动容器可能同时移动滚动条，不能只看正文位置是否改善。
- 裁剪问题需比较视口、内容容器、实际输出控件和内部文本排版的宽度。外层容器正确不代表子控件没有越界。
- 区分无限测量、错误排列宽度和真正的换行问题，不先给控件加固定最大宽度。
- 用户内容与系统输出使用不同布局时，应分别验证；一类内容正常不能证明另一类正确。
- 用窄窗口、长文本和实际控件边界测试复现，不只断言静态 Margin/Padding 值；自动化布局测试通过后仍需说明人工视觉验收范围。

## 自审清单

提交修改前逐项检查：

1. 每项新增机制是否有真实需求、契约或复现证据？
2. 有没有为了接通新功能给公共类型增加具体实现特判？
3. 创建、复用、释放及配置来源是否明确且唯一？
4. 参数类型是否位于正确层，取消令牌是否位于最后？
5. 抽象是否有消费者，参数容器是否有独立职责？
6. 接口、文件、枚举注释等基础规范是否完整？
7. 是否通过展示内容重建了本应原生维护的状态？
8. 通知是否反映完整状态，内部步骤是否提前结束外层操作？
9. 测试是否覆盖实际入口、取消收尾、磁盘恢复及通知值？
10. 报告是否准确区分已通过、忽略、失败和未验证？

## 本文可迁移性自审

- 未引用特定项目的类型、目录、供应商或业务名称。
- 示例均为通用软件开发概念，不需要额外项目背景。
- 没有把一次具体实现选择提升为绝对规则；抽象、复制、锁、委托等均以真实职责和证据为判断依据。
- 区分协议事实、测试证据、允许的业务取舍和未知因素。
- 可直接用于其他项目的审查清单、开发规范讨论及重构评估。
