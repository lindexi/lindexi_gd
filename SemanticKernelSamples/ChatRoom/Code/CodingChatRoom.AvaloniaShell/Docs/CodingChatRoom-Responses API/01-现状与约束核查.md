# 现状与约束核查

## 当前调用链

当前每个工作任务拥有独立 `CodingChatRuntime`，组合根创建：

- `AgentApiEndpointManager`
- `CopilotChatManager`
- `CodingAgent`
- `CodingAgentChatRunner`
- `CodingChatApplication`
- `CodingWorkspaceController`
- 会话存储与设置服务

发送链为：

```text
ChatViewModel.SendAsync
  → CodingChatApplication.SendMessageAsync / RunLoopIterationAsync
  → ICodingChatRunner.RunAsync
  → CodingAgentChatRunner
  → CodingAgent.RunAsync
```

聊天页已经支持模型、思考强度、图片、自动压缩、循环迭代、`dotnet run`、停止和 LSP 停止。

## 当前可复用资产

### 消息与展示

`CopilotChatMessage` 已能承载：

- 文本增量；
- 推理文本；
- 图片与音频；
- 工具调用及结果；
- Token 用量；
- 审批与子智能体展示。

这足以作为两种协议共同的 UI 投影模型。Responses 的协议 Items 不应直接绑定 Avalonia 控件。

### 编程工具

`CodingWorkspaceCache` 已集中构造：

- Roslyn 符号工具；
- 工作区文件工具；
- .NET build/test/publish 工具；
- 可选 `dotnet run`；
- 图片读取；
- 附加工具源；
- `ToolRegistrationRegistry` 展示摘要。

工具实现成熟，但缓存和运行上下文目前是 `CodingAgent` 私有实现，Responses 分支若直接复制会产生长期双维护问题。

### 配置

当前 `OpenAIProtocolLanguageModelConfiguration` 已包含 `EndPoint`、`Key` 和模型列表；`ILanguageModel` 只公开 `GetChatClientAsync`。Responses 改造需要在不改变设置文件的前提下，从现有 OpenAI 协议模型对象取得创建 `ResponsesClient` 所需的端点、凭据和模型信息。远端是否实际支持 `/responses` 由真实请求结果确认。

### 持久化

当前 XML 格式保存：

- 可见聊天消息；
- 工作区路径；
- 单个 `AgentSessionState`。

Responses 的 `response_id`、`conversation_id` 和协议恢复信息没有存储位置。只保存可见消息不能恢复完整 reasoning/tool context，也不能发挥服务端续接能力。

## 已确认的耦合点

`ICodingChatRunner` 已是良好薄边界，但 `CodingChatApplication` 仍直接依赖 `CodingAgent` 处理 LSP 停止和压缩相关判断；`CodingChatRuntime` 也直接拥有并释放 `CodingAgent`。因此不能只替换 `ICodingChatRunner` 后声称完成双路径。

## 不可接受方案

1. 修改 `CodingAgent` 内部使其根据布尔值切换协议。
2. 将 `ResponsesClient` 适配为 `IChatClient` 后继续走 `ChatClientAgent`。
3. 复制 `CodingWorkspaceCache` 和全部工具到 Shell。
4. 让两个执行引擎共享同一个协议会话状态。
5. 为 Responses 新增设置界面、设置字段或能力开关。
6. 只实现文本流和单轮请求，却宣称“第一等支持”。
7. 用“暂不支持恢复/工具/推理摘要”掩盖目标结构缺失。

## 设计输入结论

目标结构必须同时满足：

- 两条完整执行分支；
- 一个共享工具资源内核；
- 两套独立协议状态；
- 一个共同 UI 消息投影；
- 复用现有模型配置且不修改设置逻辑；
- 向后兼容的会话文件扩展；
- `AgentLib` 公开 API 零破坏；`AgentLib.Coding` 允许必要的破坏性重构。
