# 会话状态与持久化

## 状态模型

会话文件继续保存现有字段，并增加可选 Responses 协议状态：

```text
ChatCompletionsState
- 现有 AgentSessionState

ResponsesState
- ModelId
- ConversationId（使用 Conversations 时）
- PreviousResponseId
- StoredOutputEnabled
- 继续上下文所需的本地 Responses Items（不因请求 store=true 而省略）
```

可见消息用于展示历史；协议状态用于继续 Responses 上下文。两者职责不同。

## 续接策略

客户端维护并显式提交续接所需的原生历史，包括用户输入、模型输出、相关工具调用、工具结果及推理信息。不能从 UI 纯文本反推协议历史，也不因请求 `store:true` 就删除本地上下文。

显式历史路线直接提交历史与新增 Items，不同时依赖 `PreviousResponseId` 自动补齐历史。需要使用该字段时，其值来自上一轮返回的 `id`，不是上一轮返回的 `previous_response_id`；不能仅凭请求参数认定服务端状态续接已生效。

历史选择应保证上下文语义完整，不等于永久无限重传全部历史。压缩、裁剪和跨进程恢复另行设计，不增加自动探测、失败后补传或新配置字段。

### 提示词缓存

- 固定 Instructions、工具定义与历史前缀的内容和顺序，在末尾追加新输入和模型原生输出；不要为每轮请求在前缀插入随机时间或变动标识。
- 显式发送历史与提示词缓存并不冲突：客户端仍发送上下文，服务端可复用相同前缀的计算。
- 从 `usage.input_tokens_details.cached_tokens` 读取命中 token 数；单轮命中率为 `cached_tokens / input_tokens`，输入为零时不计算比率。
- 多轮汇总比率使用累计 cached tokens 除以累计 input tokens，不对单轮百分比作简单平均。
- 映射至消息已有 `CachedInputTokenCount`，当前值与累计值分别维护；缺少缓存明细时不能宣称已经命中。
- `store` 控制响应存储请求，不是缓存开关；`prompt_cache_retention` 表示提示词缓存保留策略，不是对话历史保存时长。
- 缓存命中受最小前缀长度、路由和保留策略影响，不保证每轮必然命中，不为提高命中率篡改业务上下文。

以下持久化内容仍为后续设计，当前实验未实现协议状态保存恢复。

## 分支状态边界

- CodingAgent 分支只读写现有 `AgentSessionState`；
- Responses 分支只读写 `ResponsesState`；
- 两种状态使用不同节点和编解码器；
- 不实现协议迁移、运行中切换、回切检测或自动回退。

Responses 分支首次运行时只以本轮文本和图片建立 Responses 上下文，不迁移已有 CodingAgent 协议状态。

## XML 兼容扩展

保持现有根元素、消息节点和 `AgentSessionState`，新增可选节点：

```xml
<ProtocolStates>
  <ResponsesState>...</ResponsesState>
</ProtocolStates>
```

规则：

- 旧文件无该节点时正常加载；
- 新文件保留现有节点语义；
- 格式版本递增，读取器继续支持旧版本；
- response/conversation id 可以保存；
- API key、Authorization 和完整原始请求不得保存。

`CopilotChatSessionPersistenceData` 通过可选协议状态承载 Responses 数据，原属性和公开 API 保留。

## 保存时机

复用现有会话保存流程，不新增原子替换、写前日志、双文件提交或高频运行检查点：

- 一轮 Responses 运行完成、失败或取消后，内存状态与可见消息一起进入现有保存流程；
- 完成本地工具批次后先更新内存状态，不对每个文本 delta 或 streaming event 写磁盘；
- 用户执行现有的新建、切换、关闭等会触发保存的操作时，按现有机制保存最新状态；
- 如果现有文件存储本身已采用临时文件替换，可继续复用，但本方案不要求为 Responses 新增该机制。

该设计保持状态一致性和代码可读性，不为极低概率异常退出恢复引入额外持久化状态机。

## 删除

删除会话沿用现有本地删除语义。本方案不增加远端 conversation/response 清理流程；服务端数据保留遵循所使用 API 与账号策略，不让本地删除依赖额外网络操作。
