- 已否决并删除 `CodingWorkspaceRuntime` / `CodingWorkspaceRunLease` 设计，不恢复这两个类型。Responses 引擎直接复用 CodingAgent 既有工作区工具获取方法；工具本体、缓存及资源所有权保持不变。
- 新增 `ResponsesCodingAgent`，通过模型的 `IResponsesClientProvider` 使用原生 SDK，流式事件提交消息 `ResponseInfo`，本地工具调用复用 `ResponsesToolHelper`。
- `CopilotChatSession.ResponsesSession` 延迟持有 AgentLib 的 `CopilotResponsesSession`，替代 Coding 层的列表容器及 Shell 历史字典。正常运行持续追加原生输入、响应输出及真实工具结果，既有 SDK 对象不重新组装；不使用 `PreviousResponseId` 拼接历史。
- 本轮不接入手动上下文的 `DefaultTools`，不引入其中的子代理工具；审批工具和子代理工具的注册由后续专项处理。不得将带审批的函数当作普通工具注册以绕过审批。

- `CodingWorkTaskRuntime` 持有执行分支及提示词路径，首次访问 Responses 分支时直接创建并复用 runner，不注入创建委托。`ChatViewModel` 在入口读取开关并取得 runner，显式传给 Controller；循环沿用入口传入的实例。Controller 不装配 Responses、不判断协议；运行选项只承载执行配置。原生历史归属现有会话对象，Shell runner 只传递该实例，不独立管理会话历史。
- 内存 HTTP + 真实 SDK 的多轮历史及函数工具闭环测试继续保留；新增 Shell 分支选择测试。尚未执行真实端点验收。
- 已接入现有会话存储，格式版本 3 的可选 `ProtocolStates/ResponsesState` 保存有序原生 Item JSON；保存普通 Chat 不创建 Responses 状态，旧文件缺失节点不从展示历史补建。仅加载存储初始化时反序列化并挂到会话，正常发送及内存切换禁止从 ChatMessages、ResponseInfo 或 AgentSession 恢复/重组历史。

## Responses 请求边界插话

- 活动运行通过 CodingAgentRunResult.InjectMessageAsync 将插话转换为原生用户 Item 并排队，不取消当前请求，不从展示内容重建历史。
- 本地工具批次执行完后追加待处理用户 Items；无本地工具时也检查队列，有插话则继续请求，否则完成。多条插话保持入队顺序。
- Shell Responses runner 持有本次活动运行并转发插话，追加可见用户消息及日志；结束时清理活动引用。原生历史仍由会话持有。
- 这不是向服务端正在生成的响应即时注入，而是在下一请求边界生效。
- 无工具终态、工具续轮的两条插话顺序测试通过；真实服务 ViewModel SendCommand 运行中再次发送测试通过，回答包含插话标识并显示用户插话消息。取消、消息注入的旧 CodingAgent 相关回归测试通过。

## 新建会话状态刷新专项（暂缓，不阻塞 Responses 主线）

### 用户反馈与复现边界

用户反馈偶现：响应尚未结束时点击停止，随后发送无效果；新建会话后再次发送，用户内容未出现，但界面进入插话/停止状态。

已用内存 HTTP 和真实 Responses SDK、Agent、runner、Controller 验证两种停止时机：等待响应头，以及已接收部分文本但流未完成。测试在等待取消收尾后执行同会话发送、新建会话再发送，均通过，未复现用户反馈。尚未覆盖停止后未收尾即通过 UI 命令立即发送/新建的时序。此前偶现问题暂时搁置，不认定根因，不做猜测性修复。

### 当前代码调查事实

- `CodingWorkTaskController.CreateNewSessionAsync` 调用 `EnsureCanChangeSession`；活动运行、循环或收尾期间拒绝新建。`SessionListViewModel.CreateNewSessionCommand` 同样受 `CanChangeSession` 限制。
- `CopilotChatManager.CreateNewSession` 只创建或复用空会话并切换选择，不取消任务，也不重置 `IsChatting`。
- Controller 的活动取消源、运行阶段、循环启用/活动状态不会因新建会话主动刷新；正常发送每次创建新的操作取消源，旧源由旧运行退出时清理，并非所有发送共用一个已取消的令牌。
- CodingAgent runner 的活动运行引用由旧运行完成时清理；任务级 Agent、runner 和工作区工具继续复用。
- ViewModel 切换会话重新绑定展示消息，不重建任务运行对象。协议历史归属目标会话，不发生跨会话恢复或迁移。

这些事实表明当前新建会话是数据切换入口，不是运行状态重启入口；不证明它是此前偶现问题的根因。

### 后续专项目标与待决事项

预期新建对话是类似重启的逃生通道，用于刷新运行状态，即使旧运行卡住也应能恢复使用。新建对话与打开历史会话的权限和行为需要分别设计。

- 明确取消旧操作后等待收尾的正常重置，与不等待卡住操作的逃生重启之间的语义区别。
- 核查旧运行的 finally、聊天作用域释放、保存和状态通知如何与新运行隔离。禁止仅清空字段或强设 Idle/IsChatting=false 掩盖仍存活的旧操作。
- 评估新运行协调对象的生命周期及旧操作资源退出方式；目前没有批准或实现新的对象隔离/重建架构。
- 保留任务配置、模型选择和工作路径，新对话不继承旧协议历史；旧运行保存仍针对旧会话。
- 继续遵守原生 Responses 历史约束：正常运行不从展示或 Chat 状态重建，仅存储初始化允许恢复。
- 实施前先建立可控的 UI 命令与旧运行延迟收尾测试，验证旧操作完成后不会干扰新对话。

本专项只记录调查与预期，本轮不修改新建会话、取消、运行协调或按钮可用性，优先保持 Responses API 对接主线。

## 接入职责

Responses 调用方只处理工具定义、参数、异步调用和结果。复用已有 AIFunction 实例，不分析子代理内部协议，不接管审批。子代理可以采用任意实现；对调用方仍是一次工具调用。

审批应在工具 InvokeAsync 内等待，批准后执行，拒绝返回失败结果。协议适配层不应负责将“不执行审批”的工具转换为“执行审批”的工具。下面的既有问题单独重构，不在 Responses 辅助方法中增加兜底。

## 已确认的审批问题

位置：AgentLib/Tools/HumanApprovalTool.cs。

- ConfiguredHumanApprovalFunction.InvokeCoreAsync 直接调用内部函数，绕过审批；代码明确依赖外部 BindRuntimeTool 才获得审批行为。
- RuntimeHumanApprovalFunction 的确会 await WaitForApprovalAsync，拒绝时不执行内部函数，但 chatContext 缺失、未创建审批项时仍会直接执行。
- 因此“拿到包装后的 AIFunction，调用就会经过审批”目前不成立。这是原审批实现的封装缺陷，不是 Responses 适配职责。
- 链接取消源创建后未释放，也是该专项的生命周期问题。

后续应先重构审批工具的独立调用契约，再接入协议执行路线。不得让适配器通过识别包装器或补建 Chat 上下文掩盖缺陷。

## 子代理核查

位置：AgentLib/Tools/SubAgentToolProvider.cs。

- 对外通过 AIFunctionFactory 包装 InvokeSubAgentAsync，参数是任务、系统提示词与选择条件，返回 Task<string>。
- 内部使用 IChatClient/ChatClientAgent 是当前实现选择，不要求父调用方使用相同协议；没有理由让 Responses 转换逻辑识别子代理类型或迁移其内部模型调用。
- chatContext 可为空；为空时跳过子代理进度展示，仍执行任务并返回收集结果。因此当前任务入口不强制要求父级 Chat 协议。
- 既有缺陷：InvokeSubAgentAsync 不接受本次调用的 CancellationToken，执行使用注册时捕获的 _cancellationToken。手动上下文创建默认工具时没有传入执行令牌，因此外层 AIFunction.InvokeAsync 的取消不一定传至子代理内部。后续在子代理专项修复，不由协议转换层捕获令牌补救。
- 既有耦合：进度展示直接依赖 CopilotChatContext，需与业务调用契约分开审视，不为此要求父代理采用 Chat 协议。

## 图片结果的 SDK 表达核查

AgentLib 已显式引用 OpenAI 2.14.0，不再依赖传递解析的 2.10.0。已核对 2.14.0 公开 API：FunctionCallOutputResponseItem.FunctionOutput 仍为 string，升级本身没有增加强类型多模态输出集合。

- 现有 load_image 返回 DataContent；其中图片字节与媒体类型已经完整存在，工具本体无需改写。
- ResponseContentPart.CreateInputImagePart 支持图片字节、URI 和文件 ID，证明当前 SDK 具备原生图片输入表达能力。
- 当前版本 FunctionCallOutputResponseItem 的 FunctionOutput 为 string，未提供强类型多模态输出集合。将 DataContent JSON 序列化后塞进该字符串，不等于提交原生 input_image。
- 不将图片强制转成普通 JSON 文本，不用“已加载图片”的文本替代图片，也不据此宣称 API 无法处理图片。
- 下一步需要最小用法实验，核对原生多模态 function_call_output 的服务端接收及 SDK 表达方式。必要时审查 SDK 原生 JSON 能力或适合的版本；不先实现私有协议补丁。
- 若结果应表达为多个原生 Items，辅助方法的返回类型需据此设计，不能提前固定为单个字符串工具输出。

本轮只记录代码核查事实；未修改审批、子代理或生产工具转换代码，也未宣称图片工具闭环已经验证。
