# 工具接入边界与既有问题

## 接入职责

Responses 调用方只处理工具定义、参数、异步调用和结果。复用已有 AIFunction 实例，不分析子代理内部协议，不接管审批。子代理可以采用任意实现；对调用方仍是一次工具调用。

审批应在工具 InvokeAsync 内等待，批准后执行，拒绝返回失败结果。协议适配层不应负责将“不执行审批”的工具转换为“执行审批”的工具。下面的既有问题单独重构，不在 Responses 辅助方法中增加兜底。

## 已确认的审批问题

位置：AgentLib/Tools/HumanApprovalTool.cs。

- ConfiguredHumanApprovalFunction.InvokeCoreAsync 直接调用内部函数，绕过审批；代码明确依赖外部 BindRuntimeTool 才获得审批行为。
- RuntimeHumanApprovalFunction 的确会 await WaitForApprovalAsync，拒绝时不执行内部函数，但 chatContext 缺失、未创建审批项时仍会直接执行。
- 因此“拿到包装后的 AIFunction，调用就会经过审批”目前不成立。这是原审批实现的封装缺陷，不是 Responses 适配职责。
- 链接取消源创建后未释放，也是该专项的生命周期问题。

后续应先重构审批工具的独立调用契约，再接入协议执行路线。不得让适配器通过识别包装器或补建 Chat 上下文掩盖缺陷。

## 子代理核查

位置：AgentLib/Tools/SubAgentToolProvider.cs。

- 对外通过 AIFunctionFactory 包装 InvokeSubAgentAsync，参数是任务、系统提示词与选择条件，返回 Task<string>。
- 内部使用 IChatClient/ChatClientAgent 是当前实现选择，不要求父调用方使用相同协议；没有理由让 Responses 转换逻辑识别子代理类型或迁移其内部模型调用。
- chatContext 可为空；为空时跳过子代理进度展示，仍执行任务并返回收集结果。因此当前任务入口不强制要求父级 Chat 协议。
- 既有缺陷：InvokeSubAgentAsync 不接受本次调用的 CancellationToken，执行使用注册时捕获的 _cancellationToken。手动上下文创建默认工具时没有传入执行令牌，因此外层 AIFunction.InvokeAsync 的取消不一定传至子代理内部。后续在子代理专项修复，不由协议转换层捕获令牌补救。
- 既有耦合：进度展示直接依赖 CopilotChatContext，需与业务调用契约分开审视，不为此要求父代理采用 Chat 协议。

## 图片结果的 SDK 表达核查

AgentLib 已显式引用 OpenAI 2.14.0，不再依赖传递解析的 2.10.0。已核对 2.14.0 公开 API：FunctionCallOutputResponseItem.FunctionOutput 仍为 string，升级本身没有增加强类型多模态输出集合。

- 现有 load_image 返回 DataContent；其中图片字节与媒体类型已经完整存在，工具本体无需改写。
- ResponseContentPart.CreateInputImagePart 支持图片字节、URI 和文件 ID，证明当前 SDK 具备原生图片输入表达能力。
- 当前版本 FunctionCallOutputResponseItem 的 FunctionOutput 为 string，未提供强类型多模态输出集合。将 DataContent JSON 序列化后塞进该字符串，不等于提交原生 input_image。
- 不将图片强制转成普通 JSON 文本，不用“已加载图片”的文本替代图片，也不据此宣称 API 无法处理图片。
- 下一步需要最小用法实验，核对原生多模态 function_call_output 的服务端接收及 SDK 表达方式。必要时审查 SDK 原生 JSON 能力或适合的版本；不先实现私有协议补丁。
- 若结果应表达为多个原生 Items，辅助方法的返回类型需据此设计，不能提前固定为单个字符串工具输出。

本轮只记录代码核查事实；未修改审批、子代理或生产工具转换代码，也未宣称图片工具闭环已经验证。
