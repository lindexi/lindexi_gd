## 2. LSP 工作目录按需设置与项目范围隔离

### 2.1 背景与问题

当前应用会把整个工作路径直接交给 LSP 编程工具。当一个工作路径包含多个文件夹或多个项目时，LSP 会加载整个工作路径，存在以下问题：

- 查找符号时需要加载过多文件，占用大量内存；
- 无法把符号查找范围限制在目标项目或目标文件夹；
- 其他文件夹中的同名或相关符号可能污染查找结果；
- LSP 初始化与工作路径管理逻辑过于复杂；
- Agent 可以直接调用依赖 LSP 的工具，但不能明确控制本次调用所使用的项目范围。

### 2.2 功能目标

不再在应用初始化或工作区初始化阶段直接为 LSP 设置整个工作路径。

为 Agent 封装一个专用工具，用于在调用任何依赖 LSP 能力的功能之前，显式设置本次需要查找符号的文件夹。LSP 只加载该文件夹，不加载整个应用工作路径。

### 2.3 功能要求

- 新增一个可供 Agent 调用的“设置 LSP 工作文件夹”工具；
- 工具参数为需要使用 LSP 分析的项目目录或文件夹路径；
- 设置成功后，后续依赖 LSP 的工具只在该文件夹范围内工作；
- Agent 可以根据当前任务切换 LSP 工作文件夹；
- 切换工作文件夹时，应释放或替换旧范围对应的 LSP 状态，避免旧项目符号污染新项目；
- 不再把应用的整个工作路径默认传递给 LSP；
- 不依赖 LSP 的文件读取、文件查找等工具不应被该设置限制；
- 现有工作路径仍可用于普通文件工具，但不能自动等同于 LSP 工作文件夹。

### 2.4 调用约束

所有依赖 LSP 能力的工具在执行前必须检查是否已经设置 LSP 工作文件夹，例如：

- 按符号名称查找定义；
- 查找符号引用；
- 查找接口实现；
- 其他需要启动或调用语言服务器的代码分析功能。

如果尚未设置 LSP 工作文件夹，工具不得隐式使用整个工作路径，也不得自行猜测目录，而应直接返回清晰的错误信息，提示 Agent 先调用“设置 LSP 工作文件夹”工具。

建议错误信息至少表达：

```text
尚未设置 LSP 工作文件夹。请先设置需要进行符号分析的项目目录，再调用此工具。
```

### 2.5 验收标准

- 打开包含多个项目或文件夹的工作路径时，不会自动把整个工作路径加载到 LSP；
- 未设置 LSP 工作文件夹时，调用 LSP 工具会收到可读的错误信息；
- 设置某个项目目录后，符号查找结果只来自该目录范围；
- 切换到另一个项目目录后，不会继续返回旧项目中的符号；
- 普通文件工具仍可访问允许范围内的其他文件夹；
- 相比加载整个工作路径，LSP 符号查找的内存占用和结果污染得到明显改善。

## 3. 文件工具以返回值传递错误信息

### 3.1 背景与问题

当前读取文本文件等工具通过抛出异常报告失败。实际测试中，Agent 通常只能看到简单的“工具调用错误”，无法获取异常中的具体原因，因此容易错误判断为文件不可访问、路径无效或权限不足，并基于错误判断继续操作。

### 3.2 功能目标

对于可以预期的工具调用失败，不再依赖异常把信息传递给 Agent，而是直接返回可读的错误信息字符串，使 Agent 能够理解失败原因并采取正确的后续操作。

### 3.3 适用范围

至少检查并调整以下类型的工具：

- 读取文本文件；
- 按行读取文本文件；
- 列出目录内容；
- 查找文件或目录；
- 搜索文件内容；
- 写入、替换或修改文件；
- 其他当前通过异常向 Agent 报告预期失败的文件系统工具。

修复某个工具时，需要同时检查同类工具是否存在相同问题，保持错误返回方式一致。

### 3.4 返回要求

- 对文件不存在、目录不存在、路径格式错误、访问被拒绝、内容读取失败、匹配项不唯一等可预期错误，返回明确的错误信息字符串；
- 错误信息应包含必要上下文，例如操作类型和目标路径；
- 不应只返回“调用失败”或“发生错误”等无法指导 Agent 的笼统文本；
- 错误文本应区分不同失败原因，避免误导 Agent；
- 成功返回值与错误返回值需要有稳定、可辨识的格式；
- 不应把完整异常堆栈直接暴露给 Agent；
- 对进程损坏、程序缺陷等不可恢复异常，可以继续保留异常机制，但预期的输入或文件系统失败应转换为工具返回结果。

建议错误信息示例：

```text
读取文本文件失败：文件不存在。路径：C:\Code\Project\Missing.cs
```

```text
替换文本失败：目标文本在文件中匹配到多处，无法确定唯一替换位置。路径：C:\Code\Project\Program.cs
```

### 3.5 验收标准

- Agent 能直接看到文件工具失败的具体原因；
- 文件不存在时，Agent 不会只收到通用工具调用错误；
- 权限、路径、唯一匹配等不同错误能够被区分；
- 工具失败后，Agent 可以根据返回文本修正路径或调整调用参数；
- 工具调用失败不会被错误解释为统一的“文件不可访问”；
- 成功场景的现有行为不受影响。

## 4. WinRemoteShell 沙盒运行与连接设置

### 4.1 背景与目标

应用后续需要支持在沙盒环境中运行命令和执行开发任务。沙盒连接与远程操作使用 `WinRemoteShell` 工具完成。

应用需要增加一个设置界面，用于配置 WinRemoteShell 客户端路径以及沙盒服务器的 IP 和端口。该设置是后续沙盒执行能力的基础。

### 4.2 参考资料

实现时应参阅以下文档：

- `c:\lindexi\Code\lindexi_gd\lindexi_gd\App\WinRemoteShell\README.md`
- `c:\lindexi\Code\lindexi_gd\lindexi_gd\App\WinRemoteShell\Docs\ImplementationPlan.md`
- `c:\lindexi\Code\lindexi_gd\lindexi_gd\App\WinRemoteShell\Docs\Commands.md`

WinRemoteShell 的关键使用方式包括：

- 通过 `WinRemoteShell.exe exec --server <ip:port> -- <command>` 远程执行命令；
- 通过 `push` 上传文件或文件夹；
- 通过 `pull` 下载文件或文件夹；
- 服务端地址格式为 `ip:port`；
- 服务端地址也支持 `WINRS_SERVER` 环境变量，但本应用应优先使用设置界面中明确保存的连接信息；
- `exec` 支持超时参数，并以流式方式返回标准输出和标准错误；
- WinRemoteShell 服务端维护长期运行的 `cmd.exe`，不同 `exec` 调用之间可能保留工作目录和环境变量状态。

### 4.3 设置界面

增加沙盒设置界面，至少包含以下配置项：

1. **WinRemoteShell 路径**
   - 配置本机 `WinRemoteShell.exe` 的完整路径；
   - 支持手动输入；
   - 建议支持文件选择；
   - 保存前或测试连接前检查路径是否为空以及文件是否存在。

2. **沙盒 IP 地址**
   - 配置运行 WinRemoteShell Server 的沙盒机器 IP 或主机名；
   - 不应与端口混在一个不可拆分的文本字段中保存，便于单独校验和修改。

3. **沙盒端口**
   - 配置 WinRemoteShell Server 的监听端口；
   - 端口必须是有效的整数端口值。

4. **连接测试**
   - 提供测试连接入口；
   - 使用当前界面中尚未保存的值进行测试，便于用户确认后再保存；
   - 测试应执行无副作用或低副作用的简单命令，例如获取当前用户或输出固定文本；
   - 明确显示连接成功、启动失败、超时、地址无效和远端执行失败等结果。

### 4.4 配置持久化

- 保存 WinRemoteShell 路径、沙盒 IP 和沙盒端口；
- 应用重启后自动恢复已保存配置；
- 不在日志、会话或错误信息中输出不必要的敏感连接信息；
- 配置缺失时，沙盒工具应返回明确错误，提示用户先完成沙盒连接设置；
- 修改配置后，后续沙盒调用应使用最新值，不要求重启应用。

### 4.5 沙盒工具调用要求

后续提供给 Agent 的沙盒工具应封装 WinRemoteShell，而不是要求 Agent 自行拼接 WinRemoteShell 命令行。

封装层应负责：

- 从设置中读取 WinRemoteShell 路径、IP 和端口；
- 正确构造 `--server ip:port` 参数；
- 正确处理命令参数边界，避免错误转义或参数拼接；
- 收集并返回远端命令输出；
- 支持超时和取消；
- 将可预期失败转换为 Agent 可读的错误信息；
- 保留 WinRemoteShell 的流式输出能力，以便后续在界面中持续展示执行进度；
- 为上传、下载等后续能力预留扩展空间，但首期设置界面不要求一次性实现全部 WinRemoteShell 命令。

### 4.6 状态持久带来的约束

由于 WinRemoteShell Server 维护全局 `cmd.exe`，工作目录和环境变量可能跨命令保留，因此沙盒执行功能需要明确约束：

- 不能假设每次远程命令都从默认目录开始；
- 对依赖工作目录的操作，应在命令中显式切换到目标目录，或在封装层建立明确的工作目录策略；
- 不应让一个 Agent 任务遗留的目录或环境状态无意影响下一个任务；
- 后续设计沙盒会话隔离时，需要评估全局 cmd 状态共享造成的任务污染问题。

### 4.7 验收标准

- 用户可以在界面中设置 WinRemoteShell.exe 路径、沙盒 IP 和端口；
- 配置可以保存，并在应用重启后恢复；
- 可以使用尚未保存的界面值测试连接；
- 路径不存在、端口无效、连接超时和远端错误都有明确提示；
- 后续 Agent 沙盒工具不需要自行提供 WinRemoteShell.exe 路径或拼接服务器地址；
- 配置缺失时，Agent 收到可理解的设置提示，而不是通用工具调用错误；
- 沙盒命令支持取消和超时，不产生无法管理的后台执行；
- 实现符合 WinRemoteShell 现有命令格式和行为约束。

## 5. 应用自行处理 Agent 工具调用

### 5.1 背景与目标

应用需要自行接管 Agent 的工具调用循环，而不是完全依赖当前框架自动执行工具调用。接管后，应用能够在每次工具调用前后获得明确的控制时机，用于实现更合适的会话压缩策略以及人类插话。

### 5.2 功能要求

- 应用能够识别 Agent 响应中的工具调用请求；
- 应用负责执行工具并把工具结果追加回当前会话；
- 支持 Agent 在收到工具结果后继续请求后续工具，直到返回最终回复；
- 工具调用顺序、工具调用参数、工具结果以及 Agent 后续回复均应保留在同一个会话上下文中；
- 单次工具失败不应破坏整个会话状态，Agent 应能收到明确的失败结果并决定后续行为；
- 应避免重复执行同一个工具调用；
- 应保留现有停止、取消和界面状态更新能力；
- 工具执行控制点应能被会话压缩和人类插话功能复用，不为每项功能重复实现 Agent 调用循环。

### 5.3 工具压缩时机

自行处理工具调用后，应允许应用在不会破坏当前工具调用配对关系的时机压缩会话：

- 不在工具调用请求已经产生、但对应工具结果尚未追加时压缩；
- 优先在一轮工具结果已经完整追加、Agent 尚未开始下一轮推理时判断是否压缩；
- 压缩后必须保留 Agent 继续完成当前任务所需的信息；
- 工具调用请求与工具结果必须成对保留或成对纳入摘要，不能产生缺失工具结果的会话结构；
- 自动压缩是否执行还需要服从界面的“自动压缩”设置。

### 5.4 验收标准

- 连续多轮工具调用可以正常执行并得到最终回复；
- 工具调用与工具结果按正确顺序进入会话；
- 工具失败时 Agent 能读取失败原因并继续处理；
- 压缩不会发生在工具调用和工具结果之间；
- 停止当前会话时，不会在后台继续发起新的工具调用；
- 人类插话可以复用该工具调用控制流程。

## 6. Agent 工具调用期间的人类插话

### 6.1 功能目标

用户可以在 Agent 正在执行工具调用期间输入一条新消息。该操作不取消当前 Agent 会话，也不丢弃已经生成的内容，而是在合适的工具调用边界把用户消息插入当前会话。

### 6.2 插入时机

人类插话采用以下时序：

```text
Agent 请求调用工具
  → 应用执行工具
  → 应用追加工具结果
  → 如果存在待发送的人类插话，立即追加一条用户消息
  → Agent 基于工具结果和用户消息继续执行
```

用户消息必须追加在工具结果之后、下一次 Agent 推理之前。不得把用户消息插入工具调用请求和工具结果之间，以免破坏工具调用协议结构。

### 6.3 交互要求

- Agent 会话执行期间，用户仍可输入并提交插话消息；
- 提交插话不触发当前会话取消；
- 插话消息进入待发送状态，并在下一次工具结果返回后追加；
- 界面应明确显示消息正在等待插入，避免用户误以为消息已经被 Agent 处理；
- 消息真正追加到会话后，应在聊天记录中显示为普通用户消息；
- 如果 Agent 在用户提交插话后没有再调用工具，而是直接结束当前回复，应保留该消息，并在当前回复结束后作为下一条用户消息发送或等待用户确认发送，不能静默丢弃；
- 如果用户主动停止会话，尚未插入的消息应保留在输入区或待发送区；
- 第一阶段至少保证单条待插话消息可靠处理；若支持多条，则必须保持用户提交顺序。

### 6.4 验收标准

- 用户插话不会取消正在执行的 Agent 会话；
- 插话严格出现在完整工具结果之后；
- Agent 下一轮推理能够同时看到工具结果和插话内容；
- 插话不会破坏工具调用请求与工具结果的配对关系；
- 没有后续工具调用时，待插话消息不会丢失；
- 停止、异常或工具失败场景下，待插话消息仍有明确状态。

## 8. 从指定消息开始新建对话

### 8.1 功能目标

用户可以从历史聊天记录中的某一条消息创建一个新的对话分支，用于基于已有上下文尝试不同方案，同时保留原对话不变。

### 8.2 功能要求

- 每条适合分支的消息提供“从此处新建对话”入口；
- 新对话复制原对话从开始到所选消息为止的有效会话上下文；
- 所选消息之后的内容不进入新对话；
- 原对话保持不变，不删除、不截断、不覆盖；
- 新对话获得独立的会话标识、保存记录和后续消息序列；
- 新对话创建后，界面切换到新对话，并允许用户继续输入消息；
- 工具调用请求与工具结果必须保持完整配对，不能从协议结构不完整的位置创建分支；
- 如果用户选择的是工具调用过程中的消息，应自动选择最近的合法边界，或明确提示该位置不能创建分支；
- 新对话应继承创建时必要的系统提示、模型配置和工作区上下文；
- 新对话后续对配置或消息的修改不应反向影响原对话。

### 8.3 验收标准

- 可以从普通用户消息或 Agent 消息创建新对话；
- 新对话只包含所选位置及之前的有效上下文；
- 原对话内容和后续消息保持不变；
- 新旧对话可以分别继续发送消息并独立保存；
- 不会生成缺少工具结果或缺少工具请求的无效会话历史。

## 9. 技能功能

### 9.1 功能目标

支持为 Agent 提供可复用的“技能”。技能用于封装特定任务的说明、规则、提示词以及可选资源，使用户无需在每次对话中重复输入相同的工作要求。

### 9.2 功能要求

- 支持发现和列出当前可用技能；
- 支持查看技能名称、说明和内容；
- 支持在发起任务前选择一个或多个技能；
- 支持在对话过程中按需启用技能；
- Agent 能获知可用技能，并在任务匹配时读取或使用相应技能；
- 技能内容应按需加载，避免把所有技能全文默认加入每轮上下文；
- 应明确技能的来源和作用范围，例如应用级技能、用户级技能或工作区技能；
- 多个同名技能存在时，应有稳定的优先级和来源提示；
- 技能文件无效、缺失或读取失败时，应返回清晰错误，不影响其他技能使用；
- 技能不应绕过现有工具权限、工作区边界和沙盒限制；
- 会话记录应能表达本次任务启用了哪些技能，便于恢复和追踪。

### 9.3 首期范围

首期至少支持以本地文本或 Markdown 文件定义技能，并提供：

- 技能发现；
- 技能列表；
- 技能内容读取；
- 将选中技能提供给 Agent；
- 在界面中查看当前已启用技能。

首期不要求实现技能市场、在线下载、自动更新或脚本直接执行。

### 9.4 验收标准

- 用户可以查看可用技能及其说明；
- 选中技能后，Agent 能按照技能内容处理任务；
- 未选择的技能不会无条件占用大量会话上下文；
- 技能缺失或格式错误时有明确提示；
- 工作区技能与全局技能的来源和优先级可辨识；
- 技能不能突破工具原有的安全和访问限制。

## 10. 自动压缩开关

### 10.1 功能目标

在聊天界面提供“自动压缩”勾选项，让用户决定是否允许应用执行默认的自动对话压缩。

### 10.2 界面与行为

- 聊天界面提供“自动压缩”复选框；
- 勾选时，保留默认的自动压缩行为；
- 取消勾选后，不执行任何默认或自动触发的对话压缩；
- 取消勾选不影响手动“压缩对话”按钮；
- 无论是否勾选，用户都可以点击“压缩对话”按钮手动压缩；
- 自动压缩设置应在开始 Agent 请求前生效，并在自行处理工具调用的各个压缩检查点统一遵守；
- 关闭自动压缩后，如果上下文接近或超过模型限制，应明确提示用户手动压缩，而不是静默重新开启自动压缩；
- 不得因关闭自动压缩而自动删除、截断或改写历史消息；
- 设置是否跨应用重启保留，应与现有界面设置的持久化方式保持一致。

### 10.3 验收标准

- 勾选“自动压缩”时，现有默认压缩机制正常工作；
- 取消勾选后，发送消息和执行多轮工具调用都不会触发自动压缩；
- 关闭自动压缩时，手动压缩按钮仍能正常工作；
- 上下文空间不足时，界面向用户提供明确提示；
- 切换开关后，新状态对后续压缩判断立即生效；
- 人类插话、技能和工具调用流程均遵守同一个自动压缩设置。
