# CodingChatRoom 压缩对话后展示与新会话探索

## 文档定位

本文探索 `CodingChatRoom.AvaloniaShell` 在执行对话压缩之后，如何：

1. 展示压缩后的内容；
2. 创建一个以压缩结果为历史的新会话；
3. 保证新会话后续发送时，模型实际使用的上下文与界面展示一致。

本文记录可行性、方案比较和推荐设计。当前自动压缩流程已经通过工具调用项展示压缩状态和摘要结果，但仍不自动创建新会话。

## 当前自动压缩展示

`CopilotChatManagerToolCallChatReducer` 在实际触发压缩时公开开始、完成和失败事件。`CodingAgent` 使用 `CompressionToolCallObserver` 将这些事件映射到当前助手消息中的 `CompressConversation` 工具调用项：

- 开始时创建工具调用项；
- 完成时仅拼接模型返回的 Assistant 消息作为工具输出；
- 失败时直接使用异常的 `ToString()` 结果作为工具输出；
- 配置主线程调度器时，消息更新会调度到主线程。

## 一、本轮已实现的边界

本轮在发送按钮旁增加“压缩对话”按钮，调用：

- `CopilotChatManager.ReduceSessionAsync(AgentSession, IChatReducer, CancellationToken)`

其行为是：

- 压缩当前 `CopilotChatSession.AgentSession` 中的模型历史；
- 不改写当前会话的 `ChatMessages`；
- 不把压缩摘要作为公开聊天消息展示；
- 不创建新会话；
- 压缩完成后由 `CodingChatApplication` 保存当前会话，使新的 `AgentSessionState` 可以持久化。

这里调用接收 `AgentSession` 的 `ReduceSessionAsync` 重载，以严格保持本轮范围。原有仅接收 `IChatReducer` 的重载除了压缩内部历史，还会向当前 `ChatMessages` 追加“总结对话”和摘要消息，已经包含了“展示压缩内容”的产品行为。

## 二、当前存在两套历史

### 2.1 公开消息历史

`CopilotChatSession.ChatMessages` 是界面展示和结构化会话文件中的公开消息历史。

它包含：

- 用户消息；
- 助手消息；
- 系统提示消息；
- 文本、图片、音频、工具、审批和子代理片段；
- Token 用量信息。

`ChatViewModel` 只把该集合投影到聊天界面。

### 2.2 模型内部历史

`CopilotChatSession.AgentSession` 是模型在后续运行时实际携带的历史。

`CodingAgent.RunAsync` 会：

1. 从 `IManualSendMessageContext` 获取或创建 `AgentSession`；
2. 确保编程助手 System Prompt 已写入内部历史；
3. 调用 `RunWithHistoryCompletionAsync`；
4. 让框架把本轮消息和工具调用结果维护在 `AgentSession` 中。

### 2.3 两套历史不会自动同步

当前压缩器只替换 `AgentSession` 的内存历史：

- 模型看到压缩后的上下文；
- 用户仍看到完整公开聊天记录。

因此，“界面上显示了摘要”不等于“模型会使用摘要”；反过来，“模型内部已经压缩”也不等于“摘要能直接在 UI 中取得”。后续设计必须同时处理两套历史，不能只操作其中一套。

## 三、压缩结果目前是什么

`CopilotChatManagerChatReducer` 的默认流程是：

1. 保留开头连续的 System 消息；
2. 给待总结内容加入总结指令；
3. 调用当前主模型生成摘要；
4. 返回“原 System 消息 + 模型响应消息”。

当前常见结果形态是：

- 若干 System Prompt；
- 一条 Assistant 角色的摘要消息。

接收 `AgentSession` 的 `ReduceSessionAsync` 重载当前返回 `Task`，不会把这组结果返回调用方。

`ReduceSessionAsync` 可以取得内部结果，但只提取其中 Assistant 角色的 `AIContent`，然后向公开历史追加：

- 一条预设用户消息：“总结对话”；
- 一条预设助手消息：压缩摘要。

这说明“展示摘要”在技术上已经可行，但现有 API 把“执行压缩”“提取结果”“向当前会话追加消息”绑在了一起，不适合直接支持预览、新会话或其他展示形式。

## 四、展示压缩内容的可选方案

### 方案 A：直接复用 `ReduceSessionAsync`

行为：

- 压缩当前 `AgentSession`；
- 在当前聊天末尾追加摘要消息。

优点：

- 已有核心实现；
- `CopilotChatMessage` 已支持摘要中的文本和多模态 `AIContent`；
- `ChatViewModel` 无需增加新的展示模型。

问题：

- 摘要会永久混入当前完整聊天历史；
- 用户无法在写入前预览或取消；
- API 没有返回结构化压缩结果；
- 现有 `ReduceSessionAsync` 未暴露取消令牌；
- 它只能展示 Assistant 内容，无法说明哪些 System 上下文被保留；
- 不能自然支持“压缩完成后改为新建会话”。

结论：

- 适合最小化实现“在当前会话显示摘要”；
- 不适合作为长期统一 API。

### 方案 B：让压缩 API 返回结果，再由 Shell 决定如何展示

建议增加独立结果对象，例如包含：

- 压缩后的完整 `ChatMessage` 列表；
- 可展示的摘要 `AIContent`；
- 压缩前后消息数；
- 是否实际发生压缩；
- 是否因未完成工具调用而跳过；
- 可选的 Token 或字符统计。

Shell 可以基于结果选择：

- 只显示一次性预览；
- 追加到当前公开历史；
- 创建新会话；
- 只显示“已完成”，不展示正文。

优点：

- 压缩能力与产品行为解耦；
- 同一结果可以复用到预览、消息展示和新会话；
- 更容易测试“压缩结果是什么”，而不是通过 `AgentSession` 反查。

问题：

- 需要调整 `AgentLib` 公共 API；
- 需要定义 `ChatMessage` 到 UI 消息的映射边界；
- 工具调用、图片或未来内容类型不能只按纯文本处理。

结论：

- 推荐作为后续演进的基础。

### 方案 C：增加独立摘要面板

行为：

- 压缩后不修改 `ChatMessages`；
- 在聊天区顶部、侧栏或弹窗中展示“当前模型上下文摘要”。

优点：

- 不污染原始公开聊天记录；
- 用户容易理解“完整记录”和“模型当前记忆”是两回事；
- 可以展示压缩时间、压缩前后规模等元数据。

问题：

- 需要新增摘要状态的生命周期和持久化策略；
- 仅从 `AgentSession` 恢复时，Shell 目前没有独立摘要字段；
- 如果摘要再次被压缩，面板需要更新；
- 需要定义切换会话时的加载和清理行为。

结论：

- 产品表达最清晰，但工作量高于直接追加消息。

## 五、压缩后创建新会话的可行性

### 5.1 目标语义

用户期望的新会话应同时满足：

1. 左侧历史列表出现一个新的会话；
2. 新会话界面能看到压缩摘要；
3. 原会话仍可保留并打开；
4. 在新会话继续发送时，模型使用压缩后的历史，而不是空白历史；
5. 原会话和新会话后续运行互不影响。

该能力技术上可行，但不能只调用现有 `CreateNewSessionAsync`。

### 5.2 只把摘要加入新会话的 `ChatMessages` 不足够

如果新会话只有一条公开摘要消息，但 `AgentSession` 为 `null`：

- UI 看起来有历史；
- 下一次发送时会创建新的空 `AgentSession`；
- 当前 `CodingAgent` 不会自动从 `ChatMessages` 重建模型历史；
- 模型实际上不知道界面中展示的摘要。

因此，该方案会产生“界面有摘要、模型无摘要”的错误状态，不建议采用。

### 5.3 不能让两个会话共享同一个 `AgentSession`

直接把压缩后的 `AgentSession` 同时设置给原会话和新会话，会造成共享可变状态：

- 在任一会话继续发送都会修改同一个内部历史；
- 两个公开会话会悄悄影响彼此；
- 保存顺序可能让两个会话文件写入不同时间点的同一状态；
- 并发运行风险增加。

因此，新会话必须拥有独立的 `AgentSession` 实例。

### 5.4 可通过序列化和反序列化克隆压缩后的会话状态

当前 `FileCodingChatSessionStore` 已使用：

- `ChatClientAgent.SerializeSessionAsync`；
- `ChatClientAgent.DeserializeSessionAsync`。

这条能力可以用于创建独立副本：

1. 完成压缩；
2. 序列化压缩后的 `AgentSession`；
3. 反序列化得到新的 `AgentSession` 实例；
4. 创建新的 `CopilotChatSession`；
5. 把新 `AgentSession` 设置到新会话；
6. 向新会话的公开历史加入来源说明和摘要；
7. 保存并选择新会话。

相对于直接复制 `List<ChatMessage>`，序列化克隆更稳妥，因为 `AgentSession` 的状态不一定永远只有内存消息列表。

## 六、新会话方案比较

### 方案 1：先压缩原会话，再克隆到新会话

流程：

1. 压缩当前会话；
2. 保存当前会话；
3. 克隆压缩后的 `AgentSession`；
4. 创建并保存新会话；
5. 切换到新会话。

优点：

- 与本轮“压缩当前会话”的按钮语义一致；
- 原会话后续也会使用压缩历史；
- 实现路径直接。

问题：

- 原会话内部历史已经不可逆地替换为摘要；
- 如果新会话创建失败，原会话仍然已经压缩；
- 需要在 UI 上明确“原会话也已压缩”。

适合：

- 产品明确把压缩视为当前会话状态变更，并把新会话视为可选后续动作。

### 方案 2：克隆原会话，再只压缩新会话

流程：

1. 序列化当前 `AgentSession`；
2. 反序列化为独立副本；
3. 只压缩副本；
4. 创建新会话并设置压缩后的副本；
5. 原会话保持原始内部历史；
6. 保存并切换到新会话。

优点：

- 原会话完全不变；
- “从当前会话创建压缩分支”的语义清晰；
- 新会话失败时更容易回滚。

问题：

- 与当前“压缩对话”按钮的直接语义不同；
- 需要先克隆再压缩，流程和资源消耗更高；
- 需要新的业务入口，例如“压缩并新建会话”。

适合：

- 希望把压缩当作分支操作，而不是修改原会话。

### 方案 3：只用摘要文本重建一个最小 `AgentSession`

流程：

- 创建空 Agent 会话；
- 保留编程助手 System Prompt；
- 把摘要作为 System 或 Assistant 历史写入；
- 不复制其他 Agent 状态。

优点：

- 新会话非常干净；
- 上下文规模最可控；
- 不依赖完整状态克隆。

问题：

- 可能丢失 reducer 保留的非文本内容和框架状态；
- 摘要角色如何注入需要明确；
- 如果只把摘要作为 Assistant 消息，后续模型语义可能不如专用 System 上下文稳定；
- 与实际压缩结果可能不完全一致。

适合：

- 后续明确把“摘要会话”定义为一种全新的、只继承文字摘要的会话类型。

## 七、推荐设计

推荐采用“两阶段能力 + 独立新会话”的设计。

### 阶段一：让压缩返回结构化结果

在 `AgentLib` 中增加不会修改公开消息的压缩入口，返回：

- 压缩后的完整模型消息；
- 适合展示的摘要内容；
- 压缩状态和统计信息。

现有 `ReduceSessionAsync` 可以改为基于该入口实现，保持兼容。

### 阶段二：由 Shell 提供明确的后续动作

压缩完成后可提供两个独立动作：

- “查看摘要”：显示预览或摘要面板；
- “以摘要新建会话”：创建独立会话并切换。

不建议让一次普通点击在没有提示的情况下同时修改原会话、追加公开消息并切换会话。

### 推荐的新会话语义

若产品目标是“点击压缩之后就能新建一个会话”，建议采用：

- 原会话完成压缩并保存；
- 从压缩后的状态序列化克隆独立 `AgentSession`；
- 新会话公开历史显示一条系统来源说明和一条助手摘要；
- 新会话持有克隆后的压缩 `AgentSession`；
- 新会话标题使用“摘要：原标题”，并遵守现有标题长度规则；
- 新会话保存成功后才加入列表并切换；
- 原会话和新会话都保存成功后才报告整体成功。

如果更重视原会话不可变性，则应另设“压缩并创建分支”命令，采用先克隆再压缩的方案。

## 八、建议的数据与 API 调整

### 8.1 压缩结果对象

建议不要让 AvaloniaShell 直接解析 `AgentSession`，而由 `AgentLib` 返回稳定结果对象。结果至少需要表达：

- `ReducedMessages`：模型实际使用的压缩后历史；
- `SummaryContents`：可直接映射到 `CopilotChatMessage` 的摘要内容；
- `WasReduced`：是否实际压缩；
- `OriginalMessageCount`；
- `ReducedMessageCount`。

如果 `ToolCallAwareChatReducer` 因未完成工具调用跳过压缩，也应通过状态明确返回，而不是让 UI 把“原样返回”误报为压缩成功。

### 8.2 应用协调层入口

建议由 `CodingChatApplication` 提供业务级方法，统一负责：

- 活动操作互斥；
- 压缩；
- AgentSession 克隆；
- 新会话创建；
- 会话摘要列表更新；
- 持久化；
- 失败回滚；
- 状态通知。

`ChatViewModel` 不应直接组装或保存 `CopilotChatSession`。

### 8.3 会话创建 API

现有 `CopilotChatManager.CreateNewSession` 会创建或复用空会话并加入欢迎消息，不适合直接创建“带指定公开历史和指定 AgentSession”的摘要会话。

可选做法：

- Shell 自行构造 `CopilotChatSession`，然后调用 `AddSession(session, select: true)`；
- 或在 Manager 增加接受已构造会话状态的工厂方法。

首选前者，避免把 CodingChatRoom 特定的摘要会话产品语义放入通用 Manager。

## 九、公开摘要消息建议

新会话的公开历史建议包含：

1. 系统来源说明，例如“此会话由‘原会话标题’压缩创建”；
2. 一条 Assistant 摘要消息，保留 reducer 返回的 `AIContent`；
3. 不复制原会话全部公开消息。

这些消息可标记为 `IsPresetInfo = true`，因为模型真实上下文已经由克隆后的 `AgentSession` 提供，避免将来某些重建流程重复注入摘要。

需要注意：

- 如果未来改成从 `ChatMessages` 重建 `AgentSession`，必须重新审视 `IsPresetInfo` 语义；
- System Prompt 不应作为普通公开消息完整展示，避免泄露内部指令；
- 摘要中若包含图片或其他内容，应使用现有多模态消息项，不要只取 `ChatMessage.Text`。

## 十、持久化与失败处理

### 10.1 保存内容

新会话需要同时保存：

- 新的 SessionId 和 StartedTime；
- 标题；
- 来源说明与摘要公开消息；
- 克隆后的压缩 `AgentSessionState`。

### 10.2 提交顺序

建议顺序：

1. 在内存中创建完整的新会话对象；
2. 保存新会话；
3. 保存原会话的压缩状态；
4. 加入 Manager 和摘要列表；
5. 切换选择；
6. 通知 UI。

若希望更强的原子性，存储层需要增加临时文件或批量提交能力。当前逐会话保存无法提供跨两个文件的真正事务。

### 10.3 失败策略

- 压缩失败：不创建新会话；
- 克隆失败：保留原会话，报告无法创建摘要会话；
- 新会话保存失败：不要把未持久化会话加入历史列表；
- 原会话保存失败：需要明确是否允许保留已保存的新会话；
- 切换失败：恢复原选择并移除未完成的新会话注册；
- 应保留取消语义，不把取消统一显示为普通失败。

## 十一、并发与交互建议

压缩和创建摘要会话期间应禁止：

- 发送消息；
- 停止之外的重复压缩；
- 新建、打开和删除会话；
- 可能修改同一个 `AgentSession` 的其他操作。

后续若压缩耗时明显，建议增加：

- “正在压缩对话”状态；
- 可取消入口；
- 完成后的“查看摘要”和“新建摘要会话”动作；
- 明确说明原会话是否已被压缩。

## 十二、测试建议

### 核心压缩结果

- 有历史时返回摘要及压缩后消息；
- 无 `AgentSession` 时返回不可压缩状态；
- 未完成工具调用时返回跳过状态；
- 多模态摘要内容不丢失；
- 取消时不报告成功。

### 新会话

- 新旧会话的 `AgentSession` 不是同一实例；
- 新会话后续发送会携带摘要上下文；
- 原会话后续发送不会受到新会话修改；
- 新会话公开历史只包含来源和摘要；
- 标题和会话摘要列表正确；
- 保存失败时不污染 Manager 和 UI 列表；
- 应用重启后能恢复摘要公开消息和压缩后的 AgentSession。

### UI

- 压缩期间相关命令禁用；
- 压缩成功后可以查看摘要或创建新会话；
- 切换新会话后显示摘要内容；
- 原会话仍可从左侧列表打开；
- 失败和取消反馈清晰且不会产生空会话。

## 十三、结论

可以展示压缩后的对话内容，也可以创建一个以压缩结果为历史的新会话。

其中：

- 仅展示摘要：可直接复用现有 `ReduceSessionAsync`，但更推荐先让压缩 API 返回结构化结果，再由 Shell 决定展示方式；
- 新建摘要会话：必须同时创建公开摘要消息和独立的压缩 `AgentSession`，不能只展示摘要文本，也不能与原会话共享同一个 `AgentSession`；
- 最稳妥的独立会话复制方式是复用现有 `SerializeSessionAsync` / `DeserializeSessionAsync`；
