# CodingChatRoom 循环迭代功能设计方案

## 1. 功能目标

为 `CodingChatRoom.AvaloniaShell` 增加循环迭代模式。

用户在输入框中填写一段文本，例如：

```text
根据 xxx\Docs\next-session-handoff.md 开始工作
```

勾选“循环迭代”后点击发送，应用重复执行以下流程：

```text
发送当前输入文本
  → 等待会话执行完成
  → 压缩会话
  → 再次发送同一文本
  → 无限重复，直到用户点击停止
```

循环用于让编程代理持续读取任务交接文档、完成当前步骤并更新交接文档，从而连续推进长任务。

本文只描述实现方案，不修改代码。

## 2. 设计原则

循环迭代是现有发送功能上的一个很小的控制流扩展，不引入新的业务层次，也不重新实现发送或压缩逻辑。

实现遵循以下原则：

- 原有普通发送方法保持不变；
- 原有压缩会话方法保持不变；
- 循环方法只负责依次调用现有发送和压缩方法；
- 循环所需数据全部使用方法参数和局部变量；
- 不在 `CodingChatApplication` 中增加循环轮次、循环阶段、循环提示词等共享状态；
- 不捕获或保存 `WorkspacePath`，每次发送仍完全沿用原有发送方法的行为；
- 不修改 AgentLib；
- 压缩过程继续使用当前已有接口，不额外传递取消令牌；
- 整个功能一次性实现。

## 3. 界面设计

### 3.1 循环模式勾选框

在聊天输入区域增加一个勾选框：

```text
[ ] 循环迭代
```

勾选框放在发送按钮附近，使它与本次发送行为形成直接关联。

建议布局：

```text
┌──────────────────────────────────────────────────────────────┐
│ 消息输入框                                                   │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│ [ ] 循环迭代                          [压缩会话] [停止] [发送] │
└──────────────────────────────────────────────────────────────┘
```

不增加独立的循环文本输入框。循环使用用户点击发送时消息输入框中的文本。

### 3.2 勾选框行为

“循环迭代”只用于决定下一次点击发送时采用普通发送还是循环发送。

点击发送时：

1. 如果未勾选“循环迭代”，执行原有发送逻辑；
2. 如果已勾选“循环迭代”：
   - 读取当前输入文本；
   - 立即取消勾选“循环迭代”；
   - 调用循环执行方法。

开始循环后立即取消勾选，可以明确表示该勾选框是一次性的启动选项，而不是当前循环状态指示器，也避免循环结束后下一次发送被意外再次作为循环启动。

### 3.3 停止按钮

继续使用现有停止按钮，不增加新的“停止循环”按钮。

用户点击停止后，停止当前正在执行的发送操作。循环方法在当前发送调用结束后检查取消状态并退出，不再进入下一次压缩或发送。

如果用户在压缩期间点击停止，由于现有压缩接口不接收取消令牌，本次压缩会正常执行完成；压缩返回后，循环检查停止状态并退出，不再发送下一轮消息。

## 4. ViewModel 设计

### 4.1 新增界面属性

在 `ChatViewModel` 中增加一个布尔属性，用于绑定“循环迭代”勾选框，例如：

```csharp
public bool IsLoopIterationEnabled { get; set; }
```

该属性只表示用户是否要求下一次发送进入循环模式，不表示循环当前是否正在运行。

### 4.2 调整发送命令逻辑

现有发送命令保留同一个界面入口，在发送方法中增加一次简单分支：

```text
读取并校验输入内容
  → 判断 IsLoopIterationEnabled
      → false：调用原有发送方法
      → true：先将 IsLoopIterationEnabled 设为 false，再调用循环执行方法
```

循环开始前应把输入文本保存到局部变量。后续每轮都发送这个局部变量中的同一份文本，不再读取输入框，避免输入框清空或界面内容变化影响已经启动的循环。

普通发送分支继续执行当前逻辑，不改变现有行为。

## 5. 应用层设计

### 5.1 循环执行方法

在 `CodingChatApplication` 中增加一个循环执行方法。该方法直接在一个方法体内完成循环，不增加循环控制器、循环服务、循环状态对象或其他内部抽象。

方法所需内容只有：

- 作为参数传入的固定消息文本；
- 作为参数传入或由现有停止机制提供的取消令牌；
- 方法内部的无限循环；
- 异常后的十秒等待。

循环逻辑如下：

```text
while 未停止
  try
    调用原有发送方法并等待完成
    检查是否停止
    调用原有压缩会话方法并等待完成
  catch 任意异常
    等待 10 秒
```

压缩完成后自然进入下一次循环，再次调用原有发送方法。

第一轮直接发送，不在第一次发送前压缩。

### 5.2 复用原有方法

循环方法调用现有公开方法：

```text
SendMessageAsync
CompressConversationAsync
```

不拆分发送核心方法，不拆分压缩核心方法，不复制其中的会话保存、活动状态、运行等待或界面通知逻辑。

原有方法仍然分别负责自己的完整行为。循环方法只负责调用顺序和重复执行。

### 5.3 局部变量

固定发送文本保存在循环方法的参数或局部变量中。

异常、延迟和取消判断也全部在循环方法内部处理。

`CodingChatApplication` 不需要增加以下字段：

- 当前循环提示词；
- 当前循环轮次；
- 当前循环阶段；
- 循环会话 ID；
- 循环工作路径；
- 单独的循环状态对象。

现有活动操作状态和停止机制继续负责界面是否忙碌以及当前发送任务的取消。

### 5.4 工作路径行为

循环方法不读取、不捕获、不缓存 `WorkspacePath`。

每轮调用原有发送方法时，由原有发送方法按照当前实现自行处理工作路径。循环功能不介入工作路径的获取和传递。

### 5.5 异常重试

循环内部捕获每轮发送或压缩过程中出现的所有异常。

发生异常后：

1. 不结束循环；
2. 不把异常继续抛给循环方法的调用方；
3. 等待 10 秒；
4. 等待完成后立即开始下一次循环；
5. 下一次循环仍从发送固定文本开始。

十秒等待必须能够响应停止操作。若用户在等待期间点击停止，应立即结束等待并退出循环，而不是继续开始下一轮。

异常处理范围以单次“发送加压缩”循环为边界。无论异常发生在发送阶段还是压缩阶段，下一轮都重新从发送开始。

## 6. 执行时序

### 6.1 正常执行

```text
用户输入固定文本
  → 勾选“循环迭代”
  → 点击发送
  → ViewModel 读取固定文本
  → ViewModel 取消勾选“循环迭代”
  → 调用 CodingChatApplication 循环执行方法
  → 第 1 次调用原有发送方法
  → 等待第 1 次会话执行完成
  → 检查停止状态
  → 第 1 次调用原有压缩方法
  → 等待第 1 次压缩完成
  → 第 2 次调用原有发送方法
  → 等待第 2 次会话执行完成
  → 第 2 次调用原有压缩方法
  → 持续重复
```

### 6.2 发送阶段发生异常

```text
调用原有发送方法
  → 发生异常
  → 循环方法捕获异常
  → 等待 10 秒
  → 重新调用原有发送方法
```

本轮发送失败后不执行压缩，下一轮重新从发送开始。

### 6.3 压缩阶段发生异常

```text
发送完成
  → 调用原有压缩方法
  → 发生异常
  → 循环方法捕获异常
  → 等待 10 秒
  → 重新调用原有发送方法
```

压缩失败后不补做本次压缩，下一轮重新从发送开始。

### 6.4 用户停止

发送期间停止：

```text
用户点击停止
  → 当前发送按原有机制取消或结束
  → 循环检测到停止
  → 退出循环
```

压缩期间停止：

```text
用户点击停止
  → 当前压缩继续执行完成
  → 循环在压缩返回后检测到停止
  → 退出循环
```

异常等待期间停止：

```text
用户点击停止
  → 十秒等待被取消
  → 退出循环
```

## 7. 并发与界面可用性

循环运行期间沿用现有活动操作限制：

- 发送阶段由原有发送方法设置和清理活动状态；
- 压缩阶段由原有压缩方法设置和清理活动状态；
- ViewModel 按现有状态控制发送、压缩、停止和会话相关操作的可用性。

循环方法不建立第二套活动状态。

在发送和压缩两个调用之间，循环方法应立即继续执行，不额外调度后台控制器，也不引入可被其他界面操作插入的人工阶段。

## 8. 预计修改范围

实现集中在 `CodingChatRoom.AvaloniaShell`：

- `ChatView.axaml`
  - 在发送按钮附近增加“循环迭代”勾选框；
  - 绑定 ViewModel 的循环模式属性。

- `ChatViewModel.cs`
  - 增加循环模式布尔属性；
  - 在现有发送命令中判断循环模式；
  - 循环启动时取消勾选；
  - 普通模式继续调用原有发送方法；
  - 循环模式调用应用层循环执行方法。

- `CodingChatApplication.cs`
  - 增加一个循环执行方法；
  - 在方法内部使用局部变量完成发送、压缩、异常等待和取消判断。

- 界面字符串资源文件
  - 增加“循环迭代”文本资源，并沿用项目现有本地化方式。

- 对应测试项目
  - 增加循环分支、执行顺序、异常重试和停止行为测试。

## 9. 测试方案

### 9.1 ViewModel 测试

验证以下行为：

1. 未勾选循环模式时，点击发送只调用原有发送方法；
2. 勾选循环模式时，点击发送调用循环执行方法；
3. 循环执行方法收到的是点击发送时输入框中的文本；
4. 启动循环前，循环模式属性被恢复为 `false`；
5. 输入为空时继续遵循现有校验规则，不启动普通发送或循环发送。

### 9.2 应用层测试

通过可控制的现有发送和压缩依赖验证调用顺序：

```text
发送 → 压缩 → 发送 → 压缩
```

还应验证：

1. 第一轮执行发送，不先压缩；
2. 每次发送完成后才调用压缩；
3. 每次压缩完成后才开始下一次发送；
4. 发送异常后不调用本轮压缩，等待后重新发送；
5. 压缩异常后等待，然后重新发送；
6. 用户停止后不再开始新一轮发送；
7. 异常后的十秒等待可以被停止操作取消；
8. 循环每轮发送同一份固定文本。

测试中使用可控时间机制或项目已有的延迟抽象验证十秒重试，避免测试真实等待十秒。

### 9.3 界面测试

验证：

- 输入区域存在“循环迭代”勾选框；
- 勾选框双向绑定正确；
- 原发送按钮仍是普通发送和循环发送的统一入口；
- 现有停止按钮仍可用于停止循环。

## 10. 验收标准

功能完成后应满足：

1. 聊天输入区域显示“循环迭代”勾选框；
2. 未勾选时，发送行为与当前版本一致；
3. 勾选后点击发送，会立即取消勾选并启动循环；
4. 循环固定重复发送点击发送时的文本；
5. 每次发送都等待当前会话完整执行结束；
6. 每次发送成功完成后都等待会话压缩完成；
7. 压缩完成后自动开始下一次发送；
8. 发送或压缩发生异常时，循环等待十秒后从发送重新开始；
9. 用户点击现有停止按钮后，循环不再启动下一轮；
10. 循环不捕获或缓存 `WorkspacePath`；
11. AgentLib 不发生修改；
12. 原有普通发送、手动压缩和停止功能保持原有行为；
13. 实现只增加必要的界面属性、发送分支和单个循环方法，不引入额外循环状态或架构层次。
